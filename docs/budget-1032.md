# Board budget detail

Request counting and the board budget that [taskq.md](../taskq.md) § 4 and § 5 decide.

## Counting format

Moved from taskq.md § 4 Log and board budget, which keeps the rules.

- **Log line:** `<UTC time> <text>`, time `YYYY-MM-DD HH:mm UTC` from the local clock; the lines of one message, an HTTP error body or a panic included, fold into one line.
- **Operation:** `<METHOD> <path>`, the path API-relative, at most 3 segments, numbers as `N`, other ids as `*`; later pages count under their first page. A 304 reply to a conditional GET counts apart as `<op> 304`: GitHub does not bill it, so the host rate below leaves it out (#1985).
- **Pause:** a 403 or 429 with `retry-after`, or with zero `x-ratelimit-remaining`/`ratelimit-remaining`, pauses the process's board calls on the monotonic clock until `retry-after`, else the reset header against the reply `Date`, else 60 s; at most 1 h. A GraphQL `RATE_LIMIT` or `RATE_LIMITED` error, over HTTP 200 or 403, pauses like a 403 even without those headers. Log lines: `rate limit: board requests paused until <time>` and `... resumed`.
- **Buckets:** GitHub budgets per `x-ratelimit-resource` (`core`, `graphql`); `remaining`, `limit`, `reset` and `resource` are those of the bucket with the lowest remaining share.
- **`status.json` `requests`:** `since`, cumulative `total` and `ops`, `last_hour` (null until a full hour), last `remaining`/`limit`, `paused_until`; under the alarm also `reset`, `resource` and `top`.
- **Host share (#1985, #2084):** each heartbeat carries `requests <n>/h`, the billed requests (no `304` operations, no `GET rate_limit`) of that host's service in its last full hour, then `requests <api host> <n>/h` per board API host it called (`api.github.com`, `gitlab.com`: the host name only, no user, port or path). The `taskq status` `Hosts:` line shows ` <n> req/h` per host, with ` (github.com <g>)` when the heartbeat names `api.github.com`; an older heartbeat with only `requests <n>/h` shows ` <n> req/h`. `taskq status` also prints `Board quota: <used>/<limit> core used, <remaining> left until <reset>` from its own reads: the `core` budget, never `graphql`; GitLab's one unnamed budget shows without a name. When its reads carried no core budget, a GitHub board reads `GET /rate_limit`, which GitHub does not bill; else `Board quota: unknown (no core budget headers)`.
- **Hourly log:** `requests 1h: <total>; <op> <n>, ..`, top 8 operations, then `other`.
- **Alarm log:** `board budget low: <remaining>/<limit> <resource> until <reset>; top here: <op> <n>`, `top` being the largest operation of this process's current hour.
- **Sources (#1084):** `source` is `service` or `<role> <command>`; `service` adds its subcommand; the role is `worker`/`reviewer` from `TASKQ_ROLE`, else `cli`; other words are `*`.
- **Pass cost:** on github.com one GraphQL query per 100 open issues, 1 point: labels are its only nested connection (#1043). Assignees, which would double it, are read per issue only for an `assignee-only` candidate or a report `assignee` filter. Other boards use REST. A dependency of this board is read off the open list once per process until listed open again; one of another repository each pass until done.

## Contract detail

Moved verbatim from `taskq.md` (#1179) to keep the contract under its R8 size bound. `taskq.md` keeps the decision and links here; this text keeps the same authority (R8, R13).

- Log and board budget (#1009): each service log line is `<UTC time> <text>` (`YYYY-MM-DD HH:mm UTC`, local clock); a multi-line message (HTTP error body, panic) folds into it. Service threads share one counter and pause per API host and credential; CLI and worker processes count separately. A rate-limit reply pauses all calls sharing that budget until the reset, at most 1 h, in every process of the install: the process that got it writes the reset (Unix seconds, its own clock) to `<install>/requests-paused-<key>` (`<key>`: 16 hex of SHA-256 of API root and credential), and each process reads that file before a request and adopts a future reset; calls fail at once naming the reset, the service logs one paused and one resumed line and resumes without a restart (operation names and header rules: [counting format](budget-1032.md#counting-format)). `status.json` `requests` holds the counts, the last `remaining`/`limit` and `paused_until`; the log gets `requests 1h: ..` hourly; `service status`/`list` print `Board requests: <n>/h; ..` (else unknown with reason) and the pause. #988 profiling times operations; this counts requests. CLI processes and workers count alone and pause with the install; coreq update and incident requests are not counted. Sources (#1084): a CLI process with board requests at exit, and the service [every 4 minutes and at a clean end](../taskq.md#board-request-records), append one `taskq-requests {at_ms, source, ops}` telemetry record. Board access budget (#1011): one board user's 5000 requests/h serve every host, project, service, CLI, worker, PM and DashQ. A service pass costs one open-issue list (github.com: GraphQL, labels only, skipped while a conditional probe of the `taskq` issues updated since the newest known task update returns 304 or only pull-request changes; full list at least every 5 min; #1819, #1968). Host heartbeats (#2083): heartbeat writes no longer change that probe, so three beating hosts leave it at 304. Other hosts' heartbeats, held drafts and other open issues are read only by the full list, so a kept copy is at most 5 min older than the board; this host's heartbeat write patches the kept list from its reply. Its last confirmed open heartbeat reply also survives full-list refreshes for the same credential: replace only a strictly older, still-listed trusted heartbeat, never a missing/equal/newer row. A create, close or reopen drops the kept list; closing or reopening that heartbeat drops its retained write. Leases read heartbeat age from the kept copy, which is never newer than the board: a copy fresh when listed (`listed - updated <= ttl`) that reads past `ttl` now relists before the pass uses it, so a live host never reads stale from a kept copy, and a stopped one reads stale at the first pass after `updated + ttl`, as with a full list each pass; a heartbeat already stale when listed relists no more. Every process repeats a GET with `If-None-Match` and its last `ETag` and reuses that body on 304, which GitHub does not count; issue, comment and event reads keep that `ETag` and body in `<install>/board-cache-<key>/` (one file per URL, pruned after 24 h or past 4096 entries), so a CLI process or a restarted service gets the 304 too (#1985); the admission scan and reports collection list `taskq` issues from the newest task update they have seen, so an unchanged board repeats one URL and answers 304, and every issue updated since their last full scan (heartbeats aside; closed and label-removed issues included) at least every 30 min, where admission coverage ends (#1985, #2083, #2352); the admission scan runs every 3 min and reports collection every three polls under `ttl`, each sooner when a source is unresolved or a close asks (#2352); GitLab keeps the open list the same way, and its `tasks` read asks for `taskq` issues only (#2352); it re-reads comments only of issues whose `updated_at` moved, writes the heartbeat only on a change other than a host-wide value, or past `ttl / 3` with an attempt or `ttl / 2` without (`min(60 s, ttl / 3)` with execution rows; #2352), reuses that issue for leases, verifies each label once per process and reads dependencies only for a would-be `ready` task (§ 1). Reports collection (§ 7) settles a report source missing (HTTP 404) at its result SHA: it is never fetched again and does not hold back the collection cursor (#1968). It reads comments only of closed taskq issues and keeps one board per project between passes, so `/user` and conditional replies are reused (#1973). Every process of the install reuses the board login kept in `<install>/board-user-<key>` instead of `GET /user`; on github.com the first board clock comes from `GET /rate_limit`, which GitHub does not count (#1985). Pacing (#1985): while the last `remaining` is at most 20 % of `limit`, each request first waits the time to the reset divided by the requests left, at most 5 s; `remaining` is per board user, so every host slows together before it reaches 0. Agent CI waits: § 7 rule 7. Budget alarm: at `remaining` <= 20 % of `limit` the service logs `board budget low` once per reset, and `service status`/`list` and R6 line 1 show `Board budget low: <remaining>/<limit> <resource> until <reset> (<host>); top here: <op> <n>`.
