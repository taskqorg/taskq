# Live release timing: 4.6.62

## Question

Does one real release of the #2234 flow reach the win and pds18 hosts within 15 minutes of the PM's `live` push? The measured span runs from the push to each host heartbeat that reports the new version.

## Findings

Run: [release.yml 41553937099](https://github.com/taskqorg/taskq/actions/runs/41553937099), `live` push of merged `main` commit `46fefa03` ([#2235](https://github.com/taskqorg/taskq/pull/2235)). Its merge result CI is [tests merge_group 41551954549](https://github.com/taskqorg/taskq/actions/runs/41551954549): success. Release: [v4.6.62](https://github.com/taskqorg/taskq/releases/tag/v4.6.62).

Heartbeat times come from the GitHub edit history of the host issues (`userContentEdits`): pds18 #1869, win #745. The pds18 heartbeat switched `running` to 4.6.62 between the edits at 00:38:54 and 00:39:03. The PM note reads pds18 at 00:39:13 and win at 00:42:40; the win time matches the first heartbeat with `selected 4.6.62`, not a running service on the new version.

Win diagnosis: the heartbeat at 00:45:01 lists live worker attempts `#2239` (execution `active`, one pending tool) and `#2240`. The update installed `current` at 00:42:04, and the running service waits for the restart handover (taskq.md § 8 rule 3). A pending restart admits nothing and waits until no childless attempt remains, so the host keeps the old binary while the worker runs.

Publication on github.com (A2):

- Lock: `release-publish.sh` takes `refs/taskq-release-locks/v4.6.62` before each OS writes its assets and deletes it afterwards. The three publishers ran at 00:38:14, 00:39:30 and 00:39:53, without overlap, and each finished. After the run, `git ls-remote origin 'refs/taskq-release-locks/*'` lists no ref.
- Draft then publish: the tag job created a draft (`releases/tag/untagged-…` at 00:35:32). The first publisher, linux, un-drafted it: `publishedAt` 00:38:24, 1 min before macos and windows were published. The release `createdAt` 00:18:34 is the commit date, which GitHub reports as the release creation date.
- Per-OS merge: the final `latest.json` lists `linux-x86_64`, `macos-aarch64` and `windows-x86_64`, plus the shared web assets. `SHA256SUMS` lists all three binaries. The release assets include all three binaries.

## Options

1. Accept as measured. + The release pipeline (push to the last publish) takes 4:47 and pds18 runs the new version in 3:43. − Win's running version depends on worker length.
2. Count `selected` as reporting the new version. + Win meets the target at 6:44. − Hides that the old binary still serves admission and heartbeat lines.
3. Shorten the win handover. + The running version follows `current` within minutes. − Native handover of a live CLI worker is protected recovery work (§ 8 rule 3) and needs its own qualification.

## Verdict

confirmed for the release pipeline and pds18: the push-to-publish span is 4:47, and pds18 reported 4.6.62 at 3:43. The 15-minute total is exceeded at the win step: `selected` changed at 6:44, but `running` was still 4.6.61 after 13 min. The overrun step is the win restart handover, which waits for live attempts #2239 and #2240.

## Recommendation

Accept option 1. The pipeline target is met, and the win running version waits for its live worker. Status should show `selected` next to `running` so that a pending restart is visible.
