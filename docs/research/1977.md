# Reports in Conversations

## Question

How can the operator read and decide reports, answer questions and inspect finished work in one place with fewer section changes?

## Findings

- At source `554552daf48d5b413918d54a8a6d0f88efba4020`, `workspace.js` mounts a separate Results reader; `task-workspace.css` hides Conversations while it is open. Reports and ordinary results already share a collected, SHA-bound projection and board markers in `reports.rs`/`reports.js` ([existing contract](../design/reports.md#contract-detail)).
- The [operator paths](../design/reports-conversations.md#baseline-and-five-operator-paths) compare five fixed wide-window jobs from an open report. Of the four currently supported paths, three remove a click and one ties; all four remove a section switch. Report Accept is currently unavailable, so the proposed two-click acknowledgement was explicitly accepted with the Product design rather than assigned a fabricated baseline. These are source-based counts, not native timing or a general narrow-window claim.
- [RC1–RC7](../design/reports.md#conversations-design-checkpoint-1977) preserve closed originals, held-only creation, source identity, stale/unknown handling and local archive boundaries. Accept is acknowledgement; Make tasks remains explicit.
- The [six-screen reference](../design/reports-conversations.md#six-screen-reference) uses the existing shared answer-card renderer. The instrument covers grouping, read/decided filters, simulated actions and 72 geometry cases. No board write, installed build or native Windows/macOS qualification is proved.

## Options

1. Keep the separate Results reader. Pro: little implementation change. Con: hides the question list and retains the extra return step; it does not meet the owner's merged-destination request.
2. Read results in the selected Conversations pane with shared decision cards. Pro: preserves context and existing grouping; three comparable paths need fewer clicks. Con: needs a typed result adapter, decided-history projection and native qualification.
3. Put every item in an ungrouped decision inbox. Pro: one attention list. Con: replaces approved project/pin grouping and separates the owner conversation context; adds an unnecessary navigation concept.

## Recommendation

Option 2 was approved by the owner in [the task answer](https://github.com/taskqorg/taskq/issues/1977#issuecomment-6535685297). The implementation reuses the shared controller, native draft storage and existing immutable create claims. Preserve the original task lifecycle and finish native qualification in this same task. No separate implementation task is proposed.

Verdict: inconclusive for installed operator improvement. The approved path comparison and focused bundled-browser checks support the implementation. Native Windows/macOS comparison and installed-app acceptance remain separate, unproved observations (R12). See the [qualification ledger](../design/reports-conversations.md#checkpoint-and-remaining-evidence) for exact checks and gaps.
