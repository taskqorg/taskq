# Native Windows long-history measurements

Native WebView2 measurements for [#2023](https://github.com/taskqorg/taskq/issues/2023), continuing [#1933](1933.md). Verdict: **inconclusive for native product qualification**. The experiment measures the real workspace bundle and unchanged transcript reader in a disposable native window. Its synthetic input, fixture bridge and process restart do not qualify installed TaskQ, physical input or the complete service/session path (R12).

## Question

What are the input, selection, rendering, scrolling and resource costs of normal, exact 100 MiB and 10,000-record histories on this Windows host? Can the earliest record remain reachable without truncation, including hostile records and changed sources?

Q-A6's input p95 ≤100 ms and normal warm append/prepend task ≤50 ms remain proposed reference targets, not acceptance gates. This task changes no decision or product behavior (R13). The run fixes 40 input/selection samples, three seconds of wheel input per usable fixture, 20 repeated warm reads per baseline fixture and a 120-second traversal ceiling. Failed instrumentation attempts and missing observations remain in the [evidence packet](../design/evidence/2023/README.md).

## Findings

The tested product source is `73df356b19e841e3900c06878206bfdd73b7c41e`, TaskQ 4.6.52. Windows 26H2 build 26300.9711 runs on an i5-12600KF, 16 logical CPUs and approximately 32 GiB RAM. Other compiler processes were active; one observed CPU reading was 10%, with approximately 10.7 GiB available memory. This was a shared, loaded host, not an isolated benchmark.

The actual renderer reports Edge/WebView2 `156.0.4314.50`, V8 `15.6.12.7`, DPR `1.399999976158142`, a 672×529 CSS viewport and `visible` document state. The native client area is 940×740 physical pixels. The primary desktop is 2560×1440; WMI reports 239 Hz. Windows text scaling is 140%. The computed body font is `16px -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif`. Tao reports scale 1.0 while the renderer reports DPR 1.4; these are separate observations, not proof of per-monitor DPI calibration.

Each provider has 300 normal records; 100 one-MiB native-format records with 11 visible long messages in an **exact 104,857,600-byte** source; 10,000 variable-height visible records with ignored runs; 80 hostile visible records; and a separate >16 MiB record. Fixtures, original source hashes, commands, native-reader observations and measurement definitions are linked in the [packet](../design/evidence/2023/README.md). All sources are invented; mutations use separate copies.

Each input and selection percentile has 40 samples; each wheel interval has 518–669 rAF samples. Input timing runs from immediately before the CDP request until the next animation-frame callback after it completes, including transport/host scheduling. It measures synthetic short-draft editing and Shift+Left selection. Receive timing measures the synchronous `taskq.receive` call, not the entire main-thread task or physical paint. Wheel events are CDP input into the native WebView2 target; traversal additionally uses programmatic edge scrolling. These are distinct measurements.

All input/selection p95 values fall below the proposed 100 ms reference, but maxima include 352.7 ms for Claude 10,000 input, 362.0 ms for Codex 10,000 selection, and **4065.9 ms for Codex hostile input**. The run does not attribute those end-to-end spikes to a renderer task. Long-task observations include 341 ms and 287 ms maxima in the two 100 MiB cases; a zero observer count elsewhere is not proof that all tasks meet 50 ms. Wheel rAF intervals exceed the approximately 4.18 ms reference implied by WMI's rounded 239 Hz reading; compositor presentation times were not measured. No hard-coded 16.7 ms budget was used.

Both providers reach every expected visible record and the earliest `0:0` record: 300 normal, 11 long messages in each 100 MiB source, 10,000 variable-height records and 80 hostile records. The original source bytes remain authoritative; the reader refuses each oversized record with `transcript record exceeds 16 MiB; view unknown`. Unknown/ignored records and incomplete final records do not become fabricated messages. The 100 MiB and 10,000 fixtures exercise the existing explicit Load earlier action across long ignored runs.

The sampled mounted maximum is 600 transcript items and 2810 total connected document elements for both 10,000-record cases. V8 used-heap samples there are 20,196,876 and 41,496,152 bytes; embedder samples in the 100 MiB cases reach 116,184,512 and 109,109,560 bytes. These are renderer-wide point samples without forced GC, not isolated transcript-cache bytes or a proven memory plateau. The source's 600-item window is not a byte-memory ceiling, and preserving selected records can retain more than that nominal window. No byte-cache budget was adopted.

The first process uses a fresh WebView2 data directory; subsequent fixture switches and restart reuse it. Fixture generation has just written the sources, so OS page-cache state is unknown even on first open. Native reader timings and logical cursor ranges are measured separately from rendering: first-open observations are 3.248–28.014 ms, and warm same-page p95 is 2.449–14.606 ms (20 reads/fixture). Physical disk I/O, read amplification and genuinely OS-cold I/O remain unknown. No shared cache was flushed.

The complete normal-history trace records 1759 native renderer RunTask samples, p95 0.281 ms and maximum 10.370 ms; no task exceeds the proposed 50 ms reference. Prepend/append phase maxima are 8.159/9.511 ms for Claude and 7.142/2.949 ms for Codex. Full task traces for long-message/100 MiB cases remain unmeasured. Concurrent input/wheel p95 is 11.3/12.9 ms for Claude input/selection and 22.8/53.2 ms for Codex, with a 4495.6 ms Codex selection maximum that is not attributed to a renderer task.

Native font changes at the earliest record move the sampled anchor by at most 0.000016 CSS px. Both providers show a prepend shift of 0.234375 CSS px and no append shift, including delayed observations; these fit Q-A3's 2 CSS px tolerance. Copied-source shrink, same-prefix replacement and disappearance produce explicit unknown/source-changed states. The final instrument restart restores `49974:0` with zero CSS-pixel shift. All ten original source hashes survive unchanged. Hostile literals, long unbroken text, mixed Unicode, malformed/ignored records and an incomplete trailing record were exercised; the hostile script flag remained false. This does not qualify the complete accessibility, resize, font or physical-device matrix.

The packet records instrument failures before their corrected checks and all nine process exits as 0. First-pass binary and runtime driver hashes were not captured before instrumentation edits; source, bundle and fixture identities are pinned, and the final instrument binary is hashed. This provenance gap independently prevents exact-artifact qualification (R12). No product fix or before/after optimization is claimed.

## Options

1. Accept this baseline as an inconclusive qualification report. Plus: preserves attributable native measurements and source-integrity evidence now. Minus: leaves physical input/paint, OS-cold I/O, byte-cache limits and installed restart unqualified.
2. Provision an isolated native acceptance window and adopt explicit resource budgets before qualification. Plus: permits physical input, presentation, cold-storage and complete recovery measurements against a decided budget. Minus: requires owner-controlled host time and additional qualification work.

## Verdict

**Inconclusive.** Native measurements replace #1933's adapter-only performance inference for the bounded instrument, but do not establish smooth physical interaction, a byte-memory plateau or complete installed-product acceptance. The evidence reports observations and limits under R12; no Q-A6 budget, runtime policy, permission or source-retention rule changed (R13).

## Recommendation

Accept the native baseline as inconclusive; keep cold I/O, byte-cache bounds and installed restart open before qualification.
