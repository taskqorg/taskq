# One-command README screenshot refresh (#1919)

## Question

How can one command refresh every README interface image and its manifest for a chosen TaskQ version, quickly, with verified provenance, staged replacement and a reviewable preview, reusing the existing capture scripts and renderer?

## Revision baseline

- Planned against `origin/main` `516af799` (release 4.6.47). Its README shows one interface image, `popover-dark-project-16.png`; `update.sh` captures routes `project,icon`.
- The owner's checkout holds an uncommitted README simplification on `da4ef2b6`: README SHA-256 `1f6a9b14…7070`, Conversations request and question routes in `update.sh`, a `captureInputs` manifest block, storefront fixture edits and evidence in `docs/shots/evidence/readme-2026-10-30/`. That change is source-backed capture evidence on a local 4.6.39 build, not a published release or end-to-end run. This plan assumes it lands first and names its three images: request (`popover-dark-conversations-owner-18.png`), queue (`popover-dark-project-16.png`) and question (`popover-dark-conversations-question-18.png`).
- Session context: [readme-plan.md](../design/readme-plan.md) and the evidence README above. Nothing in either checkout was changed by this task; the measurement captures were reverted.

## Findings

### Measured costs (A1, A3)

| Measurement | Where | Result |
|---|---|---|
| `cargo build --release --locked`, cold target | Mac arm64, this worktree | 339 s |
| `docs/shots/update.sh`, warm target (no-op build, sign, capture, manifest) | same | 18 s |
| Same, repeated | same | 5 s; both PNGs byte-identical to the first run |
| CI "Capture README shots" step (cold build + capture) | `macos-latest`, runs 38717829672 and 39603193860 | 170 s and 194 s; whole job 3–3.5 min |
| `docs/shots/check.sh` | local and CI | ~1 s |

Capture itself is seconds; the release build dominates. Captures are deterministic on one host, so byte equality is a usable reuse check.

### Stale-input risks and gaps in the current release path (A1)

1. **The release-tag trigger is dead.** `release.yml` tags with `GITHUB_TOKEN` (its own header: "a GITHUB_TOKEN tag starts no run"), so the `push: tags` trigger in `shots.yml` never fires. The last tag run was v4.4.3 (2026-10-15). Tags v4.4.4–v4.6.47 had no shots run; the last of all 30 runs was a dispatch on 2026-10-21.
2. **The manifest version is not verified.** Release PRs bump only `"version"` in `docs/shots/manifest.json` (4.6.46 → 4.6.47 in `516af799`); its images still come from `c5691416`, captured on Windows. Nothing compares the manifest version, `sourceCommit` and binary.
3. **Main images are stale now.** `check.sh` on `516af799` exits 2: 13 UI sources changed since `sourceCommit`. CI only warns (`tests.yml` shots job), so staleness accumulates silently.
4. **A tag run captures `main`, not the tag** (`ref: … 'main'`). A tag for an older commit gets images of a newer commit labelled as the tag.
5. **Staleness covers UI blobs only.** Fixture, conversation fixture, `update.sh`, `Cargo.lock` (build inputs such as CoreQ and web bundling), renderer environment and image bytes are not checked. The uncommitted `captureInputs` block records three inputs, but `check.sh` does not read it.
6. **Replacement is not staged.** `update.sh` runs `rm -f docs/shots/*.png`, then copies and writes `manifest.json` in place. A failed `cp` or an interrupted manifest write leaves a partial set; `check.sh` does not detect image/hash mismatch.
7. **Provenance is weak.** `binarySha256` hashes a locally signed (`scripts/macos-runner.sh`) build, which no one can reproduce or compare with a release asset. Its `environment` omits display scale; CI is 1x, the owner's Mac 2x, and the workflow keeps fresh 2x shots only by skipping the commit when `check.sh` passes.
8. **Publication bypasses current rules.** The bot commit waits with `gh run watch` (taskq.md § 7 rule 7 forbids it) and fast-forwards `main` directly, outside the merge queue that R12 makes the merge gate.
9. **No preview or visual review step.** README rendering at desktop and narrow widths was a manual session step (evidence README); hashes alone are accepted by CI.
10. **Windows capture is unqualified** (readme-plan.md), yet the committed manifest is a Windows capture.

## Options

### A. Extend `update.sh` with a target and staging (recommended)

`docs/shots/update.sh [REF] [--bin PATH] [--publish]`, details below.
- + One pipeline, existing renderer and fixtures; local and CI use the same command.
- + Warm Mac refresh in under a minute; a release artifact removes the 339 s build.
- − Staging, verification and preview roughly double the script (about 80 more shell lines plus a small preview script).

### B. Keep `update.sh`; fix only the workflow trigger and checks

- + Smallest diff: dispatch `shots.yml` from `release.yml`, compare manifest version, verify image hashes.
- − No staged replacement, no exact-target capture, no preview; A2, A5 and A6 stay manual.

### C. Capture inside `release.yml` from the built artifact

- + Exact released binary by construction.
- − Second capture pipeline (refused by scope); release jobs gain a native GUI dependency and a write to `main`.

## Recommendation

Option A.

### Command (A2)

```sh
docs/shots/update.sh [REF] [--bin PATH] [--publish]
```

- `REF` (default `HEAD`): a commit, branch or tag such as `v4.6.48`. The script resolves it to a full SHA and works in a detached temporary `git worktree` at that SHA, so the caller's dirty checkout and unrelated edits are never read or touched.
- Without `--bin`: one `cargo build --release --locked` there, sharing `CARGO_TARGET_DIR`, then one binary for all routes.
- `--bin PATH`: a verified release artifact instead of a build. Accept it only if its SHA-256 matches the release `SHA256SUMS`, `gh attestation verify` passes and `PATH --version` equals the `Cargo.toml` version at `REF`.
- Routes come from one list in the script, derived from README image links: `project,icon` and `conversations`. No manual image selection; the manifest is generated.
- Without `--publish` it only writes the staging directory and preview, and prints their paths. `--publish` replaces `docs/shots/` in the caller's checkout after every check passes. It never commits or pushes.
- Prerequisites: macOS with the WKWebView renderer (arm64 qualified; x86_64 untested), Rust toolchain unless `--bin`, `npm ci`, `gh` only for `--bin` verification. Windows and Linux: unsupported; refuse with one error.

### Fast path and reuse (A3)

- Reuse key: SHA-256 over version, UI source blob IDs, `captureInputs` (fixture, conversation fixture, `update.sh`, `Cargo.lock`), binary SHA-256 and environment (OS, arch, renderer, display scale).
- If the committed manifest carries the same key and every image hash matches, print `fresh <key>` and exit 0 without capture. Any difference captures everything; no per-image reuse.
- Targets from the measurements: warm Mac ≤ 30 s capture-to-staging; full run with preview ≤ 60 s; `--bin` from cold ≤ 90 s; CI job ≤ 5 min. Re-measure after implementation and record actuals in the manifest evidence.

### Preserved properties (A4)

Real `taskq tray --snapshot` in WKWebView; isolated `TASKQ_INSTALL` from `fixture.sh` and `tests/fixtures/conversation-shots.js`; invented storefront data; unknown values stay as the renderer shows them; a manifest recording all of the key inputs plus `ref`, `sourceCommit` and binary origin (`build` or `release v<ver>`). The script sets no board token, runs no service command, starts no agent and writes nothing outside the temporary directory until `--publish`. Add a guard: unset `GH_TOKEN`, `GITHUB_TOKEN` and `TASKQ_ROOT` for the capture step.

### Staged replacement (A5)

1. Capture into `$tmp/stage/`; write the manifest there.
2. Verify in staging: every README image link and the summary icon exists and is a non-empty PNG; hashes match the staged manifest; manifest version equals `Cargo.toml` at `REF` and the binary version; `check.sh` passes against the staged manifest.
3. Copy the stage to `docs/shots/.next/`, then rename images and finally `manifest.json` into place; delete only images the new manifest drops.
4. `check.sh` gains image-hash verification, so an interrupted rename is detected as exit 1, and `git checkout -- docs/shots` restores the last committed set.

Any failure before step 3 leaves `docs/shots/` untouched and prints one line: `update.sh: <stage>: <problem>; previous set kept`, with the capture log path.

### Preview and visual review (A6)

- Write `$tmp/preview/README.html` with the staged images, rendered offline by a pinned Markdown renderer added as a dev dependency. GitHub's Markdown API is a network call and is not needed.
- Screenshot it at 1280 px and 390 px with the existing local Playwright instrument (`PLAYWRIGHT_CHANNEL=chrome`). Check that every image loads, there is no horizontal page overflow, and the question image shows both choices, the answer input, Send and helper text. Retain page PNGs and a `page-checks.json`.
- These checks are instruments (R12). A person or reviewer still opens the three images and both page widths; the hash check never replaces that review.
- With `--publish`, copy the preview evidence to `docs/shots/evidence/<version>/`.

### Release workflow (A7)

- `shots.yml`: `workflow_dispatch` input `ref` (default `main`). `release.yml` dispatches it with the new tag; `GITHUB_TOKEN` may start `workflow_dispatch` runs.
- The job runs `docs/shots/update.sh "$ref" --bin <release asset> --publish`, asserting the manifest `version`, `ref` and binary version all equal the tag.
- If `fresh`, the run ends. Otherwise it pushes branch `taskq-shots-<version>` and opens a draft PR with the preview evidence linked. Merge follows the merge queue and existing approval rules; no direct `main` push, no `gh run watch`.
- Staleness detection: `tests.yml` keeps the warning; after the change it also flags a manifest whose version differs from `Cargo.toml` on a release commit.
- Release PRs stop hand-editing the manifest `version` line.

### Smallest implementation scope (A8)

- `docs/shots/update.sh`: `REF`, `--bin`, `--publish`, reuse key, staging and single-line errors.
- `docs/shots/check.sh` and `check.test.sh`: verify image hashes, `captureInputs` and version match; add cases for partial replacement and version mismatch.
- `scripts/readme-preview.cjs` (new, small): offline render plus two-width page checks.
- `.github/workflows/shots.yml` and one dispatch step in `release.yml`.
- `docs/testing.md` and `readme-plan.md`: document the command; edit taskq.md only if a decision below changes a rule.

Supported: macOS arm64 build path (measured). Untested: `--bin` with the release `macos-aarch64` asset (signing and WKWebView under an unbundled binary), macOS x86_64, CI preview timing. Unsupported: Windows, Linux.

## Owner decisions before implementation

1. **Canonical renderer scale.** Mac 2x (owner Mac or a PM run) or CI 1x on `macos-latest`. Recommended: CI 1x with `--bin`, accepting lower pixel density for exact-release provenance; Mac 2x stays possible by dispatch.
2. **Publication route.** Draft PR through the merge queue (recommended) or keep the direct `main` push.
3. **Preview dependency.** Add a pinned offline Markdown renderer (recommended) or use GitHub's Markdown API.
4. **Windows capture.** Keep unsupported (recommended) or qualify it as a second renderer.

No other task waits on these decisions, so this report is handed in without an `ask` (§ 7).
