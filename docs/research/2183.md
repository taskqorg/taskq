### Native cleanup: before and after observations

The recovered #2120 native receipt fails after 36.20 s: two endpoint checks pass, but profile removal returns `EPERM` and the lifecycle test fails. It used the original WSL checkout, not the final registered NTFS root. The exact historical lock cause is unknown; this attempt does not claim a new cleanup code fix or a controlled causal reproduction of that failure.

The first fresh actual-root invocation of configured Windows Node, `--test v1/tools/chrome.test.mjs`, fails before launching Chrome: its Windows Python inventory child reads a UTF-8 pin using CP1252 and raises `UnicodeDecodeError`. The receipt preserves that failure. The scoped correction is a child environment setting, without editing source or global Python configuration:

```sh
PYTHONUTF8=1 WSLENV=PYTHONUTF8/w <resolved-Windows-Node> --test v1/tools/chrome.test.mjs
```

The Node placeholder is resolved from shared `host-tools.json` and converted with `wslpath -u`, as the host contract requires. The first corrected run passes all three tests in 6.12 s wall time, with no skips. A final run adds before/after process inventory evidence and passes all three again in 6.35 s test time, with no skips or stderr. The instrument checks native CDP, low process priority, muted headless flags, bounded endpoint refusal, exact-profile shutdown/removal and a prefix-sharing sibling that remains responsive after owned cleanup.

Before/after Windows process inventories contain zero unrelated Chrome processes; none were available to demonstrate survival. Sibling preservation is directly exercised. Inspection confirms the cleanup sweep filters `chrome.exe` and the complete profile argument; no unrelated process was selected or terminated. This is bounded current cleanup evidence, not proof that the historical intermittent `EPERM` can never recur (A3; R12).
