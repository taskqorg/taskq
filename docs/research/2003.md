# Disposable macOS context: owner preparation

## Question

Prepare a separate owner-run context for future native UI30 qualification without changing production services, credentials, grants, saved views or task answers. This is a preparation plan, not a running context or native acceptance evidence (R3, R9, R12, §6).

The owner selected **Prepare future context** in [#2003 answer 6546603923](https://github.com/taskqorg/taskq/issues/2003#issuecomment-6546603923). ## Findings

- [The prior attempt](../design/evidence/1932/isolated/README.md) reached a native tray using its own TMPDIR and pinned `current`. Its [service command refused](../design/evidence/1932/isolated/service-refusal.txt): `a worker cannot run the host service`. This is the intended authority boundary, not a defect to remove. There is no pass-after observation yet.
- The [pinned command implementation](https://github.com/taskqorg/taskq/blob/98478c711b525d436ada9107161b6d21cce409f0/src/main.rs) refuses worker service execution and permission writes. [Runtime homes](https://github.com/taskqorg/taskq/blob/98478c711b525d436ada9107161b6d21cce409f0/src/runtime/accounts.rs) support separate Claude/Codex state, but separate directories alone do not establish login-Keychain isolation.
- The [owner adapter](https://github.com/taskqorg/taskq/blob/98478c711b525d436ada9107161b6d21cce409f0/src/runtime/owner.rs) maps visible Codex setup sessions to Codex App. The [access resolver](https://github.com/taskqorg/taskq/blob/98478c711b525d436ada9107161b6d21cce409f0/src/policy.rs) refuses Workspace enforcement for `codex-app`; it needs an explicit Full grant. The [request writer](https://github.com/taskqorg/taskq/blob/98478c711b525d436ada9107161b6d21cce409f0/src/setup.rs) accepts Codex setup requests on macOS, but refuses Codex project owner requests. A logged-in Codex CLI or ready setup session therefore cannot prove a working Codex project PM flow. Preparation does not change this behavior.
- [Native service ownership](../design/host-service.md#contract-detail) uses a per-user launchd unit named `com.taskq.service`. Installing another unit under the production macOS user could affect that user's service. A fresh standard macOS user separates the login Keychain, native unit domain, runtime homes and application preferences. It is not a VM or proof of every filesystem/network boundary.
- Read-only GitHub discovery identified account `alexkirs`; the source repository `taskqorg/taskq` is PUBLIC. `alexkirs/taskq-ui30-disposable-2003` returned HTTP 404 to the current credential. Its existence and visibility are unknown; the owner must establish availability before creation. No repository was created or adopted.
- [Release v4.6.56](https://github.com/taskqorg/taskq/releases/tag/v4.6.56) advertises the macOS artifact `taskq-4.6.56-macos-aarch64`, SHA-256 `b07f2d5cdeb24e51925128b891115f485a0db2be6d03591b5a9a24a81a0e9047`. This metadata read does not verify a downloaded file, provenance or installation. The intended source is `98478c711b525d436ada9107161b6d21cce409f0`; verify the tag resolves there before staging.

## Options

1. **Fresh macOS user, private board (recommended).** Separates login Keychain, runtime state and per-user native service. Costs an owner login and explicit setup; real remote transport still needs another disposable host.
2. **Fresh directories under the production user.** Fewer setup steps. Separate runtime homes/TMPDIR do not prove Keychain isolation, and native-unit installation could replace that user's service. Do not apply this alternative under the proposed effects.

## Verdict

**Inconclusive:** source and prior native evidence establish why worker-run service startup cannot satisfy A1. No owner-provisioned service, provider readiness or operator grant has been observed for this context. Owner setup plus the readiness readback are required; documentation and green source CI cannot replace them (R12). The current adapter also lacks a supported Codex project-PM path; a ready Codex setup session does not resolve it.

The owner should review the exact effects, provision the fresh-user/private-board context, and return the readiness packet. Keep #2003 incomplete until A1–A4 are observed. If an effect or target changes, revise that part of the plan before applying it. No rule, runtime behavior or production policy change is proposed (R13).
