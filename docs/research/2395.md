# Immutable batch replay pilot

## Question

Can three to five independent accepted TaskQ deltas be replayed in private Git,
with immutable evidence and failure localization, before considering production
batching? Source request and acceptance: [#2395](https://github.com/taskqorg/taskq/issues/2395).

## Plan and rollback (written before implementation)

R8/R12/R13: this is an explicitly isolated, offline experiment. It changes no
production admission, publication, release, runtime policy, queue capacity or
installed runtime. Feature PR checks and merge-result gates remain required.
The pilot consumes #2391's authoritative accepted-result projection; it never
parses lifecycle comments or treats the latest matching comment as acceptance.
Missing source proof refuses qualification and is recorded as unknown.

1. Freeze inputs by digest: producer revision/export, accepted attempt/result,
   repository/PR, result SHA, original PR base (observed or null), original merge
   parent, merged delta, exact CI run/attempt/SHA, and current reviewed source.
   Preserve historical unknowns; experimental base/head are distinct fields.
   Accepted-result identity is required independently of advisory source-ready.
   Prove integration coverage by applying the exact result delta from its frozen
   Git ancestor to the original merge-parent tree in private Git; require the
   observed merged tree exactly. A derived Git ancestor never proves a historical
   PR base. Conflicts or extra changes refuse rather than borrowing source-ready.
2. In a new private temporary Git repository without remotes, import only the
   frozen source. Reverse the three verified merge deltas, then replay those
   exact binary patches in all six orders. Reject dependencies, moved inputs,
   overlapping/conflicting changes, mismatched result deltas or extra changes.
   Every order must reproduce the frozen source tree exactly.
3. Run the complete unchanged canonical gate (`python3 scripts/check.py --full`)
   on the frozen replay head with existing early pinned lint. One initial gate,
   900-second canonical budget, no retry-to-green. Keep the host, tools, command,
   head, elapsed time, exit status and log digest in content-addressed receipts.
4. If the original gate fails, check deterministic subsets, using an exact-input
   cache (limited to one process since `0441ad23`, see
   [Local gate re-execution](#local-gate-re-execution)). Report minimal failing sets, interactions and unknowns; never remove
   members or upgrade the original outcome using diagnostics. Synthetic fixtures
   exercise refusal and diagnostic behavior separately from real evidence.
   A subset with changed check definitions is non-comparable: keep its observed
   outcome but report causal clearance as unknown. Conservatively fingerprint
   source files too, because Rust embeds regression checks beside implementation.
   Never overlay production checks or remove members to obtain a passing batch.
   Replay inputs are frozen from the reviewed source, including later reviewed
   hunks. A whole-file historical blob mismatch alone does not mean those frozen
   inputs moved. Exact Git reversal must match the verified delta's postimage
   context; freeze its resulting before/after blobs, then enforce those identities
   in every replay order. Conflicting hunks still refuse, and all orders must
   reproduce the entire reviewed tree, preserving unrelated later changes.
5. The full-matrix handoff retains the reviewed source commit as an explicit
   bundle prerequisite. Prepare the private replay head and a sanitized manifest
   as a Git bundle; preparation remains pending, never PASS. The operator verifies
   exact tree identity, publishes a unique non-release proof ref and returns the
   unchanged `tests.yml` full OS matrix's exact run, attempt, SHA and jobs. The
   pilot itself never publishes. Once that proof is verified, do not duplicate
   the local replay Windows gate; the feature-candidate checks remain required.

Rollback: stop only the pilot's own command, preserve its immutable receipts and
logs, and discard its private temporary repository. There is no production
rollback, queue write, service restart, release or installation to undo. Existing
different receipt bytes refuse overwrite. Receipts are local evidence digests,
never TaskQ events or acceptance authority. No credentials or private host paths
belong in committed evidence.

### Tool and synthetic protection

`scripts/batch-replay.py` reads a frozen manifest, imports only frozen tree
objects into private Git with no remotes, proves source coverage, reverses verified
deltas and applies all permutations. Its gate is the unchanged
`python3 scripts/check.py --full`; its experimental base commit is the gate
head's parent. It records inputs, patches, tool identity, host, command, frozen
head/tree, outcome, timing and log digests. A stored local command receipt never
qualifies a new execution (see [below](#local-gate-re-execution)); earlier receipts
of the same identity are verified against their content and log hashes and linked
as evidence. A corrupt existing
receipt is never overwritten. Failed original batches retain every member and
their failed outcome while deterministic subsets, including the empty baseline,
identify failures, interactions and unknowns.

Run the focused synthetic suite with `python3 scripts/batch-replay.test.py`.
It is also wired into `scripts/check.py`, after the existing early pinned lint.
Synthetic gate callbacks are explicitly labelled and cannot qualify real tasks.
The suite covers three-to-five-member validation, six actual Git replay orders,
missing and stale source proof, moved heads/inputs, tampering, dependency refusal,
overlaps, patch conflicts, hidden changes, exact CI identity, historical unknowns,
failed and interacting gates, receipt replay, external-input mutation through the
default runner, one execution per exact input in one process and corrupt logs.
The disappearing-check fixture also requires a subset's observed PASS to read
unknown when removing a member removes its regression assertion. Check-input
fingerprints include Rust sources conservatively; a changed fingerprint cannot
prove causal clearance. Gate receipts bind the actual check-input identity, frozen
source, pilot tool digest, tool versions and environment digest. That identity
groups executions for comparison; it does not prove what a local gate read.

Retained **synthetic** execution evidence uses actual Python subprocess checks,
not a real-task failure or a production observation:

- [Interacting failure](https://github.com/taskqorg/taskq/blob/96064118e637ea8d7347edc4ca50c5c5da186757/docs/research/2395/interacting-failure.json): all three members remain
  in the failed original; eight deterministic checks including the empty baseline
  establish the comparable minimal failure `[1, 2]`.
- [Disappearing assertion](https://github.com/taskqorg/taskq/blob/96064118e637ea8d7347edc4ca50c5c5da186757/docs/research/2395/disappearing-check.json): removing member 3 removes
  its executable assertion. The `[1, 2]` command exits successfully, but its
  changed check identity makes the result unknown; the original remains failed.
  Before the fix, localization incorrectly called `[3]` minimal despite the
  unknown empty baseline. Afterward, it reports no proven minimum, unresolved
  `[3]`, and unknown interaction. The focused reproduction fails before/pass after;
  it keeps the same failed original and no production test overlay (A7/R12).
- [Exact-input cache](https://github.com/taskqorg/taskq/blob/96064118e637ea8d7347edc4ca50c5c5da186757/docs/research/2395/cache-evidence.json), historical and superseded: under
  tool `5d12937c`, repeating identical input reused the same immutable command
  receipt with no second callback execution. Changing check inputs did not clear a
  member; corrupting the cached log refused reuse. The bytes stay unchanged as a
  record of that tool; the current tool no longer behaves this way.
- [No persisted reuse](https://github.com/taskqorg/taskq/blob/96064118e637ea8d7347edc4ca50c5c5da186757/docs/research/2395/no-persisted-reuse.json): the external-input mutation
  before and after, described below.

These indexes link retained immutable result, command, log and replay-order
objects under `2395/receipts/`. Synthetic callbacks are explicitly identified;
their outcomes never substitute for the real full matrix.

The canonical hook initially failed `scripts/check.test.py` at its five-call
expectation: the new hook correctly made six calls. The updated check passes
with six and explicitly requires exactly one replay-test invocation only after
successful lint. The lint-first, once-only and failure-before-tests protection is
retained (R8/R12); no contract assertion was weakened.

### Local gate re-execution

Review of `0441ad23` found a false PASS. An invented canonical stub read one file
outside every Git tree through an environment variable. Bytes `ok` passed. After
only those bytes changed to `bad`, with path, environment, source, tool and head
unchanged, the same receipt store returned the earlier PASS while a fresh store
executed and failed. The [recorded rows](https://github.com/taskqorg/taskq/blob/96064118e637ea8d7347edc4ca50c5c5da186757/docs/research/2395/no-persisted-reuse.json) show both
tools through the real default runner on one identity.

The receipt identity cannot prove the closure of files and services a local gate
reads, so v1 restricts reuse instead of freezing that environment:

- Every run executes its gate. A stored local receipt is evidence, never a result.
- Earlier receipts of one identity are verified, then linked in `prior_executions`.
  Tampering still refuses the run.
- A later PASS after an earlier FAILED or UNKNOWN of that identity reads unknown:
  re-execution cannot become retry-to-green. PASS followed by FAILED reads failed.
- A7's exact-input cache narrows to one process. Cross-run savings are unavailable
  until a closure is proven. The current original and subset inputs are all
  distinct, so this memo saves no execution in today's localization path.

Historical CI evidence is a different kind of record. The immutable receipt of run
41914656647, attempt 1, on head `cc7941f4` remains an exact observation of that
run and is neither re-executed nor reused as a local gate. It and the original 100
receipt objects stay byte-identical and name their producer, tool `5d12937c`. The
current tool is `4a7bc3b5`; it did not produce them and does not requalify them.
Its own [real preparation rerun](https://github.com/taskqorg/taskq/blob/96064118e637ea8d7347edc4ca50c5c5da186757/docs/research/2395/no-persisted-reuse.json) reproduced the same
input, frozen source, base, head `cc7941f4` and tree in all six orders. That rerun
stays pending: it ran no gate and qualifies nothing.

The independent synthetic reproduction attached to the task agrees. Against `0441ad23`
it exits 1, because the cached PASS survives the changed bytes. Against the current
tool it exits 0: the same store and a fresh store both execute and fail. That script
takes its fixture builder from the `0441ad23` test module, so the current tool ran
beside that module, not beside the rewritten suite.

### Canonical test cost

The hook stays unconditional and every test still runs in the full gate. The
reviewer's report of about 100 seconds is theirs, not a benchmark taken here. The
independent audit located the cost: one fixture ran three times, each repeating
verification, preparation and six Git orders, and every test rebuilt five commits.

The suite now builds one immutable source and one prepared replay per class.
Each test writes only byte copies, never hardlinks, and the class fails if the shared
source moved. Exactly two tests replay real permutations: the end-to-end test and
the later-hunk test. Cache, tamper and gate tests run at the prepared boundary.
Production verification keeps its original check order: no cost was saved by moving
a check, and no stored receipt can stand in for input, source, coverage or receipt
validation. Inside that order, the coverage proof reads frozen objects in place, and
one tree listing serves every replay order. Production still replays every
permutation, and no negative case was removed.

Private invocation, after the authoritative producer export exists:

```sh
python3 scripts/batch-replay.py manifest.json --source /exact/source/repo --receipts /private/pilot/receipts
python3 scripts/batch-replay.py manifest.json --source /exact/source/repo --receipts /private/pilot/receipts --prepare-bundle
```

The manifest format is exercised by the synthetic fixture builder in
`scripts/batch-replay.test.py`. It carries `schema: 1`, `synthetic`, repository,
immutable producer revision/executable digest and frozen source head, and three to five members.
Each member freezes the #2391 export and canonical JSON digest, expected
task/attempt/result-entry/result SHA, publication mapping, dependency issue body,
derived source-delta base, merged-delta digest and exact CI API observation.
The `accepted_result_state: proven` projection comes from the frozen #2391
producer above, not an installed-runtime claim. Original PR base, derived source-delta base,
historical merge parent and experimental replay base retain distinct meanings.

Keep raw receipts and logs private: commands can contain host paths. Publish a
sanitized summary with their digests, preserving the exact SHAs and outcomes.
The temporary repository is removed after its command finishes; receipts and
logs survive separately. A receipt digest is never a TaskQ lifecycle event.
Git attributes preserve exact evidence bytes across checkouts. The focused Git
fixture reproduces a receipt hash break with CRLF conversion, then passes after
the evidence directory disables text conversion. Content-addressed payloads are
opaque to Git diff because they include exact patch bytes; the linked receipt and
command objects retain their audit identities.

### Acceptance and limits

A1 is complete: the plan and rollback were written before code, and production
behavior is unchanged. A2 uses the three authoritative accepted identities above.
A3 preserves historical unknowns, exact source/merge delta coverage, frozen inputs
and CI identities. A4's six actual Git orders have equal complete trees and retained
execution logs. A5 links content-addressed immutable inputs, patch, tool, command,
host, time, tree and log records; different existing bytes refuse overwrite.
A6 has the exact frozen full matrix above. A7 retains failed originals and separates
comparable failures, unresolved cases and unknown check coverage; its exact-input
cache is limited to one process, and persisted local-command reuse is removed. A8
keeps synthetic fixtures distinct, including three-to-five-member validation, and
wires their checks into the canonical gate without weakening early pinned lint.

Focused checks and retained fixture evidence protect these failure paths. Feature
validation follows §7: one rebase before first push, then its canonical gate and
one PR; the task result/PR records that candidate's checks. Its owner gate and green
merge-group publication remain required. Replay CI does not qualify that feature
candidate, source-ready publication evidence, an installed runtime, cold-CI timing
or a general batching performance benefit. No production admission, publication,
release, capacity, runtime policy or credentials changed. No R-number was amended.

## Options

- Retain isolated replay as an instrument: gains repeatable audit/failure evidence;
  costs a full canonical gate and keeps all feature/publication gates.
- Propose production batching separately: may reduce repeated integration work;
  requires a new accepted design and production qualification absent from this pilot.

## Verdict

Confirmed for this isolated three-task cohort: six replay orders produced one
reviewed tree and its exact frozen head passed the full canonical OS matrix.
This does not establish general production batching safety or a performance win.

## Recommendation

Keep production batching disabled; decide further work only from the frozen pilot evidence.
