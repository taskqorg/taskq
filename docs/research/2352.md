# GitHub request burn

## Question

Which callers exhaust the shared GitHub token, and can three hosts stay below
3,000 billed GitHub requests per hour? Source baseline:
[`7edc9b21`](https://github.com/taskqorg/taskq/tree/7edc9b21cfbeb493d503babe23ffbf85d7ce2077).
[Task #2352](https://github.com/taskqorg/taskq/issues/2352) owns acceptance.

### The paired POSTs are real permission probes

`src/board/github.rs::GitHub::access` reads issues, commits and pulls, then sends
an empty JSON object to `POST /issues` and `POST /pulls`. HTTP 422 proves write
access without supplying the fields needed to create either object. These are
real HTTP requests, not a counter defect or evidence of 54 created objects.

`src/service.rs::refresh_health` invokes this through
`src/health.rs::board_items`. `health::EVERY` is 600 seconds. Nine GitHub project
services checked six times/hour produce exactly 54 requests to each POST
endpoint, plus 162 GET probes/hour. Explicit doctor requests and restarts can
add probes. Existing regression protection is
`board::tests::token_access_probes_each_permission_and_names_a_403_contents_gap`;
it checks the empty payload, 422 interpretation and the two POST destinations.
The deployed per-call HTTP status
for the task's original hour has not been recovered.

These probes are required by the existing
[health-check contract](../design/host-service.md#health-checks-2194), which
specifies ten-minute checks. There is no accounting fix to make them free.

### Callers and cadence

Focus off refuses new task admission; it does not stop board reads or heartbeats
(§4). `src/main.rs::poll_wait` uses the normal 60-second poll when any board task
is Ready, Doing or Review, even if this host has focus off. Only an idle board
uses three polls. The existing test
`service::tests::idle_passes_wait_three_polls_until_work_or_a_poke` protects this
behavior. Increasing that wait changes the decided rule, so R13 applies.

The `GET issues` operation combines several callers: the open-list changed-task
probe, `incoming::History::refresh` admission history, `reports::Cache::collect`,
and health permission reads. The first three already use task-filtered probes;
admission/report broad scans run at least every five minutes. Their varying URL
parameters and response changes require attribution; operation totals alone do
not distinguish their individual billed shares.

Heartbeat comparison already omits diagnostic observation timestamps, usage
rows, `at` and execution-progress observation time. Genuine queue, load and
execution changes can still force writes. No unconditional per-pass timestamp
defect was found. The measured PATCH total alone does not identify a changing
line or prove that every PATCH was a heartbeat.

### Reproduced heartbeat refresh defect and fix

`GitHub::edit` already patches the kept issue list with its successful heartbeat
PATCH response. However, `GitHub::open_unchanged` replaces that list on a full
refresh. GitHub's documented list lag can replace a confirmed write with an
older heartbeat. The next pass sees the older body/time and renews it again.

The fix retains one trusted, open heartbeat PATCH response per adapter and
credential generation across list refreshes. It replaces only a still-listed
trusted heartbeat with a strictly older timestamp. Equal/newer board edits win;
absent rows are not restored; explicit close/reopen invalidates the response.
It keeps the original board timestamp, so renewal and lease expiry continue.
No polling, health-check, authority or lease interval changes are needed.

The regression `lagging_lists_do_not_repeat_confirmed_heartbeats` supplies a
three-minute-lagging full list and current PATCH replies, forcing a full read
on each 60-second pass. Before: **FAIL, 58 PATCHes in the simulated hour**.
After the cache fix: the same reproduction passes the bound of at most 30,
while continuing periodic renewal. The fixture also checks equal/newer edits,
removal, generation changes and explicit close/reopen invalidation.
This is adapter evidence for the failure mode, not proof of its share in the
measured native totals or a native under-3,000/hour pass (R12).

The budget detail now matches §4: unchanged heartbeats use `ttl / 3`, with
`min(60 s, ttl / 3)` for execution rows. This corrects the detail's obsolete
universal 60-second wording; the root decision and implementation are unchanged.

## Options

1. Attribute and cut repeat callers under the existing credential. This attacks
   the request burn and keeps the current account model; it needs complete host
   counters and a matched after hour.
2. Adopt GitHub App installation authentication separately. This isolates the
   installation budget from personal-token traffic, but adds credential renewal
   and changes the §9 credential contract. It does not remove wasteful callers.

## GitHub App recommendation

Recommend option 1 first. A GitHub App installation has a separate minimum
5,000-request/hour bucket. Non-enterprise installations can scale above that
with more than 20 repositories or users, capped at 12,500; Enterprise Cloud
installations get 15,000. Three hosts sharing one installation still share its
bucket. GitHub App **user** tokens instead share the user's primary rate limit,
so switching to those would not isolate the current personal bucket.

Installation tokens expire after one hour, requiring secure app-key ownership,
renewal and adapter qualification. Budget isolation can be worthwhile later
when legitimate service traffic competes with personal clients; it is not a
substitute for the under-3,000/hour target. No account or credential was changed.

Official sources read on 2026-11-04:

- [REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#primary-rate-limit-for-github-app-installations)
- [Installation access tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)

## Verdict

Inconclusive for the native savings target. A1's full-hour before counters are
recorded, and source inspection explains the paired POST permission probes.
The reproduced heartbeat defect is fixed locally. A3 remains open until the PM
supplies the matched after counters from all three hosts on the corrected build.
No native deployment or under-3,000/hour pass is claimed.

## Recommendation

Publish the checked candidate through green merge-result CI and the normal
release path (§7, §8). The PM then collects each host's full `requests.last_hour`,
service version, `since`, observation time and heartbeat per-API request totals
after an uninterrupted hour on the corrected build. Count each host once and
exclude 304s and `GET rate_limit`; use the GitHub split for the fleet target.
Do not substitute a shorter sample, synthetic replay or counter reset for A3.
If the measured rate still exceeds the target, continue this task with the
remaining callers; do not declare the target passed from this fixture.
