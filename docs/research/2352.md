# GitHub request burn

## Question

Which callers exhaust the shared GitHub token, and can three hosts stay below
3,000 billed GitHub requests per hour? Source baseline:
[`7edc9b21`](https://github.com/taskqorg/taskq/tree/7edc9b21cfbeb493d503babe23ffbf85d7ce2077).
[Task #2352](https://github.com/taskqorg/taskq/issues/2352) owns acceptance.

### The paired POSTs are real permission probes

`src/board/github.rs::GitHub::access` reads issues, commits and pulls, then sends
an empty JSON object to `POST /issues` and `POST /pulls`. HTTP 422 proves write
access without supplying the fields needed to create either object. These are
real HTTP requests, not a counter defect or evidence of 54 created objects.

`src/service.rs::refresh_health` invokes this through
`src/health.rs::board_items`. `health::EVERY` is 600 seconds. Nine GitHub project
services checked six times/hour produce exactly 54 requests to each POST
endpoint, plus 162 GET probes/hour. Explicit doctor requests and restarts can
add probes. Existing regression protection is
`board::tests::token_access_probes_each_permission_and_names_a_403_contents_gap`;
it checks the empty payload, 422 interpretation and the two POST destinations.
The deployed per-call HTTP status
for the task's original hour has not been recovered.

These probes are required by the existing
[health-check contract](../design/host-service.md#health-checks-2194). There is
no accounting fix to make them free; this task lowers their cadence from ten
minutes to one hour (A3).

### Callers and cadence

Focus off refuses new task admission; it does not stop board reads or heartbeats
(§4). `src/main.rs::poll_wait` uses the normal 60-second poll when any board task
is Ready, Doing or Review, even if this host has focus off. Only an idle board
uses three polls. The existing test
`service::tests::idle_passes_wait_three_polls_until_work_or_a_poke` protected this
behavior. The owner's answer changed § 4 step 8: a focus-off host now waits three
polls for every board state, and the test asserts it.

The `GET issues` operation combines several callers: the open-list changed-task
probe, `incoming::History::refresh` admission history, `reports::Cache::collect`,
and health permission reads. The first three already use task-filtered probes;
admission/report broad scans run at least every five minutes. Their varying URL
parameters and response changes require attribution; operation totals alone do
not distinguish their individual billed shares.

Heartbeat comparison already omits diagnostic observation timestamps, usage
rows, `at` and execution-progress observation time. Genuine queue, load and
execution changes can still force writes. No unconditional per-pass timestamp
defect was found. The measured PATCH total alone does not identify a changing
line or prove that every PATCH was a heartbeat.

### Reproduced heartbeat refresh defect and fix

`GitHub::edit` already patches the kept issue list with its successful heartbeat
PATCH response. However, `GitHub::open_unchanged` replaces that list on a full
refresh. The [§4 list-lag case](../../taskq.md#4-service) can replace a confirmed
write with an older heartbeat. The next pass sees the older body/time and renews
it again.

The fix retains one trusted, open heartbeat PATCH response per adapter and
credential generation across list refreshes. It replaces only a still-listed
trusted heartbeat with a strictly older timestamp. Equal/newer board edits win;
absent rows are not restored; explicit close/reopen invalidates the response.
It keeps the original board timestamp, so renewal and lease expiry continue.
No polling, health-check, authority or lease interval changes are needed.

The regression `lagging_lists_do_not_repeat_confirmed_heartbeats` supplies a
three-minute-lagging full list and current PATCH replies, forcing a full read
on each 60-second pass. Before: **FAIL, 58 PATCHes in the simulated hour**.
After the cache fix: **PASS, 29 PATCHes in the simulated hour**, while continuing
periodic renewal. The fixture also checks equal/newer edits,
removal, generation changes and explicit close/reopen invalidation.
This is adapter evidence for the failure mode, not proof of its share in the
measured native totals or a native under-3,000/hour pass (R12).

The budget detail now matches §4: unchanged heartbeats use `ttl / 3`, with
`min(60 s, ttl / 3)` for execution rows. This corrects the detail's obsolete
universal 60-second wording; the root decision and implementation are unchanged.

### A3: callers, attributed

Each project has three independent `GET issues` readers. A host runs 13 project
loops on Windows and Mac and about 8 on pds18; nine are GitHub boards and four or
five are GitLab. `requests.last_hour` mixes both providers.

| Operation | Caller | Why it bills | Cut |
|---|---|---|---|
| `POST issues`, `POST pulls` | Health probes | Six runs/hour per GitHub project. Real empty writes answering 422, so the 63/hour of each is the same probe as the 54 in A2 | Health hourly |
| Other `GET`s of the probe set | Health probes | Token, members, rules, labels and repository reads six times/hour. The unfiltered `GET /issues?per_page=1` always changes | Health hourly; that read asks for `taskq` issues only |
| `GET issues` | `reports` and `incoming` full scans | Every 300 s, unfiltered, so another host's heartbeat always changes the reply: 24 billed/hour per project | `FULL_SCAN` 1800 s |
| `GET issues` | `reports` and `incoming` per-pass probes | Each pass of each project asks; a task change bills two reads per reader | Reader every 180 s; `reports` every three polls |
| `GET issues` | GitLab open list and `tasks` | GitLab had neither the kept list nor a label filter, so any heartbeat changed both replies at each pass | Same probe and kept list as GitHub; `tasks` asks for `taskq` issues only |
| `PATCH issues/N`, `PUT issues/N` | Heartbeat of each project | `PATCH` on GitHub and `PUT` on GitLab. See below | Needs an owner decision |
| `GET issues`, heartbeats | Tray | A window that is only open, even in the background, keeps every project at a 15 s pass. Mac billed about 450 `GET issues` per project/hour, 304s included, against 85 on Windows | Needs an owner decision |
| `POST graphql` | Open list | Reuse ends at 300 s, and a kept heartbeat that passes `ttl` relists it: 16 to 21/hour per project | None: it protects stale-lease detection |

The heartbeat writes were attributed from real board edits on the `taskq` board
in the last hour before about 16:50Z: Windows 86, Mac 67, pds18 38, where renewal
alone needs 20 to 30. On Mac only 12 of 66 sampled edits were pure renewals. The
others changed values that are the same for the whole host, so one change writes
every project's board:

- `queue` project rows: `ready`, `reason`, `waiting`, `tasks.<N>`, `spawn`.
- `balancing.runtimes.*`: `load`, and `code` and `reason`, where every runtime
  flips to the launch-interval gate after a spawn and back.
- `doctor` time, `has gui`, `headroom`, `requests`.

Windows also writes `execution` rows at 60 s on its working board, which is a
decided rule. pds18 is mostly renewal. Focus off does not stop any of these:
`poll_wait` keeps 60 s while any board task is Ready, Doing or Review, whichever
host holds it.

### A3: cuts made and the decision they need

This PR ships the cuts that change no decided rule (table above). In
`heartbeats_do_not_bill_the_open_list_each_pass`, ten passes with another host's
heartbeat read the GitLab list once, not eleven times; in
`reader_scans_on_its_own_cadence_unless_a_source_is_unresolved`, 60 passes ask
for one admission scan, not 60. Costs accepted:

- A token that loses access shows in `taskq doctor --hosts` up to an hour later,
  not ten minutes. An explicit `taskq doctor` still checks at once.
- A heartbeat read on GitLab may be up to 5 min old, as on GitHub, and `views`
  relists one that turns stale.
- A held draft or other non-task issue reaches admission history up to 30 min
  later, so the newest closed New bin can read as outside verified coverage for
  up to 30 min instead of 5.

Estimate, not a measurement and not a pass (R12): these cuts leave the fleet at
about 3,700 to 3,800 billed/hour. Heartbeat writes and the Mac pass rate remain.
Getting under 3,000 needed changes to § 4 steps 3 and 8 and to menu M8. The owner
approved them (answer 1, comment 6637575503), and this PR applies all four:

1. A value that is the same for the whole host stops forcing a heartbeat write;
   it travels with the next renewal. An attempt, session, execution, version,
   service, focus, limit, login, machine or policy change still writes at once.
   `host_wide_values_wait_for_the_renewal`: 60 writes in 60 passes before, 20 after.
2. A focus-off host with no child waits three polls unless poked or after a
   failed pass. `idle_passes_wait_three_polls_until_work_or_a_poke`: 60 s before,
   180 s after, with a Ready, Doing or Review task on the board.
3. The tray keeps the 15 s pass only while a window is visible and focused. No
   test drives a native window, so this path has no native proof.
4. A host with no attempt on a board renews it every `ttl / 2`.
   `idle_heartbeat_is_batched_at_half_ttl_and_stays_fresh` asserts the renewal and
   that the lease stays fresh.

Costs accepted by the owner, and one that follows from them:

- Hosts see a host-wide value one renewal late: runtime load, headroom, `requests`,
  queue depth, doctor time.
- A background window keeps the normal pass, so it can show `Data from HH:MM`.
- A focus-off host sees board changes up to three polls later, including an answer
  or a pending publication reconcile that arrives without a poke.

With all four the estimate is about 2,650 to 2,800 billed/hour. This is still an
estimate. Only the next three-host hour measured by the PM can show a pass.

### Rule gate fix

The rule gate ignored every entry after a worker `gone`, so it refused the owner's
answer on this task's replacement attempt, as #2232 did for a `later` park. This
PR models that one transition (§ 2 row 10) in `scripts/check.py`. No existing
assertion changed. New tests keep an unanswered ask, an attempt-bound answer, a
mismatched revision, the dead attempt's late ask, a second `gone` and a reviewer
`gone` from granting anything. A reviewer should read this change as a widening
of what the gate accepts, made in the PR that needed it.

## Options

1. Attribute and cut repeat callers under the existing credential. This attacks
   the request burn and keeps the current account model; it needs complete host
   counters and a matched after hour.
2. Adopt GitHub App installation authentication separately. This isolates the
   installation budget from personal-token traffic, but adds credential renewal
   and changes the §9 credential contract. It does not remove wasteful callers.

## GitHub App recommendation

Recommend option 1 first. A GitHub App installation has a separate minimum
5,000-request/hour bucket. Non-enterprise installations can scale above that
with more than 20 repositories or users, capped at 12,500; Enterprise Cloud
installations get 15,000. Three hosts sharing one installation still share its
bucket. GitHub App **user** tokens instead share the user's primary rate limit,
so switching to those would not isolate the current personal bucket.

Installation tokens expire after one hour, requiring secure app-key ownership,
renewal and adapter qualification. Budget isolation can be worthwhile later
when legitimate service traffic competes with personal clients; it is not a
substitute for the under-3,000/hour target. No account or credential was changed.

Official sources read on 2026-11-04:

- [REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#primary-rate-limit-for-github-app-installations)
- [Installation access tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)
