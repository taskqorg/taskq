# GitHub quota shared by four hosts (#1985)

Sources: `gh api rate_limit` sampled every 5 min from the win host, `taskq status` (`Hosts:` and `Board quota:` lines), the heartbeat issues (`requests <n>/h`), the win service log (`requests 1h:` lines) and `taskq profile board --since 1h` on win. Hosts ran taskq 4.6.56 (pds18, win) and 4.6.57-dev (Mac); all include #2005/#2006. All times are UTC on 2026-10-31.

## Question

One GitHub user serves the Mac, win, WSL and pds18 hosts, and the shared core quota of 5000 requests/h ran out. Do per-process caches (`GET /user`, ETags), per-issue comment and event reads and uncounted agent `gh` polls cause it? Do fixes for them keep the sum under 3500/h?

At 15:45 the win service made 726 requests, 115 of them 304 (unbilled), so 611 billed. Of those, `GET issues` (list probes and scans) is 399 (65 %), heartbeat `PATCH issues/N` 142 (23 %) and the GraphQL open list 70 (11 %). `taskq profile board --since 1h` on win agrees: list 495, write 147, inbox 84, read 67, claim 1, comment 1.

Uncounted gap: GitHub use minus the GitHub share of the services. The services' GitHub share is 1184/h (win + pds18) plus the unknown GitHub part of Mac's 3901. In the 16:15 hour that rest is about 3050 − (712 + 874) ≈ 1460/h; in the 17:15 hour 3429 − (856 + 1252) ≈ 1320/h. The rest is Mac's GitHub share plus agent `gh`, PM and DashQ. If the Mac service costs on GitHub what win does (700-850/h), the uncounted part is about 500-700/h. It cannot be split exactly: the Mac count mixes GitHub and GitLab, and CLI processes no longer leave per-source lines in the win log (the last `taskq-requests` line is from 2026-10-14).

### A2. Repeated reads

- `GET /user`: per process before #1990; now read from `<install>/board-user-<key>`. Win: 2 in the 13:45 hour, 0 later. Fixed.
- Issue comment and event reads: before #2005 the 12:22 hour billed 110 comment reads; after it, 57-63 per hour answer 304 inside the service. A CLI, worker or restarted service still started with an empty ETag map and paid in full. This PR keeps the `ETag` and body of `GET issues/N`, `GET issues/N/comments` and `GET issues/N/events` in `<install>/board-cache-<key>/`, so every process of the install gets the 304 (test `issue_reads_carry_across_processes_and_304_is_unbilled`; it fails with the shared list empty).
- The admission scan listed from the last scan time minus 30 s, so its URL changed every pass and never answered 304. It now lists from the newest issue update it has seen, so an unchanged board repeats one URL.
- Remaining cost: the open-issue probe `GET issues?since=<newest known>` stays billed. The probe patches host heartbeats into the kept list but does not move `since` past them (`src/board/github.rs`, `open_unchanged`), and three hosts write heartbeats on each board about once a minute in sum. The probe body changes on nearly every pass, so it never answers 304 (0 `GET issues 304` in the complete 14:45 and 15:45 win hours). It costs 7 boards × 60 passes ≈ 400/h per host.

### A3. Pacing

Merged in #1990: while `remaining` is at most 20 % of `limit`, each request waits (reset − now) / remaining, at most 5 s. No pause file or `board budget low` line appeared in the window.

### A4. Visibility

Merged in #2005/#2006: heartbeat `requests <n>/h`, `Hosts:` shows `<n> req/h` per host, `Board quota:` line in `taskq status`. Brief CI waits stay `gh pr checks --watch --interval 60` (§ 7 rule 7).

### A5. Two-hour window

Window 16:15-18:15 at normal load: pds18 and win on 4.6.56, Mac on 4.6.57-dev (restarted on a newer dev build at about 17:49). The per-host counts grew during the window (pds18 573 → 874 → 1252 req/h, win 611 → 712 → 856).

- 16:15-17:15: about 3050/h.
- 17:15-18:15: 3429/h.
- No board pause: no `requests-paused-*` file, no `paused` or `board budget low` line in the win service and project logs after 15:50.

Both hours are under 3500, the second by 2 %. The margin shrinks as load grows: list probes scale with boards × hosts × passes, not with work done. This PR's cross-process cache was not deployed during the window, so the window measures #1990, #1997, #2001, #2005 and #2006.

## Options

| Option | Pros | Cons |
|---|---|---|
| A. Keep current fixes (#1990, #2005, #2006, this PR) | done; GET user and per-issue reads are cheap now | the list probe stays billed, about 400/h per host |
| B. Move `since` past patched heartbeats | small change in `open_unchanged` | heartbeats every minute still change the body on most passes; small gain |
| C. Probe only task issues (`labels=taskq`), read host heartbeats on the 5-min relist | probe answers 304 while no task changes; saves most of the 400/h per host | other hosts' heartbeats age up to 5 min in the kept list; lease freshness (§ 3) must allow it; spec change first |
| D. Count requests per API host in the heartbeat | Mac's GitHub share becomes visible; the gap becomes exact | format change (§ 4 heartbeat lines) |

## Verdict

Confirmed for the parts named, but they are no longer the main driver; A5 is met, narrowly.

- `GET /user` per process: confirmed and fixed (#1990, #1997). Win now makes 0-2 per hour.
- ETags per process: confirmed. The service has its own 304s since #2005 (win: 197 unbilled of 1054 in the 17:45 hour); CLI and worker processes get them with this PR.
- Per-issue comment and event reads: confirmed before #2005 (110 billed comment reads per hour on win at 12:22); after it, 131 answer 304 against 33 billed.
- Uncounted agent `gh` polls: inconclusive. The gap is 1320-1460/h including Mac's GitHub share; an estimate puts the agent, PM and DashQ part at 500-700/h.
- Not in the hypothesis: the open-issue list probe is the largest cost, 547 of 857 billed requests (64 %) on win in the 17:45 hour. Heartbeat writes change the list about once a minute, so the probe answers 304 only 4-5 times per hour.

## Recommendation

Keep the merged fixes and this PR (option A), and do C next: probe only task issues so heartbeats do not bill the list, which removes most of about 500/h per host. Add per-API-host counts (option D) so the next window measures the uncounted gap exactly.
