# Board readability: short issue pages, packed records, visible attachments

## Question

Issue pages are crowded with service log entries, links and technical records; results and attachments are hard to find ([#1980](https://github.com/taskqorg/taskq/issues/1980)). Which board format lets a person read state, result and attachments from the issue page in under 30 s, and shrinks technical records by at least half, without losing R1 board state? The decision rule: adopt an option only if both hold on real issues.

**Verdict.** The hypothesis is not confirmed as stated. No option meets both parts on stored records. One option meets both parts on the *visible* GitHub page under a stated reading model: option C (summary comment edited in place, plus GitHub's native collapse of service entries once their attempt ends). It cuts visible technical text by 78% and brings all 38 GitHub issues under 30 s (median 13.0 s, maximum 21.2 s, against 30.4 s and 100.9 s today). On the GitLab boards csgo and cs (17 issues, [1984.md](1984.md)), the summary alone (option B) brings 14 of 15 task issues under 30 s (today 7 of 15); with its Files line capped at three labels, all 15. GitLab has no comment collapse, so the size part is not met there. Two things are unknown and block adoption under R12: whether collapsing a comment changes its `updated_at` (which would make `fold` ignore it), and whether a person really reads the page that fast (the times are a model, not a user test). The recommendation is to qualify both unknowns first, then ship the summary on both boards and the collapse on GitHub.

## Findings

### Sample and method (A1)

55 real issues were read in full, from five GitHub and two GitLab boards. Totals: **1,531 comments, 507,045 characters**.

- GitHub, through the API on 2026-10-30: 38 issues, 36 task issues (28 closed, 8 open) and 2 heartbeat issues from taskq, pilotq, specq, dashq and coreq; 0 to 101 comments; 852 comments, 249,997 characters.
- GitLab, through the API from the Mac host on 2026-10-31 ([#1984](https://github.com/taskqorg/taskq/issues/1984), [1984.md](1984.md)): 17 issues from csgo and cs, 15 task issues (10 closed, 3 open, 2 closed held) and 2 heartbeat issues; 0 to 184 comments; 679 user comments, 257,048 characters, plus 6,190 system notes that are counted but not read. The Windows host has no GitLab access, so #1984 ran the same method there. Its script reproduces this report's GitHub read times within 0.3 s on unchanged threads; its option B times run up to 2.5 s above the mockups below, so they are on the slow side. Older csgo threads carry v3 entries (`**take** · codex:<id>`), classified by kind as service-only, outcome or human ([1984.md](1984.md#sample-and-method-a1-a2)).

Each line of each comment was classified:

- **machine**: the `taskq:` header, `op-id:` and `revision:` lines, `<!-- taskq` markers, and every line of a service-only kind (`hold`, `start`, `spawn`, `accepted`, `released`, `executing`, `enqueued`, `gate`, `rebased`, `usage-limit`, `approve`, report and result markers);
- **boilerplate**: `To answer:` lines;
- **both**: `Checks:`, `delivery`, `merged`/`enqueued` receipt lines;
- **human**: everything else, and all comments without a `taskq:` header.

Page height uses a GitHub desktop model: 96 px per comment block plus 24 px per extra rendered line, wrapping at 95 characters. Read time uses: 2 s to read the labels; 0.6 s to skim past one comment; 25 characters per second to read text. Today a reader starts at the bottom, skims up to the latest outcome (`result`, `ask`, `publish` or `close`) and reads its human lines. Files outside that comment cost one skim of the whole thread. These constants are assumptions; nobody was timed.

What the sample shows (GitHub figures unless a bullet names GitLab):

- **Service entries dominate the page, not the text.** 566 of 852 comments (66%) are service-only entries. They hold 36,022 characters (14%), but at one block each they take about 62,376 px, 37% of the modeled page height. Technical text overall is 49,095 characters (20%).
- **Only 19 of 38 issues read under 30 s today** (median 30.4 s, 90th percentile 44.5 s, maximum 100.9 s for taskq#1929). Long threads are slow because the latest outcome sits under its own trail of service entries, and because `close` repeats the `publish` verdict in full.
- **Duplication is concentrated.** 154 human or both lines (18,184 characters) repeat an earlier line of the same issue, mostly `close` repeating `publish`, and `publish` repeating `result`.
- **Results live in four places.** In 26 issues the result is a `result` comment; in 24 also a PR; in 3 a report file; 12 have none yet or were closed by hand. A reader needs the latest outcome comment plus at least one click to the PR.
- **Files are rare and never in a result.** 7 media links in the whole sample, all owner uploads: 5 in issue bodies, 2 in plain comments. The five UI-polish issues (taskq#1924, #1929, #1930, #1932, #1933) carry the same owner handoff zip in the body. No `result` or `ask` in the sample used `--image`. Worker visual evidence lives in repository files linked from the PR (taskq#1940 `docs/design/evidence/1940/`), two or more clicks from the issue.
- **Nothing was edited in place**: 0 of 852 comments have `updated_at` after `created_at`; all were written by one trusted account. Heartbeat issues already use the packed form: one body edited in place, 759 characters, no comments.
- **GitLab has the same shape on v4 issues.** cs is almost all v4: 69% service-only comments and 29% technical characters, against GitHub's 66% and 20%. csgo's older v3 threads show 46% and 12%, because v3 worker notes (`problem`, `beat`) read as long human text. Only 7 of 15 GitLab task issues read under 30 s today (csgo median 42.5 s, cs 29.4 s, maximum 99.8 s for cs#528).
- **GitLab threads carry admission churn.** cs#528 holds 91 `spawn` entries for 22 `accepted`: 69 claims that never ran, each a full comment block. This inflates the page on any board and is separate from the page format.
- **On csgo, files live in outcome comments.** csgo has 28 file links, all GitLab project uploads: 14 in `ask` comments (11 zip), 9 in `result` comments (7 zip), 5 in plain comments, none in issue bodies; cs has none. So "files are never in a result" holds for GitHub and cs, not for csgo. csgo#323's 23 uploads would make an uncapped summary Files line 920 characters long (37 s of reading).
- **GitLab keeps every description edit.** Each in-place edit of an issue description adds a "changed the description" system note: 5,733 on the csgo heartbeat issue, 285 on cs's, 43 on the v3 task csgo#323. 0 of 679 GitLab comments were edited, so whether editing a note (not the description) adds a system note is unknown.

Execution receipts (`accepted`, `released`, `executing`) are part of R1 truth: `fold` and the execution-ownership protocol read them ([runtime qualification](../runtime-qualification.md#execution-ownership)). ### Platform facts that decide the options

- GitHub can collapse a comment through the GraphQL `minimizeComment` mutation (classifier `OUTDATED` or `RESOLVED`); the page then shows one collapsed row. Whether this changes the comment's REST `updated_at` is **unknown**. If it does, `fold` treats the entry as edited and ignores it, which would lose state. This must be tested on a scratch issue before any use.
- GitHub web folds the middle of very long timelines behind "Load more"; the first and the last comments stay visible. A summary comment created early stays on screen; the threshold was not measured.
- GitLab has no comment collapse for issue notes. Threads can be resolved on merge requests; resolvable issue threads were not verified for these boards. A summary written to the issue description would add a system note and a stored version per edit, as the heartbeat issues show, so on GitLab the summary must be a note.
- Both boards allow a trusted account to edit its own comment in place, which taskq already relies on for heartbeat issue bodies.

### A. Trimmed status quo

Drop the derivable op-id lines of `accepted`, `released` and `executing`; `close` keeps its header and delivery receipt and names the `publish` it repeats; the board `ask` drops `To answer:` (the app card already renders without it).

- Pro: smallest change; no new object; same page on GitHub and GitLab.
- Pro: removes the duplicate verdict, so the latest outcome is short (median read 9.6 s).
- Con: technical text falls only 23%; long issues keep their trail (taskq#1929 still 100.9 s); fails the hypothesis.
- R1 impact: op ids become implied by header, so `fold` must derive them; N-1 services read a missing op id differently, so this needs an all-host cutover (§9). Dropping `To answer:` edits the §2 ask card rule. The Results card must read the verdict from `publish` when `close` refers to it.
- GitHub/GitLab fit: equal.
- Migration cost: medium (fold change, golden traces, cutover); old issues stay as they are.

### B. Summary comment edited in place

The service writes one summary comment per issue and edits it on every accepted state change: state, latest outcome (Changed, Open or the open question with its options), PR and merge receipt, and file links from the issue body and outcome comments: at most three labels, newest outcome first, then `and N more` linking the comment that holds them. Body starts with a hidden marker; `fold` never reads it. New tasks get it right after `hold`, so it sits under the issue body. On GitLab it is a note, never the issue description. Includes A.

- Pro: one place answers "what state, what result, which files"; in the model all 38 GitHub issues and, with the capped Files line, all 15 GitLab task issues read under 30 s.
- Pro: works on both boards; older issues get the summary on their next state change.
- Con: with the Files cap, older files are one click away instead of zero (csgo#323 lists 23).
- Con: technical records shrink only by A's 23%; fails the size part alone.
- Con: one extra comment edit per state change (API budget; about 10-20 per task).
- R1 impact: a new board object that is a projection, like labels. R1 must name it as a projection that `fold` ignores; a missing or stale summary is repaired from the log like a label. No issue machine block: it is a comment, and it holds human text only.
- GitHub/GitLab fit: equal; both support edits of own comments. Whether a GitLab note edit adds a system note is unknown; a description edit does.
- Migration cost: medium (writer, repair pass, R1 and §2 text); no cutover, because N-1 ignores comments without a known `taskq:` header.

### C. Summary plus collapsed service entries (recommended, GitHub)

B, plus: when an attempt ends (its `released` is read back) or a task closes, the service collapses that attempt's service-only entries with `minimizeComment` (`OUTDATED`). `result`, `ask`, `publish`, `close` and human entries stay open.

- Pro: meets both parts of the hypothesis on the visible page: visible technical text −78%, every issue under 30 s.
- Pro: stored records and comment order are unchanged, so `fold`, op ids and the claim race are untouched, if collapse leaves `updated_at` unchanged.
- Con: unknown whether collapse changes `updated_at` (blocking); one GraphQL call per entry (about 15 per task; the sample would have needed 566).
- Con: GitLab cannot collapse notes; csgo and cs keep B only (15 of 15 under 30 s with the Files cap) and the size part fails there.
- R1 impact: none if the qualification passes; if collapse changes `updated_at`, this option is dropped.
- Migration cost: low after B; old closed issues can be collapsed by a one-time, rate-limited pass, or left as they are.

### D. One execution ledger per attempt

B, plus: `accepted`, `released`, `executing` and `enqueued` go into one ledger comment per attempt, edited in place; `spawn` stays a separate comment.

- Pro: fewer blocks (−35%) on both boards.
- Con: only −34% technical text; fails the size part.
- Con: breaks "the first release proof is immutable" and "edited observations are ignored": an edit can rewrite an earlier receipt, and two hosts editing one comment race.
- R1 impact: large: new fold input, new execution protocol, all-host cutover.
- Migration cost: high. Rejected.

Also measured and rejected: packing service entries written within 5 s into one comment cuts blocks only 13% (566 to 495) and changes every entry reader; a separate machine-log issue per task breaks R1's per-task truth.

### Decision questions

1. **Summary comment in R1.** Today a person finds state, result and files by scrolling the log; a summary comment puts them under the issue body, but R1 must name a new board object.
   1. Summary as an R1 projection. Plus: all 51 sampled task issues read under 30 s (model). Minus: one comment edit per state change, about 10-20 calls per task.
   2. No summary; the app Results card only. Plus: no new board object and no extra API calls. Minus: the issue page stays slow (24 of 51 task issues under 30 s today).
   Recommended: summary as an R1 projection, because it alone meets the 30 s part on both boards and repairs like a label.
2. **Scope of GitHub collapse.** If collapse keeps `updated_at`, ended service entries can fold to one row each; this decides when.
   1. Collapse on every task once an attempt ends (C). Plus: open long tasks shrink too (taskq#1929: 39 blocks to rows). Minus: about 15 GraphQL calls per task during work.
   2. Collapse only when the task closes. Plus: fewer calls, one pass per task. Minus: open tasks, where decisions happen, keep their full trail.
   Recommended: every task once an attempt ends, because open reviews and asks are where the owner reads the page.
3. **Size cap for result archives.** Workers get `--file` for zip, tar.gz, PDF and HTML; the cap decides what fits and what clones cost.
   1. 25 MB. Plus: matches GitHub web uploads for zip. Minus: larger evidence still goes through the PR.
   2. 10 MB. Plus: same as today's image cap; small clones. Minus: csgo-style handoff zips may not fit.
   3. 100 MB. Plus: almost every archive fits. Minus: git refuses at 100 MB and warns at 50 MB; slow evidence fetches.
   Recommended: 25 MB, because it matches the owner's own upload route and stays well under git's limits.
4. **GitLab without collapse.** csgo and cs cannot collapse notes, so only the 30 s part can hold there; technical text stays at 12-29% of the page.
   1. B with the Files cap on GitLab. Plus: 15 of 15 GitLab task issues under 30 s (model), no extra work. Minus: the size part stays unmet on GitLab.
   2. Also hide service entries as GitLab internal notes. Plus: may shrink the visible page. Minus: unverified; internal notes hide entries from non-members and may change what `fold` reads.
   Recommended: B with the Files cap, because it meets the reader goal now; revisit after the GitLab note qualification.
