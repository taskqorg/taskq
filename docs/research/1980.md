# Board readability: short issue pages, packed records, visible attachments

## Question

Issue pages are crowded with service log entries, links and technical records; results and attachments are hard to find ([#1980](https://github.com/taskqorg/taskq/issues/1980)). Which board format lets a person read state, result and attachments from the issue page in under 30 s, and shrinks technical records by at least half, without losing R1 board state? The decision rule: adopt an option only if both hold on real issues.

**Verdict.** No option meets both parts on stored records. One option meets both parts on the *visible* page under a stated reading model: option C (summary comment edited in place, plus GitHub's native collapse of service entries once their attempt ends). It cuts visible technical text by 78% and brings every sampled issue under 30 s (median 13.0 s, maximum 21.2 s, against 30.4 s and 100.9 s today). Two things are unknown and block adoption under R12: whether collapsing a comment changes its `updated_at` (which would make `fold` ignore it), and whether a person really reads the page that fast (the times are a model, not a user test). GitLab has no comment collapse, so GitLab boards get the summary but not the size cut. The recommendation is to qualify both unknowns first, then ship the summary on both boards and the collapse on GitHub.

## Findings

### Sample and method (A1)

38 real issues were read in full through the GitHub API on 2026-10-30: 36 task issues (28 closed, 8 open) and 2 heartbeat issues from taskq, pilotq, specq, dashq and coreq; 0 to 101 comments. Totals: **852 comments, 249,997 characters**.

csgo and cs are self-hosted GitLab boards. This Windows host has no GitLab token and no registered GitLab project, so they were **not read** (unknown, R12). Their fit is judged from the GitLab adapter (`src/board/gitlab.rs`) and GitLab's documented behavior. A follow-up task on the Mac host extends the sample to them.

Each line of each comment was classified:

- **machine**: the `taskq:` header, `op-id:` and `revision:` lines, `<!-- taskq` markers, and every line of a service-only kind (`hold`, `start`, `spawn`, `accepted`, `released`, `executing`, `enqueued`, `gate`, `rebased`, `usage-limit`, `approve`, report and result markers);
- **boilerplate**: `To answer:` lines;
- **both**: `Checks:`, `delivery`, `merged`/`enqueued` receipt lines;
- **human**: everything else, and all comments without a `taskq:` header.

Page height uses a GitHub desktop model: 96 px per comment block plus 24 px per extra rendered line, wrapping at 95 characters. Read time uses: 2 s to read the labels; 0.6 s to skim past one comment; 25 characters per second to read text. Today a reader starts at the bottom, skims up to the latest outcome (`result`, `ask`, `publish` or `close`) and reads its human lines. Files outside that comment cost one skim of the whole thread. These constants are assumptions; nobody was timed.

What the sample shows:

- **Service entries dominate the page, not the text.** 566 of 852 comments (66%) are service-only entries. They hold 36,022 characters (14%), but at one block each they take about 62,376 px, 37% of the modeled page height. Technical text overall is 49,095 characters (20%).
- **Only 19 of 38 issues read under 30 s today** (median 30.4 s, 90th percentile 44.5 s, maximum 100.9 s for taskq#1929). Long threads are slow because the latest outcome sits under its own trail of service entries, and because `close` repeats the `publish` verdict in full.
- **Duplication is concentrated.** 154 human or both lines (18,184 characters) repeat an earlier line of the same issue, mostly `close` repeating `publish`, and `publish` repeating `result`.
- **Results live in four places.** In 26 issues the result is a `result` comment; in 24 also a PR; in 3 a report file; 12 have none yet or were closed by hand. A reader needs the latest outcome comment plus at least one click to the PR.
- **Files are rare and never in a result.** 7 media links in the whole sample, all owner uploads: 5 in issue bodies, 2 in plain comments. The five UI-polish issues (taskq#1924, #1929, #1930, #1932, #1933) carry the same owner handoff zip in the body. No `result` or `ask` in the sample used `--image`. Worker visual evidence lives in repository files linked from the PR (taskq#1940 `docs/design/evidence/1940/`), two or more clicks from the issue.
- **Nothing was edited in place**: 0 of 852 comments have `updated_at` after `created_at`; all were written by one trusted account. Heartbeat issues already use the packed form: one body edited in place, 759 characters, no comments.

### Platform facts that decide the options

- GitHub can collapse a comment through the GraphQL `minimizeComment` mutation (classifier `OUTDATED` or `RESOLVED`); the page then shows one collapsed row. Whether this changes the comment's REST `updated_at` is **unknown**. If it does, `fold` treats the entry as edited and ignores it, which would lose state. This must be tested on a scratch issue before any use.
- GitHub web folds the middle of very long timelines behind "Load more"; the first and the last comments stay visible. A summary comment created early stays on screen; the threshold was not measured.
- GitLab has no comment collapse for issue notes. Threads can be resolved on merge requests; resolvable issue threads were not verified for these boards.
- Both boards allow a trusted account to edit its own comment in place, which taskq already relies on for heartbeat issue bodies.

### A. Trimmed status quo

Drop the derivable op-id lines of `accepted`, `released` and `executing`; `close` keeps its header and delivery receipt and names the `publish` it repeats; the board `ask` drops `To answer:` (the app card already renders without it).

- Pro: smallest change; no new object; same page on GitHub and GitLab.
- Pro: removes the duplicate verdict, so the latest outcome is short (median read 9.6 s).
- Con: technical text falls only 23%; long issues keep their trail (taskq#1929 still 100.9 s); fails the hypothesis.
- R1 impact: op ids become implied by header, so `fold` must derive them; N-1 services read a missing op id differently, so this needs an all-host cutover (§9). Dropping `To answer:` edits the §2 ask card rule. The Results card must read the verdict from `publish` when `close` refers to it.
- GitHub/GitLab fit: equal.
- Migration cost: medium (fold change, golden traces, cutover); old issues stay as they are.

### B. Summary comment edited in place

The service writes one summary comment per issue and edits it on every accepted state change: state, latest outcome (Changed, Open or the open question with its options), PR and merge receipt, and every file link from the issue body and outcome comments. Body starts with a hidden marker; `fold` never reads it. New tasks get it right after `hold`, so it sits under the issue body. Includes A.

- Pro: one place answers "what state, what result, which files"; every sampled issue reads under 30 s in the model.
- Pro: works on both boards; older issues get the summary on their next state change.
- Con: technical records shrink only by A's 23%; fails the size part alone.
- Con: one extra comment edit per state change (API budget; about 10-20 per task).
- R1 impact: a new board object that is a projection, like labels. R1 must name it as a projection that `fold` ignores; a missing or stale summary is repaired from the log like a label. No issue machine block: it is a comment, and it holds human text only.
- GitHub/GitLab fit: equal; both support edits of own comments.
- Migration cost: medium (writer, repair pass, R1 and §2 text); no cutover, because N-1 ignores comments without a known `taskq:` header.

### C. Summary plus collapsed service entries (recommended, GitHub)

B, plus: when an attempt ends (its `released` is read back) or a task closes, the service collapses that attempt's service-only entries with `minimizeComment` (`OUTDATED`). `result`, `ask`, `publish`, `close` and human entries stay open.

- Pro: meets both parts of the hypothesis on the visible page: visible technical text −78%, every issue under 30 s.
- Pro: stored records and comment order are unchanged, so `fold`, op ids and the claim race are untouched, if collapse leaves `updated_at` unchanged.
- Con: unknown whether collapse changes `updated_at` (blocking); one GraphQL call per entry (about 15 per task; the sample would have needed 566).
- Con: GitLab cannot collapse notes; GitLab boards keep B only and the size part fails there.
- R1 impact: none if the qualification passes; if collapse changes `updated_at`, this option is dropped.
- Migration cost: low after B; old closed issues can be collapsed by a one-time, rate-limited pass, or left as they are.

### D. One execution ledger per attempt

B, plus: `accepted`, `released`, `executing` and `enqueued` go into one ledger comment per attempt, edited in place; `spawn` stays a separate comment.

- Pro: fewer blocks (−35%) on both boards.
- Con: only −34% technical text; fails the size part.
- Con: breaks "the first release proof is immutable" and "edited observations are ignored": an edit can rewrite an earlier receipt, and two hosts editing one comment race.
- R1 impact: large: new fold input, new execution protocol, all-host cutover.
- Migration cost: high. Rejected.

Also measured and rejected: packing service entries written within 5 s into one comment cuts blocks only 13% (566 to 495) and changes every entry reader; a separate machine-log issue per task breaks R1's per-task truth.

### Hypothesis check

| Part | A | B | C | D |
|---|---|---|---|---|
| Read state, result, files in < 30 s | 31/38 issues (model) | 38/38 (model) | 38/38 (model) | 38/38 (model) |

The hypothesis is **not confirmed** as stated. It holds for C on GitHub under the model, and only for the visible page. Confirmation needs the collapse probe and a timed read of the three mockups by a person.

## Recommendation

1. Qualify the two unknowns first: collapse and `updated_at` on github.com, a non-branch evidence ref, and GitLab collapse or resolve options, on a scratch issue.
2. Ship B on both boards: the summary comment as a named R1 projection, with file links from the issue body and outcome comments. This alone fixes reading time.
3. Ship C on GitHub if the probe shows `updated_at` unchanged; otherwise keep B and accept the size gap.
4. Add an archive route to `result` (`--file` for zip, tar.gz, PDF, HTML up to 25 MB through the evidence ref on GitHub and project uploads on GitLab), listed in the summary.
5. Take A's `close` de-duplication into B's summary work; leave the op-id trim, which needs a cutover for 9% fewer characters, until a §9 cutover happens for other reasons.

### Decision questions

1. May R1 list a service-owned summary comment, edited in place and never read by `fold`, as a projection next to labels? ★ yes, as in B; alternative: no summary, keep reading from the app Results card only.
2. If GitHub collapse does not change `updated_at`, should ended service entries be collapsed on every task (C), or only on closed tasks?
3. Which size cap fits result archives: 25 MB (GitHub web parity, recommended), 10 MB (today's image cap) or 100 MB (git limit, larger clones)?
4. GitLab boards cannot collapse notes: is B alone acceptable there, which means the size part of the hypothesis is not met on csgo and cs?
