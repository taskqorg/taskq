# Contract reuse audit: one spec change reaches every surface

## Question

The owner's goal ([#1981](https://github.com/taskqorg/taskq/issues/1981)): a format rule, such as the answer-card choices, is edited once in a spec. The rule then holds in Conversations, the taskq CLI, PilotQ and DashQ with no per-surface code.

Hypothesis: each shared format has one owning contract that every surface consumes, so a spec edit needs no hand edits elsewhere.

Decision rule: a format passes only if a probe edit propagates and tests fail where a surface drifts.

### Consumption ratings

Each consumer is rated:
- **a, shared:** shared code or a versioned schema with field access; drift fails at least at runtime.
- **b, vendored:** a pinned copy of taskq code or fixtures; it lags until a person repins it.
- **c, own:** an own reimplementation of the text format; nothing fails on drift.

"Lines" counts the duplicated parsing or table code in the consumer, not the rendering.

### Drift found

1. **Card fixtures do not match the writer.** Only 2 of 23 option cards in [tests/fixtures/answer-card.json](../../tests/fixtures/answer-card.json) use the § 2 writer form `<label> - + <gain>; - <cost>`. The fixtures test the parser, not what `taskq ask` accepts.
2. **Six production cards bypass the writer.** The retry-limit card ([src/core.rs:94-100](../../src/core.rs#L94-L100)) has no `Done:` line and its options lack gain and cost, although § 2 specifies its content. The blocked, closed, start-refused and input-failed cards are hand-written too.
3. **PilotQ parses raw card text.** It never reads `question`, so `recommended`, `consequential` and `evidence` are re-derived. It answers with N.K rebuilt from rendered text, not choice ids. Its test fixture uses the retired `Plus:` / `Minus:` / `Recommended:` layout (pilotq `tests/telegram.rs:2626`). The live test is `#[ignore]` (pilotq `tests/telegram.rs:1855-1881`).
4. **PilotQ state tables omit `failed`** in `src/journal.rs:2079-2085` and `src/conversation.rs:53-74`.
5. **DashQ checks only half of `consequential`.** taskq marks a choice consequential if it starts with `close` or approves a SHA ([src/snapshot.rs:601](../../src/snapshot.rs#L601)). dashq `closes()` (`src/answer.rs:46`) checks only `close`, so its `/answer` route accepts an approval choice. Only the vendored component honours the flag.
6. **DashQ counters omit `held`.** dashq `COUNTS` (`src/data.rs:13`) has 7 states; taskq [src/display.rs:8-9](../../src/display.rs#L8-L9) has 8, and task-counters K-A3 counts Held.
7. **DashQ drops valid telemetry.** dashq `ERRORS` (`src/agent_work.rs:16`) lacks taskq's `argument-too-long` ([src/profile.rs:14](../../src/profile.rs#L14)); such records count as corrupt with no error.
8. **DashQ heartbeat `ttl` is never sent.** dashq parses it; taskq never writes it, so dashq always uses 300.
9. **DashQ text limits are stale.** dashq hardcodes 4 lines of 240 characters; taskq now sends `limits: {chars: 240}`. dashq `fixture/input.json:110` still has `limits: {lines: 4}`.
10. **agentq 1.0 reads as unknown.** taskq accepts agentq only as `0.x` with x ≥ 5 ([src/agentq.rs:54](../../src/agentq.rs#L54)).
11. **coreq telemetry allowlist is a hidden copy.** coreq `src/telemetry.rs:41` lists six taskq field names. A new taskq field is dropped with no failure.
12. **DashQ pins disagree with its own docs.** `resource-controls.md:69` says the files come from unreleased source `0d4b1be`; `assets/taskq/sources.json` says v4.6.25.

### Probe: answer-card case end to end (A3)

Dry run in this worktree, reverted before the report: the recommended marker moves from the end of an option to the front, `K. ★ <label> - + <gain>; - <cost>`.

**Step 1, spec only.** Edited taskq.md § 2 Ask card item 4. Ran `cargo test --locked --bin taskq` with filters `card`, `question`, `option`, `fixture`, `ask` and `answer`: 92 tests, **0 failed**. The full binary suite failed the same 18 tests as without the edit; all 18 are host, lifecycle, resources, tray-capacity and sandbox tests that the worker sandbox blocks. The spec text is not executable, so nothing notices the edit.

**Step 2, canonical code.** Changed `core::options` to read a leading `★ ` and `numbered` to write it (4 lines). The full suite then failed **15 more tests**:

- Parser and writer: `ask_card_follows_section_2`, `answer_card_fixtures_carry_the_canonical_parse`, `status_json_matches_the_golden_fixture`, `report_follows_r6`, `result_and_close_follow_section_7`, `compact_report_keeps_choices_links_and_original_evidence`, `enrollment_projects_only_approved_board_metadata`.
- Fold and delivery: `core::golden_traces`, `delivery_falls_back_to_option_then_first_line`, `limit_text_adds_the_card_only_at_the_limit`, two `pending` answer tests, `board` inbox JSON, `tray` answer bridge, and the installed Windows binary fixture (fold of an option match).

These failures come from old-format literals in tests and fixtures. Inside taskq the canonical code is guarded.

Result: the answer card fails the decision rule. A spec edit propagates nowhere by itself. A code edit is caught inside taskq, but 7 taskq producers and the PilotQ parser drift silently, and DashQ lags until a manual repin.

### Verdict

The hypothesis does not hold. Of 13 shared formats, 2 meet it (coreq enrollment and status keys). The answer card meets it partly: one owner, one canonical parser, released fixtures and a component DashQ consumes. But nothing ties the prose to the code, 7 producers bypass the writer, and PilotQ and the DashQ server reimplement parts of it. States, verdicts, heartbeat and telemetry vocabularies have no released contract at all, so every consumer keeps its own table.

## Options

### Option A: released schema and fixtures, contract test per consumer

Extend the answer-card release pattern ([answer-card.md](../design/answer-card.md)) to the status snapshot, state names, verdict, heartbeat and telemetry vocabularies. Each consumer runs a contract test against the pinned fixtures and a scheduled check against the latest release.

- **+** Language-neutral; works for Rust, JavaScript and the Telegram renderer. Pattern and release tooling already exist.
- **+** A taskq change that alters a fixture shows up as a failing test in every consumer.
- **−** Consumers keep their own parsing and tables; the test only detects drift.
- **−** Pins still lag until someone repins.
- **Code removed:** none directly. It adds about 100 lines of tests per consumer.
- **Migration cost:** low to medium; one taskq task, one task per consumer.

### Option B: consumers read only taskq-parsed JSON

taskq parses each text format once and emits typed fields, as it already does with `question`. Add `verdict {changed, checks, open}`, the state list with labels and counter order, and the telemetry vocabularies to `status --json`. Consumers stop reading card or comment text.

- **+** A format change edits one parser and one writer in taskq; the JSON stays the same, so consumers need no edit.
- **+** Removes the largest silent drift: PilotQ card, state and verdict parsers, and DashQ tables.
- **+** Fixes drift items 3-7 as a side effect.
- **−** Needs new snapshot fields and a schema version; consumers must handle older taskq versions while hosts upgrade.
- **−** Rendering stays per surface, which is intended (Telegram and HTML differ).
- **Code removed:** about 315 lines (pilotq ~121, dashq ~175, taskq tray parse ~10, coreq allowlist ~6, profile copy ~3).
- **Migration cost:** medium; one taskq task, then one task per consumer.

### Option C: shared crate and package

Move `State`, `question`, verdict parsing and vocabularies into a library, either coreq or a new taskq-format crate with an npm twin.

- **+** Rust consumers get compile-time errors on drift.
- **−** coreq pins already differ in every repository (`1c23357`, v0.11.0, 0.14.6, 0.14.10); the lag moves into the crate version.
- **−** Product formats would live outside taskq.md's owner, which inverts R13 ownership.
- **−** JavaScript and Telegram rendering still need a second implementation or a WebAssembly build.
- **Code removed:** about 300 lines, similar to Option B, but adds a library and its release process.
- **Migration cost:** high.

### Option D: taskq renders for every surface

`taskq render --surface telegram|html` or generated renderers; surfaces show taskq output verbatim.

- **+** No per-surface format code at all.
- **−** taskq would own Telegram markup and DashQ server pages; DashQ has no local taskq binary for most views.
- **−** Couples surface releases to the taskq version on each host.
- **Code removed:** about 500 lines including renderers, but adds them to taskq.
- **Migration cost:** high.

### Within taskq

All options need two taskq changes regardless: one card writer for all producers, and fixtures that pass the writer's own validation. Spec prose cannot be tested; the executable contract is the writer, the parser and the released fixtures.

## Recommendation

Adopt **Option B, guarded by Option A**:

1. taskq routes every card through one writer and validates its fixtures with it.
2. taskq adds `verdict`, state metadata and telemetry vocabularies to the snapshot and publishes the snapshot schema and fixtures as release assets.
3. PilotQ and DashQ drop their text parsers and tables, read the typed fields, and run a contract test against the released fixtures, plus a scheduled check against the latest release.
4. DashQ automates its repin check so that lag shows as a failing job, not a docs note.

This removes about 315 lines of own reimplementation. After it, a format edit changes the spec, the taskq writer and parser, and the fixtures; every consumer either needs no change or fails its contract test.

Option C is not recommended: coreq pins already lag in every repository, and taskq.md should keep owning product formats.

### Decision questions

These do not block any task. They decide the scope of the proposed tasks.

**Q1. Contract mechanism.**
1. Typed JSON plus released fixtures - + removes ~315 lines, drift fails tests; - new snapshot fields and version handling ★
2. Released fixtures only - + cheapest, no schema change; - keeps ~420 duplicate lines
3. Shared crate - + compile-time errors for Rust; - pin lag moves into the crate, formats leave taskq.md

**Q2. DashQ vendored assets.**
1. Scheduled latest-release check - + lag becomes a failing job; - still a manual repin PR ★
2. Fetch from the release at build - + no vendored copy; - build needs network and a pinned checksum list
