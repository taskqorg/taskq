# Unaccepted spawn churn on cs#528

## Question

[cs#528](https://gitlab.ufobe.com/gradus/cyprusbz/-/issues/528) holds 91 `spawn` entries for 22 `accepted` ([1980.md](1980.md), [1984.md](1984.md)). Why did those claims never run, and does the same churn fill GitHub issue pages?

**Status.** Stage A2 is done. Stage A1 is open: this attempt ran on the Windows host, which has no GitLab access ([1980.md](1980.md#sample-and-method-a1)), so it could not read cs#528 or the Mac service log that serves cs. The per-spawn evidence is a Mac-host step, filed as [#2038](https://github.com/taskqorg/taskq/issues/2038); this report gets its A1 section when that evidence lands.

## Findings

### Method

[2020-spawns.py](2020-spawns.py) reads an issue's comments and classifies each `spawn` entry S by what followed it:

- **accepted**: a later `taskq: accepted S attempt S` exists. The child was delivered.
- **ran**: no `accepted S`, but a later entry carries `attempt S` (result, ask, requeue, gone, released). The child ran; the writer predates `accepted` entries or never wrote one.
- **no-start**: `released S no-start`. Fold took the claim; the owner host proved the child never started.
- **lost**: no later entry names S. Fold did not take the claim, or the claim was never delivered and never released.

The count of `accepted` entries is not a count of accepted spawns: a resume (`executing`) is also accepted. On GitHub most long issues hold more `accepted` entries than spawns. A ratio of 91 to 22 therefore means at least 69 spawns without their own `accepted`.

### cs#528: what the GitHub record already shows (A1, partial)

The cause of the bulk of the churn is already on record, from tasks that ran on the Mac host:

- [#1903](https://github.com/taskqorg/taskq/issues/1903), filed 2026-10-30 07:53Z: the Mac service re-posted `spawn` on cs#528 about every 45 s from 07:24Z, logging `claim unknown: readback lacks the spawn`. The issue then had 138 notes; the last good claim was before note 100.
- Cause, from [PR #1904](https://github.com/taskqorg/taskq/pull/1904): the board client sent page 1 of the notes as a conditional GET. A 304 replayed the cached reply and its `Link` header. The cache was filled while the issue had at most 100 notes, so the replayed `Link` had no next page. A long-running service never read notes past 100, never saw its own spawn, and claimed again on the next pass.
- Fix: PR #1904 (merged 08:15Z) rereads a full 304 page once, and remembers an unseen spawn so the service posts no new spawn for that task until it shows (`src/service.rs`, `claim_inner`). Released in v4.6.47 (published 2026-10-30 12:51Z).
- [#1905](https://github.com/taskqorg/taskq/issues/1905), filed 08:17Z: cs#528 then held 144 notes, 64 spawns and 17 `accepted`, so at least 47 unaccepted spawns. At about 45 s per pass, a loop from 07:24Z to about 08:00Z posts about 48 spawns, which matches. These spawns are attributed to the #1903 readback loop by timing, not yet spawn by spawn.

Open: between #1905 (64 spawns, 17 `accepted`) and the #1984 read on 2026-10-31 (91 spawns, 22 `accepted`), cs#528 gained 27 spawns and only 5 `accepted`: about 22 more unaccepted spawns after the loop window. Their cause is **unknown**. Candidates, each checkable from the Mac service log:

1. The #1903 loop continued until the Mac host installed v4.6.47. A restart refills the cache with a full page 1 and its next link, so a restarted old binary should not loop again; a loop after a restart would point to another cause.
2. A fold-rejected claim. `claim_inner` guards only the unseen case: a spawn that the readback sees but fold does not take logs `lost the claim` and returns, and nothing stops the next pass from posting again. If the service's admission and fold's acceptance ever disagree for this task, it would post a spawn every pass. No GitHub issue shows this.
3. Claims released as `no-start`, or two-host races, if another host also serves cs.

Missing evidence for A1: the cs#528 notes (id, time, host, and what followed each spawn) and the Mac service log lines for task 528 (`spawn <id> lost the claim`, `claim unknown`, `released`, restarts and updates) from 2026-10-29 on. Both are readable only on the Mac host.
