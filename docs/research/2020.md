# Unaccepted spawn churn on cs#528

## Question

[cs#528](https://gitlab.ufobe.com/gradus/cyprusbz/-/issues/528) holds 91 `spawn` entries for 22 `accepted` ([1980.md](1980.md), [1984.md](1984.md)). Why did those claims never run, and does the same churn fill GitHub issue pages?

**Status.** Both stages are done. A2 was read on the Windows host from GitHub. A1 needs cs#528 and the Mac service log, which only the Mac host can read; [#2038](https://github.com/taskqorg/taskq/issues/2038) read them and reported in [2038.md](2038.md).

## Findings

### Method

[2020-spawns.py](2020-spawns.py) reads an issue's comments and classifies each `spawn` entry S by what followed it:

- **accepted**: a later `taskq: accepted S attempt S` exists. The child was delivered.
- **ran**: no `accepted S`, but a later entry carries `attempt S` (result, ask, requeue, gone, released). The child ran; the writer predates `accepted` entries or never wrote one.
- **no-start**: `released S no-start`. Fold took the claim; the owner host proved the child never started.
- **lost**: no later entry names S. Fold did not take the claim, or the claim was never delivered and never released.

The count of `accepted` entries is not a count of accepted spawns: a resume (`executing`) is also accepted. On GitHub most long issues hold more `accepted` entries than spawns. A ratio of 91 to 22 therefore means at least 69 spawns without their own `accepted`.

- **The churn marker fires only on note count here.** `taskq profile health` on the Windows host flags one task, desiign#14 (`notes 131 · spawns 14 · accepted 18`): over 100 notes, no unaccepted spawns.

### cs#528 (A1)

Evidence: [2038.md](2038.md), which ran [2020-spawns.py](2020-spawns.py) unchanged on all 205 notes of cs#528 (read 2026-10-31 on the Mac host) and matched each spawn to the Mac service log of the cs project (from 2026-10-26, so it covers every spawn).

| Class | Count | Time (UTC) | Host |
|---|---:|---|---|
| accepted | 19 | 2026-10-29 13:49Z to 2026-10-31 06:00Z | mac |
| ran | 0 | - | - |
| no-start | 1 | 2026-10-30 07:24:50Z | mac |
| lost | 72 | 2026-10-30 07:25:27Z to 08:17:45Z | mac |

92 spawns: one more than the #1984 read, an accepted spawn at 2026-10-31 06:00:35Z.

- **All 73 unaccepted spawns have one cause: the [#1903](https://github.com/taskqorg/taskq/issues/1903) readback loop.** Each has its own `#528 spawn <id> claim unknown: readback lacks the spawn` log line, 2 to 5 s after its board time. The board client replayed a cached page-1 reply whose `Link` header had no next page, so the service never saw its own spawn past note 100 and claimed again about every 44 s ([PR #1904](https://github.com/taskqorg/taskq/pull/1904)).
- **The first spawn of the loop (2026-10-30 07:24:50Z) is the no-start.** Fold took it, but the service never saw it and never started the child. After the restart the service released it as `no-start` and wrote `gone`.
- **The other 72 are lost.** Fold ignored each one, because the task was already `doing` under the first. Each still has its `claim unknown` line.
- **The loop ended at a restart.** The update to the build made after PR #1904 merged (08:15:08Z) logged at 08:17:46Z; the old process posted its last spawn at 08:17:45Z; the new service started at 08:17:53Z. The log does not record the build's source commit, so the fix is placed in that build by timing and by the stop.
- **No other cause occurs.** The cs log has no `lost the claim` line and no other `claim unknown` line; every spawn is by the `mac` host, so no two-host race is possible; no other restart falls inside the window.
- **The 22 later unaccepted spawns this report estimated do not exist.** The estimate took 64 spawns from the #1905 filing as the count at 08:17Z. The notes show 86 spawns by 08:17:45Z, so 64 was an earlier, partial count. All 6 spawns after the loop are accepted.

## Options

1. **Treat the churn as fixed by PR #1904 (v4.6.47).** Plus: every unaccepted spawn on cs#528 and on 12 GitHub issues has a named cause; no spawn churned after the fix. Minus: none found.
2. **Also add the build source commit to the service start line.** Plus: a later attribution could prove which fix a build holds. Minus: a code change for a question this evidence already answers by timing.

## Verdict

Confirmed. All 73 unaccepted spawns on cs#528 come from the #1903 readback loop on the Mac host, 2026-10-30 07:24:50Z to 08:17:45Z: 72 lost behind the first claim, and that first claim released as no-start after the restart. The churn does not occur on GitHub: 3 of 152 spawns on 12 long issues never ran, all two-host claim races, as § 3 expects.

## Recommendation

Option 1. Claims that never run stopped filling issue pages with PR #1904; no new task.
