# GitLab note options and note edit readback

## Question

[#2016](https://github.com/taskqorg/taskq/issues/2016) A3 needs GitLab evidence the Windows host cannot collect: which issue note collapse, thread resolve and internal-note options a GitLab board accepts, and what a note edit does to `updated_at`, system notes and order. The answer decides whether a GitLab board can hide or mark taskq entries without `fold` ignoring them (taskq.md § 2: an entry whose `updated_at` differs from `created_at` is ignored; the GitLab adapter compares the two strings, `src/board/gitlab.rs`).

## Method

- Instance: `gitlab.ufobe.com`, `GET /version` = `17.2.9-ee` (revision `91146650fd2`, enterprise).
- Project `alex/csgo`, run from the Mac host on 2026-10-31 with the host's GitLab token (owner account, Reporter+).
- Scratch issue `alex/csgo#438`, created without labels (no `taskq`), closed at the end of the run (`state: closed`, `closed_at 2026-10-31T05:42:21.848Z`, `labels: []`).
- Script: [2030-probe.py](2030-probe.py) (`SSL_CERT_FILE=/etc/ssl/cert.pem python3 -I docs/research/2030-probe.py gitlab.ufobe.com alex/csgo <token file>`).
- Raw readbacks, every request with its HTTP status and response, author objects reduced to the username: [2030-readbacks.json](2030-readbacks.json).

## Findings

### A1. Options and their HTTP status

| Option | Request | HTTP | Readback |
|---|---|---:|---|
| Internal note at create | `POST notes {internal: true}` | 201 | `internal: true`, `confidential: true`; `updated_at = created_at` |
| Internal note at create, deprecated name | `POST notes {confidential: true}` | 201 | same as above |
| Make an existing note internal | `PUT notes/:id {internal: true}` | 200 | ignored: `internal: false`, `updated_at` unchanged |
| Start a resolvable thread on an issue | `POST discussions {body}` | 201 | `individual_note: false`, `type: DiscussionNote`, `resolvable: true`, `resolved: false` |
| Resolve the thread | `PUT discussions/:id {resolved: true}` | 200 | `resolved: true`; note `updated_at` moved from `05:42:09.355Z` to `05:42:10.288Z` |
| Resolve via the note | `PUT notes/:id {resolved: true}` | 200 | `resolved: true`, `resolved_by: alex` |
| Resolve via GraphQL | `discussionToggleResolve(resolve: true)` | 200 | `errors: []`, `resolved: true` |
| Collapse | `PUT notes/:id {collapsed: true}` | 200 | ignored: no field, `updated_at` unchanged |
| Hide | `PUT notes/:id {hidden: true}` | 200 | ignored, same |
| Minimize | `PUT notes/:id {minimized: true}` | 200 | ignored, same |

GraphQL confirms the REST result. `UpdateNoteInput` has only `clientMutationId`, `id` and `body`. Type `Note` has `internal`, `resolvable`, `resolved`, `resolvedAt`, `lastEditedAt`, but no collapse, hide or minimize field. No note mutation exists for collapse; the note mutations are `createNote`, `updateNote`, `destroyNote`, `createDiscussion`, `discussionToggleResolve` and diff/image-note variants.

Results:

- **Collapse: none.** GitLab 17.2 has no API or field to collapse, hide or minimize an issue note. Unknown parameters return 200 and change nothing.
- **Resolve: works on issue threads, but edits the note.** Resolving moves `updated_at` of the thread note, so a resolved taskq entry reads as edited and `fold` ignores it.
- **Internal: only at create.** An internal note keeps `updated_at = created_at` and stays in the notes list for a Reporter+ token. An existing note cannot become internal.

### A2. Note edit readback

Plain note `29942` was posted, then its body edited with `PUT notes/:id {body}` (HTTP 200).

| Note | Before edit: created_at / updated_at | After edit: created_at / updated_at | system |
|---|---|---|---|
| 29942 plain | `05:42:03.500Z` / `05:42:03.500Z` | `05:42:03.500Z` / `05:42:18.852Z` | false |
| 29943 internal | not yet posted | `05:42:06.300Z` / `05:42:06.300Z` | false |
| 29944 confidential | not yet posted | `05:42:07.449Z` / `05:42:07.449Z` | false |
| 29945 thread, resolved | not yet posted | `05:42:09.355Z` / `05:42:10.288Z` | false |

- The edit keeps `id` and `created_at`, sets `updated_at` to the edit time, and adds no system note. The notes list holds no system note before or after, also after the close (a later read showed the same four notes).
- Order: the default list is newest first (29945, 29944, 29943, 29942); `order_by=created_at&sort=asc` is oldest first. An edit does not move a note in either order.
- An edit is detectable by `updated_at != created_at`, as the adapter already does; GraphQL also exposes `lastEditedAt`.

## Options

1. **GitLab keeps every taskq entry visible; summary only.** Plus: matches #1980 option B on GitLab, no fold change. Minus: GitLab pages keep their full length.
2. **Post service-only entries as internal notes at create.** Plus: hidden from guests and the public issue page; `fold` still reads them unchanged. Minus: hides nothing for Reporter+ readers, who are the board's users; a mixed visibility rule per entry kind.
3. **Resolve threads to fold them away.** Plus: GitLab collapses resolved threads in the UI. Minus: resolving changes `updated_at`, so `fold` ignores the entry; taskq entries are individual notes, not threads.

## Verdict

**Confirmed** for the #2016 A3 question as asked: the instance accepts internal notes at create and thread resolve on issues, and accepts no collapse. Resolve and edit both move `updated_at` without a system note, so neither can hide a taskq entry without `fold` ignoring it.

## Recommendation

Option 1: on GitLab, rely on the #1980 summary and keep taskq entries as plain, never-edited notes; do not use resolve or internal notes for entries.
