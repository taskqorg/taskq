# Windows-first fleet qualification

## Question

Which work can the existing Windows Codex host execute across the thirteen named projects, while preserving native acceptance and active attempts?

The owner's roughly 80 percent Windows preference is routing intent, not a measured acceptance threshold or a scheduler guarantee. This is a host qualification report, not authorization to change routing, permissions, credentials, capacity or services. No project rules are amended.

## Findings

### Evidence boundary

The private receipt set `taskq-2120-qualification` retains exact roots, source identities where readable, input hashes, board task bodies, commands, output and executable hashes. Private fleet paths and source locators are intentionally absent from this public report. Receipt filenames below identify observations within that set; they are not public download links.

The initial source inventory, post-registration probes and isolated executable checks are separate observations. A successful board read or `service check` does not prove that Git, a build, a native client or a provider works (R12). Failed and omitted checks remain explicit.

- **Registration:** `service-status-latest.json` records exactly thirteen expected NTFS roots, no registry error, and an observed CSGO attachment with received/applied/observed receipts. After the PM's final receipt, `service-status-final-receipt.json` verifies the same native service identity and thirteen roots. The earlier UNC attachment failure is superseded. The existing attachment-preflight task owns that defect; this report does not duplicate it.
- **Board/Codex:** after the final PM receipt, `after-receipt-<project>-board.json` records an exit-zero, complete board read for every row below. `final-<project>-readiness.json` independently records Codex CLI found, logged in and access granted for all thirteen. These are read-only checks of existing access, not new grants (R9).
- **Source:** `inventory.json` records usable Git for the TaskQ and AgentQ roots, both dirty. Ten other initial Windows roots refuse Git with `fatal: detected dubious ownership`: repository owner Administrators differs from the worker user. The new CSGO root has the same native Git refusal. No ownership, permission or `safe.directory` change was made. Source identities behind these refusals remain unknown.
- **Preservation:** the worker used its existing TaskQ worktree, an isolated AgentQ archive and OS temporary fixtures. It did not edit other project sources, move attempts, change registrations/labels/services, access production assets, make paid calls or use remote CSGO source (A4; R2/R9/R11).

### CSGO Windows/WSL route

The final registered root is NTFS; build/check execution is through Ubuntu with that root mounted under `/mnt/c`. The original Ubuntu checkout is retained. WSL Git resolves both checkouts to the same recorded commit. A full native-root WSL `git status` exceeded the 60-second inventory bound; cleanliness is unknown. Subsequent readback found no remaining Git process. No retry or cleanup of other work was attempted.

After the PM's final setup receipt, `csgo-native-final-host-info.json` records successful login-shell discovery of Cargo, Linux VRF, Windows Node/Chrome/Blender/media tools and a Windows-local archive. Earlier missing-Cargo/VRF observations are superseded. Reference identity remains unverified and the optional external viewer unregistered; discovery is not version/fidelity acceptance.

The original WSL route's `node --test v1/tools/chrome.test.mjs` passed two endpoint tests but failed native Chrome lifecycle cleanup after successful CDP connections: temporary profile removal returned `EPERM`. Its 36.20-second receipt retains the error. Exact fixture-profile process readback subsequently found zero matching Chrome processes; the failed temporary directory was retained. No unrelated process was stopped.

The final NTFS-root probe used the resolved Windows Node through the documented WSL login shell. It failed before any test ran: exit 126, `cannot execute binary file: Exec format error`. The documented Windows `cmd.exe /c ver` control failed identically. Binfmt readback was enabled but its `WSLInterop` registration was absent (`csgo-final-native-preflight.json`, `csgo-final-windows-control.json`, `csgo-final-binfmt.json`). Operator-owned interop repair is required before that route can run; no registration, restart or runtime fallback was attempted. This final failure supersedes any implication that earlier native Node execution qualified the current route.

Discovery and CDP startup do not prove GPU timing, WebGPU, game/source fidelity, input, media delivery or native Mac behavior. No game build, production asset generation, source import, capture or full gameplay acceptance was run. Those clauses remain intact (R12).

### Remaining prerequisites and board constraints

- Normal Git access must be restored by the PM/operator for the ten affected fleet roots, and the native CSGO service/worktree path must retain the approved WSL route. This worker made no trust exception or ownership change. Until then, an “exists” setup row is insufficient proof that a worker can prepare and publish source.
- CS declares Node 22/npm 10, Bun 1.3.13 and Deno 2.8.1. Only Node 24.5.0 is listed by the existing Node manager; installed npm is 11.5.1, and Bun/Deno are not found on PATH. Its pinned toolchain and isolated application/database fixtures need qualification before routing implementation checks there.
- Desiign's final setup check reports a private-plan publication gap. RepeatAI's publication-route probe reports unsupported/unknown. Successful board authentication does not resolve either; publication policy belongs to the PM, with exact-SHA CI where the contract permits private fallback.
- The worker read board snapshots and relevant task acceptance before recommendations. Existing runtime-adoption dependencies, PilotQ's A40 chain, AssetQ's generation/storage chain, explicit runtime/host pins and already-running Mac/Windows attempts remain unchanged. Mac housekeeping tasks are not Windows tasks merely because their code is portable (R2/R10/R11).
- ServerQ/Tight Linux host checks, native Mac client/service/UI cases, PilotQ's real release journeys, AgentQ native integrations, AssetQ provider/storage/restore/visual acceptance and RepeatAI listening/Android-device behavior remain required on qualified targets. This task spent nothing to exercise them.

## Options

1. **Windows-first for new portable slices.** Gain: use the observed board/Codex access and working Rust/Python routes. Cost: clear each checkout/toolchain prerequisite and keep target acceptance as a separate gate.
2. **Keep routing unchanged until broader qualification.** Gain: retain established target evidence while gaps are repaired. Cost: defer Windows throughput despite successful bounded execution.

Neither option migrates an active attempt, overrides an explicit pin or weakens native acceptance. The PM owns any subsequent registration/configuration/label work.

## Verdict

**Inconclusive for fleet-wide execution qualification.** All thirteen registered boards and existing Codex access passed; bounded Windows execution is demonstrated. Git ownership failures, unrun builds, the CSGO native cleanup failure and target/provider gaps prevent a claim that every project's ordinary implementation path is qualified. No percentage of future work was measured or guaranteed.

## Recommendation

Prefer Windows for newly admitted portable work after that project's concrete prerequisites pass. Retain genuine native/provider checks and all explicit task pins. Preserve active attempts and dependencies; do not apply a host-wide routing or capacity change from this report.
