# Reports: notice, understand and decide

## Question

How can an operator notice completed research while using the menu or Conversations, understand its proposal and decide without waiting for board reads?

## Findings

### Existing flow and cost

A report is a completed, trusted `taskq` research issue, or a docs proposal registered by `Report: docs/research/<N>.md` in its accepted result. Its Markdown and proposed tasks belong to the result SHA. It is separate from queue state. Review closes the research; the owner decides later unless another task needs the decision before close ([§7](../../taskq.md#7-worker-reviewer-publication), [Reports contract](../design/reports.md#contract-detail)).

At baseline `be3c20f3337d8db3e2c7bb555bbae777247c2bb2`:

| Encounter | Steps and calls before this change |
|---|---|
| Menu | Open menu → expand Reports → discover closed research/docs and read every candidate's comments → choose a report → read issue/comments/source and write/read back a read marker → scan the document → Make tasks, Later or Drop. No report in ordinary attention or the Conversations badge. |
| Conversations | Open Conversations → expand the separate Reports section → the same discovery and open calls. Reports were absent from the thread list. Returning restores the conversation draft. |
| CLI | `taskq reports --json` discovers all closed candidates, then reads their comments before paging. `taskq reports N --sha SHA --action open --json` revalidates the issue/comments, fetches the SHA source, and marks read. |
| PilotQ | The available TaskQ integration boundary is the same JSON CLI; it has no separate Reports implementation in this repository. PilotQ-side discovery, rendering and notification delivery were not verified. No external repository was changed. |

The task reported 65 seconds for 9 reports on macOS. A read-only Windows run of installed v4.6.47 reproduced **70,540 ms for 9 reports**. Its committed telemetry attributes **3,680.083 ms** to discovery and **66,493.939 ms** to **95 comment-list calls**, each **487.655–1,912.695 ms**. The command span was 70,235.503 ms; wall time also includes process startup/exit. The per-call observations are retained in [before-calls.json](../design/evidence/1940/before-calls.json). This run did not open, acknowledge or decide a live report.

### Implemented flow

The [Reports contract](../design/reports.md#contract-detail) was edited before implementation under R13. The existing root §7 link continues to own that contract detail; its review-close/owner-later lifecycle and R6 queue counts are unchanged.

1. The service collects report identities, trusted markers, exact-SHA content and validated proposals in a separate background worker. Its ordinary pass schedules collection; close events invalidate it without waiting for the next due collection. Supervision continues during slow board reads.
2. The pushed projection supplies unread menu attention, the Conversations new-item count and report rows in the thread list. The operator can open a report directly from either workplace.
3. List and card render locally. Question, Recommendation and Proposed tasks lead. Full report expands with one action. Reading sends a separate asynchronous acknowledgement; an unconfirmed read stays unread.
4. Make tasks, Later and Drop remain direct actions. They validate the displayed SHA against current board state, retain readback and partial receipts, and never start proposed tasks. Returning preserves the conversation and draft.

Unchanged projections reuse comments only after their update second has settled on board time. SHA content is immutable. Missing, stale, failed or corrupt collection remains unknown with its reason; previous useful rows survive failed refreshes. A source failure belongs to its report, rather than falsely emptying the list (R1/R12).

Receipt overlays contain marker state, not source or close order. They are scoped by SHA and retired once the collected comment revision catches up. Regression cases cover a delayed old-SHA acknowledgement, partial Make, and a newer remote reservation.

### Verification and limits

| Case | Evidence |
|---|---|
| Notice without opening Reports | `tests/reports.browser.cjs`: pushed report appears in Conversations and increments the menu badge before any Reports request. |
| Instant local list/card | `tests/reports-cache.test.cjs`: failed before with `opening Reports must not request a board list`; passes with content available in the opening frame. `tests/reports_cli.rs` checks the real CLI without board credentials. |
| Fresh/stale/unknown and close refresh | `reports::tests`: collected content, TTL boundary, corrupt/missing cache, per-report source failure, same-second markers, and close-event scheduling. |
| Source-bound decisions | Existing Rust decision/create-claim tests retained; component tests retain partial/unknown receipts, Later, Make and Drop. Review reproductions for close order and old-SHA receipts failed before their fixes and pass afterward. |
| Readable layout | Browser instrument covers Menu/Conversations, dark/light, 350/940 px and 16/20 px: 16 cells. Native evidence and final gate outcomes are recorded in the [acceptance evidence](../design/evidence/1940/README.md). |

Telemetry separates background `reports.collect.list`, `.comments` and `.source` from `reports.list.cached` and `reports.open.cached`. UI operations use `js.reports.view.toggle`, `.open` and `.section`, so reading cost remains observable without a board request. Timings and screenshots qualify only the named candidate/platform; source checks do not qualify production or PilotQ delivery (R12).

## Options

1. **Service-collected cards.** Plus: decisions arrive in the existing workplace and reading makes no board request. Minus: cold collection remains background work and its age must be explicit. This implements A3–A6.
2. **Faster on-demand lists.** Plus: less background work. Minus: opening still waits for board access and discovery still requires entering Reports; it does not meet A3/A5.

## Recommendation

Use the service-collected flow required by this task. Preserve SHA-bound decision markers, held-only task creation and explicit unknown states. Keep full findings behind one action so the decision remains readable at first open. No additional product decision is deferred by this implementation.
