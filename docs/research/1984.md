# csgo and cs GitLab issue pages, measured with the #1980 method

## Question

[#1980](https://github.com/taskqorg/taskq/issues/1980) measured 38 GitHub issues and left the GitLab boards csgo and cs unread: the Windows host has no GitLab access ([docs/research/1980.md](https://github.com/taskqorg/taskq/blob/taskq-1980/docs/research/1980.md), PR #1982). Do GitLab issue pages look like the GitHub ones, and does the summary comment alone (option B) bring each issue under 30 s there?

**Verdict.** Yes on cs, almost on csgo. Under the #1980 reading model, option B reads 14 of 15 GitLab task issues under 30 s (cs 7/7, median 12.9 s; csgo 7/8, median 16.3 s), against 7 of 15 today (cs median 29.4 s, csgo 42.5 s). The one miss, csgo#323, fails only because its summary lists 23 file links; a Files line capped at three labels plus a count brings it to about 24 s. Files on csgo already live in `result` and `ask` comments as GitLab uploads, which #1980 found nowhere on GitHub. As in #1980, the times are a model, not a timed reader (R12).

## Findings

### Sample and method (A1, A2)

17 real issues were read in full through the GitLab API from the Mac host on 2026-10-31: 15 task issues (10 closed, 3 open, 2 closed held) and 2 heartbeat issues, csgo (`alex/csgo`) and cs (`gradus/cyprusbz`) on gitlab.ufobe.com; 0 to 184 comments. Totals: **679 user comments, 257,048 characters**, plus 6,190 system notes. The script is [1984-measure.py](1984-measure.py); it reads GitLab with a read token and GitHub with `gh`.

The method is #1980's, applied unchanged where GitLab allows:

- Line classes as in #1980: `taskq:` header, `op-id:`, `revision:`, `<!-- taskq` and every line of a service-only kind are **machine**; `To answer:` is **boilerplate**; `Checks:`, `delivery`, `merged`/`enqueued` lines are **both**; the rest is **human**. "Human lines" counts human and both.
- Read now: 2 s for labels; 0.6 s per comment skimmed up from the bottom to the latest outcome (`result`, `ask`, `publish`, `close`); its human and both lines at 25 characters per second; files outside that comment cost one skim of the whole thread. Without an outcome the reader reads the `## Goal` section; a heartbeat, its first 190 characters.
- Read B (summary only): 2 s for labels plus the summary at 25 characters per second. The summary is a 40-character state line, the latest outcome's `Changed:` and `Open:` lines (for an `ask`: `Problem:` and the options), 60 characters for a decisions line when the thread has an `answer` or `steer`, and a 40-character label per file link.

Two GitLab additions, both stated so they can be reversed:

- **Legacy entries.** Older issues carry v3 entries such as `**take** · codex:<id>`, which the #1980 rule reads as human because they lack `taskq:`. They are classified by kind: `take`, `beat`, `shown`, `spawn`, `run`, `adopt`, `runtime`, `reserve`, `launch`, `ready`, `waiting`, `deps`, `edit` are service-only; `result`, `ask`, `close` and `reject` are outcomes; `problem`, `answer`, `later`, `requeue`, `release` keep their text as human. A legacy outcome without `Changed:`/`Open:` contributes its first two human lines (160 characters each) to the summary. With the literal #1980 rule csgo shows 140 machine lines instead of 398, and csgo#255 reads 66.9 s under B instead of 12.4 s.
- **System notes** (description edits, mentions, assignments) are counted but not read: #1980 did not count GitHub timeline events either.

Calibration: the same script, run on seven of #1980's GitHub issues today, reproduces its published read-now times within 0.3 s where the thread has an outcome and has not changed since.

### What the GitLab sample shows

- **Same shape as GitHub on v4 issues.** cs is almost all v4: 69% service-only comments and 29% technical characters, close to GitHub's 66% and 20%. csgo's older threads are mostly v3 worker notes (`problem` and `beat`, 116 comments), so its technical share looks lower (12%) and its human text is long.
- **Long threads are slow for the same reason.** The latest outcome sits under its trail. cs#528 (open, 184 comments) holds 91 `spawn` entries for 22 `accepted`: 69 spawns that never ran, each a full comment block. That is admission churn on the board, a separate issue from page format.
- **Files live in outcome comments on csgo.** csgo has 28 file links, all GitLab uploads (`/uploads/`): 14 in `ask` comments (11 zip), 9 in `result` comments (7 zip), 5 in plain comments; none in issue bodies. cs has none. So #1980's "files are rare and never in a result" holds for cs and GitHub, not for csgo; the GitLab upload route already carries zips at decision time.
- **Many files make the summary long.** csgo#323's summary under B lists 23 file labels (920 characters, 37 s of the 46.8 s). With three labels plus "and 20 more", it reads in about 24 s.
- **Results live in the result comment plus an MR.** 10 of 15 task issues have a `result` (v3 or v4) and an MR or report; 3 have none (two held drafts closed unstarted, csgo#255 closed on a v3 `answer`); 2 are still in work.
- **Heartbeat edits flood the GitLab timeline.** Every in-place edit of a heartbeat body adds a "changed the description" system note: 5,733 on csgo#356, 285 on cs#539. Nobody reads these pages, but GitLab keeps every version. Older v3 task issues show the same from state kept in the description (43 on csgo#323); v4 task issues do not edit the description.
- **Nothing was edited in place**: 0 of 679 comments have `updated_at` after `created_at`. Whether editing a note (not the description) adds a system note was not observed in this sample (unknown).

## Options

The board formats are #1980's; this report only measures them on GitLab. Option C (collapse) does not exist on GitLab, so only A and B apply.

### B as proposed in #1980

- Pro: meets the 30 s part on cs (7/7) and on 7 of 8 csgo issues with no GitLab-specific work.
- Con: misses csgo#323 (46.8 s) because the Files line grows with every upload.
- Con: technical text on the page is unchanged on GitLab (no collapse), as #1980 already states.

### B with a capped Files line

Same as B, but the summary lists at most three file labels, newest outcome first, then `and N more` linking the comment that holds them.

- Pro: every sampled GitLab issue reads under 30 s in the model (csgo#323 about 24 s).
- Pro: the same rule keeps GitHub summaries bounded when workers start using `--image` and archives.
- Con: older files are one click away instead of zero.

### B written to the issue description on GitLab

Rejected: each edit adds a system note and a stored description version, as the heartbeat issues show (5,733 on one issue). The summary must be a note, edited in place.

## Recommendation

1. Keep #1980's answer for GitLab: option B is enough for the 30 s part on csgo and cs; the size part stays unmet there (no collapse).
2. When the summary-comment task is filed, add two acceptance points: the Files line shows at most three labels plus a count, and on GitLab the summary is a note, never the issue description.
3. Before that task, check whether editing a GitLab note adds a system note or changes what `fold` reads; add it to #1980's qualification task (its GitLab acceptance item already lists note options).
4. Track the cs#528 spawn churn (69 unaccepted spawns) separately from page format; it inflates pages on both boards.
