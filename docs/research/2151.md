## Findings and evidence

[Original output](2151/observed.json) records the earlier Mac worker run on Darwin 27.2.0/macOS 27.2. [Coalition output](2151/coalition-observed.json) records this continuation on the same OS. Both omit private paths, process IDs, coalition IDs, account data and release keys. [Instrument source](2151/scope_probe.py) contains assert-based failure checks and private-pipe teardown; no installed client or production process is controlled. Each wait has a 10-second deadline. These are process-fixture observations, not qualification of a protected native launch (R8/R12).

1. `EVFILT_PROC` accepts `NOTE_FORK|NOTE_EXIT`. Adding `NOTE_TRACK` returns `ENOTSUP (45)`. The retained XNU source explicitly rejects `NOTE_TRACK`, `NOTE_TRACKERR` and `NOTE_CHILD`; using FreeBSD child-tracking semantics on this Mac is invalid.
2. In both `setsid` and `posix_spawn(..., setsid=True)` traces, the root is reaped and its original process group is absent while the exact owned descendant remains alive in another group/session. Both descendants finish through their private controller pipe. These executable counterexamples refute root-only and unconstrained-group completion. They do not establish that a runtime fix passed.
3. Denying the `setsid` and `setpgid` syscalls alone is insufficient. In the retained XNU `posix_spawn` source, `POSIX_SPAWN_SETPGROUP` calls `setpgid` internally, and `POSIX_SPAWN_SETSID` calls `setsid_internal`. Those calls do not enter either syscall. The instrument proves ordinary spawn detachment; the combined deny-profile bypass remains source evidence, not a qualified native observation.
4. CoreQ's locked `v0.18.0` source is `e84761cdab43723b871a42b3021e9c39afcd9484`. Its identity/termination APIs are suitable for PID-reuse fencing and exact cancellation. Its contract explicitly says identity is not descendant or external-effect proof. Bounded exchange/reaper cleanup owns the direct child and writer; it does not supply a recoverable Mac descendant scope. Checked CoreQ main `55ec4176372b7832790c6d6e59d1b149b79e4dfb` has the same process source blob and no separate scope/process module in its complete tree. No dependency pin changed.
5. Direct coalition creation requires privilege, but that does not exclude a user launchd job as a source of an isolated coalition. Apple's pinned [coalition documentation](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/doc/observability/coalitions.md) says membership survives fork/exec/posix_spawn, cannot change after process creation, and represents a launchd job. Coalition IDs are monotonically assigned and not reused within that kernel lifetime. A loaded service may reuse its coalition across restarts, so coalition identity alone is not a one-operation dispatch fence. No direct coalition create, entitlement request, privileged helper or grant change was attempted. The approved launchd submission is recorded in finding 11.
6. Inherited Seatbelt markers plus a process census are an investigation lead, not completion proof. A PID census is not an immutable birth/exit journal: the reviewed `proc_iterate` first collects PIDs, unlocks, then finds them for callbacks. Fork, exit and PID reuse can race the later reads. A same-user operation can also match another sandbox's deny rule. No marker scanner, global process killer or polling-based release is proposed for adoption.
7. The earlier narrowing probe returned `sandbox_init: -1`, `Operation not permitted`. Its enforcement checks remain **sandbox-blocked**, not PASS. The current instrument does not rerun that rejected candidate. No retry with different permissions, attempt stripping or slot refusal bypass occurred. The cause is not attributed to TCC.
8. The read-only coalition wrapper is exported and works inside this worker. The pinned 40-byte `PROC_PIDCOALITIONINFO` layout yields the same resource coalition for the controller and each exact live detached descendant. Both ordinary fork/setsid and posix_spawn/setsid traces preserve it after the root is reaped and its original group disappears. Reading the first 16 bytes of `coalition_resource_usage` returns success; surrounding canaries remain unchanged, started/exited counters are monotonic, and controlled starts/exits increase them. Querying invalid ID 0 returns `-1/ESRCH (3)`, with no filled counters. No absent ID is interpreted as completion.
9. The counter source reads `task_count` and `dead_task_count` under the same coalition lock. It therefore offers a kernel accounting source independent of process-group/session escape. This run uses the worker's shared coalition: it proves read availability and inheritance, **not operation isolation or final emptiness**. It cannot release any original slot. Exec may affect task accounting; counter deltas are not asserted to equal PID/fork counts.
10. Coalition membership covers inherited kernel tasks, not arbitrary work delegated to launchd, XPC services or external daemons. Apple's documentation explicitly puts app extensions in separate resource coalitions. A future whole-operation completion receipt must also close dispatch/input routes and retain AssetQ's external-effect/tool-completion responsibility (A8); counter equality cannot attest remote/external effects.

## Integration constraints if the experiment succeeds

Do not add a second resolver or scheduler. Preparation must use the existing resolver and resource store, bind the canonical registered project and actual consumer PID/start/boot, and return the current revision/account, approver, image/hash/home and generated profile hash independently of launch (A1). Launch compares immutable preparation and fresh authority under the existing grant lock before any native input, including after job dispatch (A2).

A product job would run the trusted adapter with the existing resolved Workspace profile and enforcement readback, not this standalone Python fixture. The launchd path does not inherit the caller's Seatbelt; it must establish and verify the required boundary itself. The private transport must preserve native stdio, account/home/model/effort and immutable caller/slot incarnation. No native input or descendant work is released before durable native/coalition binding and independent authority readback.

Before dispatch, durably consume the original launch operation in the existing host store. Before releasing the native gate, bind boot, exact kernel incarnation, resource coalition, immutable artifact/profile and exact job generation. A controller crash before binding cannot justify a second dispatch. Recovery may inspect/reconcile only that original generation; if it cannot recover the original scope it returns unknown and keeps occupancy. A loaded job can reuse a coalition, so no duplicate/reordered observation may reopen dispatch or manufacture a fresh operation.

Completion must seal further native input and all dispatcher routes before relying on same-boot kernel accounting. A new observation cannot erase an older unresolved launch or external effect. Coalition absence is unknown in this proposal. Preserve the original slot key/payload/effect identity; only verified whole-operation completion followed by acknowledged original authenticated slot release frees occupancy (A3/A4). The experiment has no slot release path.

A5 still needs executable models for prepare/launch drift, all pre/post-intent and pre/post-binding crash windows, a leaf surviving root/controller loss, PID reuse, reordered/duplicate reads, no replay, dispatch closure and recovery of the same operation. Native scope qualification additionally needs exec/fork/double-fork/spawn inheritance, exact build/ABI bounds, controller interruption with a live leaf, unsupported/missing readback and nonvacuous unrelated-sentinel protection. Counters do not replace these guards.

Only after the reviewed product implementation and green merge-result CI may PM qualify the added preparation/completion/recovery paths under the existing Mac Workspace authority (A6). Reuse the AssetQ PASS; do not replay native boundary/crate/model work. Private authority/host receipts remain off public boards.
