# Runtime qualification matrix

Verify supported TaskQ capabilities through observable outcomes. [R9, R12 and runtime contract](../taskq.md) own policy; [specq verification](https://github.com/taskqorg/specq/blob/main/engineering/verification.md) owns test method. This matrix does not grant access or turn pending permission designs into shipped behavior.

## Short dependency commands

Operator inspection commands and tray status/selftest/setup exchanges use the shared CoreQ executor through `platform::output`. Complete nonzero output remains available for receipt parsing; spawn, timeout, capacity and incomplete output return an explicit unknown with the original native error. Inspection/status/selftest use30s; board mutation/setup use60s. The process trace keeps the failure even when a caller handles it. An OS opener records submission only; it does not claim that the target window appeared. Interactive pickers and resource terminals have their own human-driven lifetime and are not short exchanges.

## Native observation budget (contract detail)

Each normal or reduced project pass admits native recovery, liveness and cancellation observations within20s of native work. A native dependency call uses the remaining deadline, up to its existing per-call bound. Stop admitting another observation when the budget expires; retain its handle/reservation and report `unknown` with a named deferred-observation reason. Rotate the next owned execution and cold-recovery candidate so a slow first item cannot starve the rest. This is scheduling state in the existing service, never a new task journal or an exit proof. A deferred observation cannot authorize replacement. Explicit emergency control retains its existing owned cancellation path.

The next poll is due from pass start, subtracting work time rather than adding a full sleep after it. The service continues to publish aggregate status on its60s target; unavailable board access remains stale/unknown. Budgeting cannot make kernel/filesystem calls or OS scheduling hard real-time, and installed cadence still requires native load qualification. A freshly published host heartbeat does not turn a deferred execution observation healthy.

## Execution policy

One bounded live scenario covers each applicable runtime, role and continuation. Run it when that integration, permission configuration or client version changes, not on every commit or documentation edit. Record exact versions, effective permissions, initial state, actions, observed output and remaining gaps. A prior pass qualifies only its recorded configuration.

Deterministic checks follow [specq test classes](https://github.com/taskqorg/specq/blob/main/engineering/verification.md#test-classes). TaskQ chains: state transitions, duplicate/stale writes, admission, publication and preservation of active work. A constructor/argument-string check is not live permission or behavior proof.

## Cleanup after a run

Every qualification or canary run (#2048) names the native objects it creates with a `Qualification` or `Canary` marker together with `TaskQ`, `CoreQ`, `Codex` or `Claude` (for example `TaskQ-Qualification-<id>`), keeps its scratch in an OS-temp folder named `taskq-<purpose>-<id>`, and removes its Scheduled Tasks, user units, launchd jobs and scratch folders after the run, failed runs included; the result names any object it had to leave. The [host doctor](design/host-service.md#host-doctor) removes leftovers of interrupted runs after a day. Fixtures outside the OS temp dir and `<install>` (for example `~/.local/share/taskq-*` or `~/taskq-*`) are outside the service's folders (taskq.md § 8); the run that made them removes them.

## Evidence reuse and invalidation (R12)

Keep model (pure transitions), adapter (integration with substitutes), process (real executable/IPC) and native-platform (actual client/OS/service) proof distinct. A fake board or native manager cannot qualify the installed manager; a release hash, heartbeat, result or stop acknowledgment cannot prove native execution exit.

For each affected cell record candidate SHA/artifact hash, client and OS version, effective grant/enforcement, fixture/input identity, command, result and native receipt. Reuse only unchanged tested sources/artifacts, checks, dependencies and environment. Mutable heartbeat/status observations need a fresh dated read; the historical index is not current health.

| Cancellation, crash/recovery, exit observation, update/drain or ownership handover | Affected native lifecycle/recovery rows and relevant A–F cases; preserve active owned work | Existing execution/service chains and installer process instrument; substituted manager remains process proof |

Run the affected check during development; freeze and run the selected merge gate once. New and previously failing checks remain selected. Validate the selector at the full-run triggers in [testing.md](testing.md); do not add another selector or harness. Release/deployment adds affected native/client/lifecycle/outage checks before exposure, not a fresh full matrix for unchanged cells. The A–G cases below are the reusable scenario recipe: choose the affected steps rather than replaying every role on every platform.

Paid/model probes require explicit owner approval under §7 and the existing fixture/grant boundary (R9). A rerun trigger does not grant that approval. Missing approval or prerequisites leaves the native claim unknown; no automatic Full fallback, login, model/effort change or production mutation. This documentation task performs no paid probe or other-host operation.

## Bounded live scenario

1. Record candidate/client/OS and effective configuration. Use only an isolated fixture and an explicitly owned test task; leave existing jobs, grants and global configuration untouched.
2. Start worker with an ambiguous in-memory pause fixture. It must ask before editing. Answer keep-active, resume the same session, verify exact canonical rule bodies in both actual inputs, and inspect tool output for expected baseline failure and corrected active/repeat/empty success.
3. Start independent reviewer, execute the published fixture, inspect its actual rule input, ask before acceptance, resume the same reviewer and inspect the continuation before closing. A self-report or handshake is insufficient.
4. For each changed permission boundary, controller creates disposable canaries with unknown content, agent attempts the approved positive/negative operations, controller checks actual results and unchanged forbidden targets. Use native denied operations, not a request to obey prose. Never inspect real private files or credentials. Report allowed reads separately from denied writes.
5. For operator, inspect actual tools and execute only authorized fixture read/write/check. Require actual read/write/check results and same native session on continuation; disabling that runtime must prevent continuation without fallback. Proposed JSON still passes the existing validation/confirmation/readback chain.
6. For lifecycle changes, preserve an owned long-running fixture across pause/update; distinguish process exit, app-turn exit, lease and board state. Do not cancel unrelated work to manufacture an idle host.

## Runtime adapters

Contract detail of `taskq.md` § 9 (R8, R13). Each agent runtime (`claude`, `codex`, `antigravity`, `codex-app`) is one `crate::runtime::Adapter` in `src/runtime.rs`, found by `crate::runtime::of(name)`.

- The adapter owns everything that differs by runtime: launch and resume, the command line, policy and sandbox arguments, the session link, process identity, auth and login hints.
- The runtime module keeps that code; other modules ask the adapter (binary, client name, home, CLI child, Remote Control session, app turn, Codex family, setup access) and never compare runtime names.
- `crate::runtime::RUNTIMES` is the only runtime list; setup runtimes, profiles and the service derive from it.
- Owner sessions (`service setup`, tray AI requests, `retro`) launch, link and get Claude trust through `crate::runtime::owner`; `src/setup.rs` keeps only the request state machine.
- `crate::runtime::session_link` is the only session-link resolver and `crate::runtime::open_link` the only opener; `thread_url`, `plain_thread`, `remote_url` and `link_ok` are the only link builder and checks.
- Kid adoption (`crate::runtime::adopt`), handover waits (`handover_waits`), the worker default runtime (`preferred`) and the Claude process lookup go through the adapter.
- Allowed exceptions: the sandbox files (`src/linux_sandbox.rs`, `src/windows_sandbox*`) and tests.
- `scripts/check.py` refuses, anywhere else in non-test Rust including `src/main.rs`, a runtime name literal and the native names `claude.exe`, `.claude.json`, `CODEX_HOME` and `CODEX_THREAD_ID`.
- New runtime policy changes update the golden admission traces; existing pin, grant and ownership protections remain binding.

### AgentQ runtime

AgentQ owns shared native runtime mechanics through `agentq_runtime::agent`, pinned to published source `9be735b5a82f5a526cd8b1757196387956c3b5d0` (`agentq-runtime` 0.1.0). CoreQ retains process, telemetry, update and host primitives; its frozen agent compatibility API remains available to older consumers. TaskQ owns board state, attempts, capacity, accounts, permissions, model/effort, focus, briefs, tool grants and protected recovery persistence (R3/R8/R9/R13). Worker, reviewer and owner/operator start/resume paths use the same shared API, including Claude background/Remote Control and Codex app. Native identities, checkpoints and usage attribution retain their existing meaning.

Optimizer installation is optional. A launch inherits `AGENTQ_OPTIMIZATION=inherit|off|on` (absent: inherit); invalid intent refuses before submission. AgentQ resolves the account's actual client home and optional installation read-only. Each launch reports intent, effective on/off/unknown and reason in the private service/launch diagnostic. `on` never enables a disabled integration; `off` applies only to the child/provider request. Configuration at launch never proves actual compression. No host/global configuration is written; app handshakes and queued turns remain separate observations. Claude starts merge only optimizer environment keys into existing per-session settings; a background resume passes no flags and keeps the optimizer keys saved with the job (#2262: Claude starts a copy job with a new conversation when a resume passes any flag, so a settings overlay broke the same-session rule above). Permission/model settings remain native-owned. Active sessions remain unchanged.

Forward: adopt the immutable dependency and run the selected Windows/portable gate and existing deterministic client/recovery/contract checks; publication requires green merge-result CI (R12). Ordinary installation uses only the merged release. Rollback selects the previous immutable TaskQ build with CoreQ `e84761cdab43723b871a42b3021e9c39afcd9484`; session IDs, checkpoint formats and observation IDs remain compatible, with no replay or policy change. Preserve the predecessor's qualification receipts. Live Mac and Claude (capacity 0) Q1/Q6/Q15 and live usage baseline remain explicitly unverified until their authorized native qualification; source/fake-client checks do not qualify them.

### Antigravity boundary

The TaskQ adapter resolves `agy` through `user_bin_path`, preserving service PATH precedence and adding `<home>/.local/bin`, and uses AgentQ command/session/usage/terminal-event mechanics. Native `agentapi` background-server launches are not qualified for TaskQ and are not selected as a substitute for `agy`. Command construction targets agy 1.4.12; stream transport and admission checks are adapter/process evidence only. Actual Antigravity subscription work, reviewer continuation, permissions and each supported OS need native qualification (R12). No minimum client version is qualified yet; tools report this explicitly.

## Rule delivery: contract detail

**Rule delivery (R13).** Every worker, reviewer, operator and PM start, resume and compaction receives the current project contract and ten mandatory core bodies from one freshly selected specq revision, before the task text. Registered `taskq.json` repository basename selects `<repository-name>.md` (nested forge namespaces supported), read at the freshly fetched `origin/main` commit the worker branch starts from and named with it in the header; a root without Git or `origin/main` reads `<root>/<repository-name>.md`; a contract absent at that commit refuses or falls back as below; missing, unreadable, invalid UTF-8 or empty non-TaskQ contracts refuse launch. Only unregistered setup roots and registered TaskQ may use the release TaskQ fallback. The header names revision, cache, project contract, precedence (project overrides shared), evidence requirement and the separate TaskQ command-contract reference. Known other shared rules and project `docs/` remain indexed by path/heading for demand loading. Continuation bodies supersede earlier versions; an index alone is insufficient after a change or compaction. This retains core-plus-index delivery but repeats mandatory bodies, so live context/compression cost remains to be qualified. The complete payload stays within128KiB; invalid/unavailable rules or documents refuse launch. `taskq rules size` measures the continuation payload with the working-tree contract a branch proposes and prints size, cap and headroom; over the cap it exits nonzero, so project CI fails before merge (#1946). A start over the cap is a deterministic refusal: one attempt ask naming size and contract file, no gone retries; its reply starts a fresh attempt (a fresh reviewer keeps the result), since a never-started attempt has no session to resume. Claude background and Codex App receive only a short reference to an immutable UTF-8 file in `<root>/.taskq/inputs/<uuid>.txt`, requiring a complete read before work and reporting read/truncation failure. Content never enters their native launch/queue arguments. Each adapter holds the existing input lock until the turn ends; hourly retention keeps the newest50 plus locked files. Inputs are rebuildable caches, never task state. Codex CLI uses stdin. Claude new sessions install the SessionStart compact hook; resumes preserve that native conversation/hook. PM hook: `taskq rules pm start|compact`. Shared source is the published specq `refs/heads/main`, resolved from bounded HTTPS Git protocol-v0 reference advertisements without a REST request per turn. Before each rule payload, accept a valid local source observation only while its age is below60s; stale, future-dated, missing or invalid observations require a successful refresh. Failed/ambiguous/malformed discovery refuses launch without a release-pin fallback. Capture one selected40hex SHA for the entire payload, cache namespace, file URLs, metadata and header, so a moving branch cannot mix bodies. Cache observations record device UTC seconds; a backwards clock invalidates a future observation. For each selected SHA, fetch/cache the recursive Git tree once through the GitHub Git-data API. Refuse truncated/oversized/invalid trees, duplicate or unsafe portable paths, nonregular eligible Markdown entries and missing mandatory core files. Discover other Markdown files dynamically (excluding README/AGENTS/SECURITY and scripts/vendor/audits/docs). Verify each body against its Git blob SHA from that tree before delivery; no mixed-revision or unchecked fallback. Keep the ten mandatory paths as the compatibility contract: a renamed/removed mandatory file refuses launch. New eligible indexed files need no TaskQ rebuild. Tree cache uses the same revision/path/SHA256 checks as bodies. Each cached shared file has metadata binding revision, relative path and SHA-256 of its UTF-8 body. Missing, malformed or mismatched metadata/content refetches the immutable HTTPS URL; unavailable repair refuses launch. Git blob checks also reject a changed body with coherently rewritten body metadata. Editable source/tree caches are not an authenticity boundary against an actor able to rewrite the whole cache. Reads/fetched bodies are limited to128KiB. Concurrent cache publication uses unique staging names and atomic replacement; interrupted pairs are invalidated/refetched. Delivery logs are transport evidence, not proof that a model applied the rules; real behavioral canaries remain required.

### Execution ownership

R1/R2/R8/R11/R12/R13: execution safety is separate from task state. This accepted recovery contract replaces timeout-only failover. Its implementation and cutover are incomplete in this draft; do not release the queue from specification or local-test evidence alone.

- One task can have many turns within an attempt. Identify each external submission separately by task, accepted attempt and requested inbox cursor. A result, answer, requeue, cancellation request or expired heartbeat never proves that submission stopped.
- Commit attributable board intent before external submission; read it back before proceeding. An accepted initial spawn can be that intent. Continuations need their own intent, tied to the requested inbox boundary; coalesced inbox entries do not create several executions. An uncertain intent write is discovered by its stable operation identity, never blindly reposted or executed.
- Record release only after observed native completion/termination or proven no-start. The release identifies its exact execution and accepted attempt, including an attempt replaced meanwhile. Duplicate release is idempotent; stale, malformed, foreign or unmatched release changes nothing. Release is an execution observation, not a new task result or authorization.
- Every host checks unresolved execution intents before a new worker, reviewer or continuation. This includes prior attempts after result/requeue and user cancellation. Board fencing rejects late task writes but cannot cancel arbitrary external effects. Missing heartbeat means unavailable owner, not permission to duplicate work.
- Reuse board intent and native identity/state/logs first. Extend an existing bounded record only for recovery data shown missing in the [adapter matrix](#adapter-recovery-matrix). Identity enables readback; it proves neither acceptance nor termination. A marker found after a crash never proves no-start. Preserve required unresolved identities across update/pruning and refuse admission if their protected preparation fails. No independent ownership journal, task database, prompt copy or permission grant.
- Reconcile interrupted submission by the recorded native identity and original input boundary. Never infer ownership from process name, a reused PID, another conversation's completion or launcher exit. An uncertain external side effect needs its own reconciliation even after process exit.
- A fresh owner can resume supervision of a proven identity. Missing/corrupt identity, unreachable runtime and ambiguous acknowledgment stay unknown, retaining occupied capacity and blocking replacement. Resume does not clear this fence. Expose task/attempt, last observation, unresolved boundary and required recovery action.
- New safe retries remain automatic after confirmed no-start/exit and ordinary task policy. A persistently unavailable host leaves its affected tasks waiting until verified recovery; elapsed time is not proof. Preserve worktrees, sessions and logs.
- Lost spawn (#1879): every native start writes the attempt log's rules line before its native call, so an initial spawn on its owner host with no `accepted`, no child, no held launch and no attempt log is a definite pre-submission failure, not a post-crash marker. One ttl after the spawn the pass releases it `no-start` and posts `gone` naming `lost spawn`; until then its row waits as `Waiting for the agent to accept input`. An existing attempt log or a continuation stays unknown. A lost spawn that is no longer the task's live attempt (requeued or parked, #1886) and has no hand-in of its own waits on nothing: the next pass of its host, a retired host booted once included, releases it `no-start` at once with op id `release-<id>`, and another host may claim. While an execution stays unknown, `execution_wait` names the step: `reboot <host> to prove exit` on its host, `start the taskq service on <host> once, after a reboot if the run had started` elsewhere.
- Lost resume (#2272): a live Claude handle of a resumed conversation (an answer's continuation) whose job row names no process, whose recorded process (if any) is gone and whose transcript holds no readback of its input is a native observation that the input was never taken. Until 300 s after launch its execution reads unknown with `no native process after resume: ... input not accepted <s> s after launch` (`Waiting for the agent to accept input`); then the handle ends: the pass releases it `exit` with that text and posts `gone` naming it, so the task returns to `ready` under § 2 row 10 instead of the R6 input fence. A hand-in after the execution's intent, a transcript readback or a live process keeps the ordinary path; a recovered observer (no launch time) and every other unaccepted exit keep the fence.
- Cutover requires every service on the board to support the execution-release protocol. Old services may expire an attempt even under admission hold, so a local capability label or hold does not make mixed-version recovery safe. Drain/stop incompatible services before release, reconcile historical unresolved attempts and preserve rollback evidence. Never invent historical release records from age, task closure or owner acceptance. Cutover records attributable native/operator verification evidence and refuses rollback below a compatible execution-protocol version.

Status exposes unresolved execution id, host and termination reason in `execution_wait` per snapshot row, plus host `execution_waits`. Task state and counts remain board-derived. Native launcher I/O is bounded: Claude background exchange30s; Codex open/queue10s each. Pre-submission failures may release no-start; timeout, nonzero launcher exit and post-submission read errors remain uncertain, except a Claude background refusal: a nonzero exit code with no background ID and a non-empty stderr is a confirmed no-start, and the saved `claude.launch` record of an unresolved execution reconciles the same way (a record without `status` counts as nonzero; a signal or a printed ID stays unknown).

Acceptance chains: disconnected owner with a running child; crash before/after intent and native submission; lost acknowledgment; same-attempt inbox continuation; worker result before process exit; cross-host requeue; cancellation refusal; corrupt ownership metadata; duplicate/stale release; confirmed no-start/exit permitting progress; incompatible service cutover refusal. Model, process and installed-host evidence remain separate.

Execution observations share the trusted immutable comment log but do not change task state or its revision. An accepted `spawn` is its first intent: execution id and initial intent cursor equal the spawn id. `taskq: executing <inbox cursor> attempt <A>` records a continuation only for the current doing/review attempt, after all earlier executions released, at its newest accepted inbox entry. That comment id is the new execution id.

`taskq: accepted <execution id> attempt <A>` records attributable native acceptance of that execution's exact input. It advances delivery through that execution's cursor; intent, process creation, task result and native exit do not. An observation can arrive after exit or task replacement, but cannot affect another execution. A prior `no-start` contradicts acceptance and cannot be overwritten. A released execution with unknown acceptance requires reconciliation before replaying its input, including inside a later cumulative input.

`taskq: released <execution id> exit|no-start attempt <A>` releases that exact accepted intent, including after its attempt is replaced. The first release proof is immutable; no-start is rejected once native acceptance is known. Release cannot target a future intent. A continuation cursor may repeat only when the prior intent for it has confirmed no-start; all earlier inputs must be accepted or confirmed no-start. Retry uses a new execution id and operation id `execute-<attempt>-<cursor>-<previous execution id>`; no-start does not consume the cursor. A new cursor must equal the newest accepted inbox entry. Two no-start failures for a continuation cursor ask the owner while retaining the inbox and session. An answer permits another bounded cycle; a native-identity lookup failure preserves the input and exposes a recovery action.

Edited, duplicate-op and malformed observations are ignored; absence of release preserves the fence. Services use deterministic operation ids (`accept-<execution>` and `release-<execution>`) and read back observations before updating caches. Retry an observation after a lost response, never the underlying native call. Historical accepted spawns without release remain unresolved until native proof; age, task state, task closure, legacy `gone` and owner acceptance never synthesize release.

Boot proof (#1386): a host boot strictly later than an execution's intent comment proves that every process of that execution ended on that host. Each pass the owning host (execution `host` equal to this host, no live local handle) reads the OS boot time once: macOS `sysctl kern.boottime`, Linux `/proc/stat` `btime`, Windows wall clock minus `GetTickCount64`. When boot is strictly later than the intent comment's board `created_at`, it writes `taskq: released <execution> exit attempt <A>` with the text line `host booted <UTC> after intent <UTC>` and op id `release-<execution>`, through the ordinary idempotent release and readback. A failed boot read, a missing intent time, boot at or before intent, another host's execution or an execution started after the current boot writes nothing and stays in `execution_waits`. Boot proves exit only, never input acceptance: a released execution with unknown acceptance still needs reconciliation. Boot and intent use different clocks (local OS versus board); skew larger than the gap between a spawn and the next reboot could release early, an accepted ceiling for historical executions. Windows Fast Startup does not reset the tick count, so its boot reads older and keeps executions held. Legacy exit without acceptance stays explicitly unknown for input delivery.

Closed-task worktrees (#1549): `.worktrees/taskq-<N>` of a closed task waits only on this host's unreleased executions, named by its host name or its OS hostname (executions written before the `hosts` mapping); another host's process never runs in this host's folder. Cleanup applies the boot proof above to those executions, then removes the worktree by the ordinary dirty rule. An execution it cannot release keeps the worktree with one line `#<N> worktree kept: execution <id> on <host> termination unknown; stop its process or reboot this host`. The service logs a kept or unconfirmed-removal line only when it differs from the last line for that task in `<root>/.taskq/cleanup`, a cache (R1), so a restart with the same outcome logs nothing; `taskq cleanup` always prints every line.

### Unified status and heartbeat

One status protocol uses existing transports: aggregate cross-host observations in the host/project heartbeat, local projections in `status.json`, and durable state/terminal entries in the trusted task log. Per-execution status identifies the attempt and input boundary; running/waiting includes a fixed reason and last observation. Terminal success/failure/cancellation is attributable to the exact execution. A release acknowledges native termination, while result/review retain their task meaning. A later heartbeat cannot reopen a terminal execution. Readback is the acknowledgment; retry the same message identity, not execution.

Heartbeat detail uses one `execution <JSON>` line per unresolved execution owned by that host. Fields: `task`, `attempt`, `id`, `through`, `state` (`running`, `waiting`, `unknown`) and a single-line `reason` of at most240 characters. The board heartbeat timestamp dates the observation; unchanged detail does not force extra writes. Readers match the exact board-owned host, attempt, execution and input boundary; missing, malformed, duplicate or stale observations read unknown. These projections never release work. Durable `released` readback wins over every heartbeat. Keep the existing lease/session lines for compatible readers. The service publishes runtime observation, not inferred model progress; acceptance pending, admission waits, native errors and recovery waits remain distinct.

The service aims to publish at most 60 s between periodic observations and wakes immediately for state/terminal changes. Slow native calls must not delay the publication timer behind a serial pass. One heartbeat PATCH per host/project/minute costs `60 * hosts * projects` requests/hour before changes, reads and terminal writes (six projects on two hosts: 720/hour). The existing 5000/hour shared token budget covers all requests, not just heartbeats. Rate limits and transport failures expose stale/unknown status and next retry; they never silently change the cadence or release an execution. The source scheduler now uses `min(60 s, ttl / 3)` and batches fast passes; serial native-call isolation and installed cadence remain stages 3–4 qualification gates.

## Windows native execution scope

The production launch boundary creates one Windows Job Object in the global kernel namespace, starts its child suspended, assigns it before user code can run, then resumes its verified primary thread. Use no breakaway flag; set kill-on-close (#2266): owned descendants inherit the job and survive service interruption while the launcher's duplicated handle keeps the job open, and Windows terminates every member once the last handle closes. The existing protected `kids` row adds `job-kill:<UUID>` for Codex; rows written before #2266 carry `job-global:<UUID>` (no kill-on-close). No second store, daemon or process journal. Old rows remain readable but cannot authorize Windows CLI adoption without that scope. Existing readers reject the extra column rather than silently treat it as a process-only record.

Cold reconstruction requires exact board execution ownership, original PID/creation identity and the saved job token. Query the native job's active-process count; launcher exit alone stays pending while members remain. Reopen and terminate the saved native job rather than rediscover a tree by PID. CLI polling returns pending while an acknowledged stop awaits native exit; failed control/readback remains an explicit error and retains the observer. A Windows job stop is not resent after its acknowledgment. A stop acknowledgment is not exit: observe zero active members, root termination and signaled handles for the observed members before release. Retain those handles while termination is pending: native accounting can reach zero before process wait handles signal. Membership observation accepts at most4096 native process IDs; incomplete/oversized/unreadable lists remain unknown. Remove signaled handles, not an unbounded history. The global namespace permits the same user to reopen the scope from another Windows session without enabling privileges; session-local records are unsupported and preserved. Missing job plus a live original root, unreadable scope or conflicting membership stays unknown. Job names disappear after the last open handle closes even if associated processes survive. Before resume, duplicate a query/terminate job handle into the original process so a live executor preserves the name across service loss. A missing `job-kill` scope with the original root gone proves exit: no handle remained, so kill-on-close ended every member; the service adopts it as ended and writes the ordinary Exit release, so another host can admit the task. A missing `job-global` scope never establishes exit; retain its reservation and require native reconciliation (a reboot proves exit). One row that cannot be adopted is logged and kept with its reservation; it never stops the project loop. Exact trusted board Exit may retire a stale record after confirming no live scope contradicts that already-recorded proof. Existing identity-only Windows rows require explicit legacy reconciliation. Retire/replace protected rows only after scope-aware exit readback. Setup failures before native resume are no-start only after confirmed child cleanup; otherwise retain the observer and report uncertainty.

Native Windows scope qualification remains partial. The native chain qualifies warm group observation/cancellation, unrelated-job preservation, failed terminal-receipt retry and protected-record cleanup. With the observer lost after the root exits, the chain verifies explicit unknown, preserved recovery evidence and no release or replay; fixture-only exact descendant cleanup is not product recovery. Installed Codex0.162.0-alpha.17.2 passes both owner-loss cases without a prompt/model: recover and cancel its still-live original process, or retain unknown when it ended and the addressable Job disappeared. No launcher or owner exception is required for the plan's explicit unknown outcome. Windows304 source units and13 integrations pass on that recorded candidate; full installed TaskQ, remaining native client/tool/continuation cases and stages4–7 remain open.

Windows native errors are captured at each handle-creation/open call before invoking an automatically instrumented helper. Telemetry cannot replace the dependency diagnosis.

## GUI eligibility (contract detail)

R9/R12 and §4: `needs-gui` requires a successful macOS Screen Recording preflight and PNG capture less than 300 seconds old, no Accessibility or App Data grant read `missing` or `stale` ([worker permissions](design/worker-permissions.md#macos-signing-identity)), plus effective Full access for the selected runtime. Configured `has: gui` never substitutes for the probe. Initial workers, reviewers, pending-inbox resumes and held-slot launches use the same eligibility check. Unsupported, missing, failed or stale evidence holds launch, preserving inbox, attempt and lease; running children continue. Tasks never grant access. Existing host, needs, runtime preference, focus and capacity filters remain in force.

The service probes at most every 300 seconds with a 5-second capture deadline, without requesting Screen Recording permission, and removes its private temporary PNG. Other platforms report unsupported. `status.json` `gui` contains `listed`, `reason`, `stale_grant` and `grants`; `waits` lists local `{task, reason}` records, also projected into task execution waits. The heartbeat includes `has gui` only while local evidence and a Full runtime remain eligible. Another host's heartbeat cannot qualify this host or hide a local refusal.

This is scheduler eligibility evidence, not proof that every worker/client can capture its target. The #1149 Mac evidence index retains native permission/client qualification limits; scheduler fixtures do not qualify installed GUI capture. No qualification label, host opt-in, CLI switch or grant is introduced.
