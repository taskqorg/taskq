# Shared answer card

Accepted target under [taskq.md § 2](../../taskq.md#ask-card). TaskQ owns the component and its conformance fixtures; DashQ consumes it. This is not a shipped UI claim. Apply shared [operator rules](https://github.com/taskqorg/specq/blob/main/design/operator-ui.md) and [AI-assisted controls](https://github.com/taskqorg/specq/blob/main/design/workflow.md#ai-assisted-controls).

Follow [shared-block inheritance B1–B4](shared-blocks.md). Compact placement does not authorize independent icons, tokens, counter layouts or simplified editors; the parent package governs visual fidelity.

## Ownership and delivery

One small browser-compatible component implements task question, source-numbered choices, recommendation, free text and receipt states. TaskQ workspace and DashQ supply adapters for their existing bridges; the component owns no credentials, network client, board parser or task state machine. No UI framework, service or general plugin system.

Keep source, styles/tokens and fixtures in TaskQ. Publish versioned static assets with the TaskQ release and checksum; until a v* release carries them, the pin is a TaskQ commit plus SHA-256 (§ Implementation, #937 owner answer). DashQ pins that version/hash and serves them locally under its CSP. Vendored generated assets are permitted only with provenance and checksum, never independent edits. No runtime CDN, iframe of the tray, npm registry or moving-main dependency. A compatible component update must pass both consumer fixtures.

## Card and interaction

- Consume TaskQ's canonical parsed card/snapshot: board identity, task identity/link, state, question/card revision, original text/evidence, ordered choices and recommendation. Parse with TaskQ's own semantics, never a second parser in DashQ. Unparseable cards remain readable with their board link and no write controls, except the explicitly enabled tray-only fallback below.
- Keep state, linked issue number and title one flowing block. Reveal the question with its task identity; each consumer places it (TaskQ target: the task's thread in workspace Conversations, [TW2](tray-workspace.md#contract-detail)). Preserve Done/Problem/evidence information; don't repeat boilerplate answering instructions when controls convey them.
- Text entry, attachments, validation and Send use the one [workspace composer](ai-workspace.md#native-dialogue-workspace-c1c9) (C3); technical operation and correlation IDs show only in details.
- Preserve choice IDs, order, text and recommendation. `★` has accessible name Recommended. Never sort the recommended choice first or renumber it.
- A normal choice submits that choice directly. A separate text field submits free text; the shared dispatcher wraps board lines under taskq.md § 5 without a reply line-count cap. Never infer a numbered choice from free text. No extra confirmation for an ordinary answer.
- Consequential operations, including a choice that TaskQ interprets as close/publication, stay visible in source order but unavailable in the dashboard with a reason and a board link. Do not silently remove or reinterpret them.
- Shared states: actionable, sending, accepted, stale, rejected, not sent (`failed`: nothing reached the board), partly applied (`partial`: a two-step action stopped after its first step), delivery unknown and read-only. Each receipt names its task and what it carries (`#N answer K. <choice>`, `text answer` or the fallback action). Show one local receipt beside the question; preserve row, scroll, focus and typed draft through refresh. Acceptance is one board operation, not worker resumption, task completion or repaired service.
- Bind a draft to board/task/question revision. A changed question keeps Send available and preserves the draft's source revision. Show the updated question and explain that Send saves the old draft as a task note. A choice clicked on the newly displayed card binds to that card. The dispatcher resolves stale choices from their original card and saves a note; it never reuses their number on the new card. No review acknowledgement is required.
- One operation ID binds one immutable answer payload and expected revision. Double click and uncertain-delivery reconciliation retain that ID; changed text/choice is a new operation. Disable duplicate controls while sending. Unknown delivery never becomes accepted on timeout or triggers a new-ID retry.

Tray-only fallback (R6, #1021): `capability.manage` enables requeue (nonempty reason, wrapped under taskq.md § 5), Later and Close without publishing only for `ask` with no canonical choices. Other consumers receive no new authority. Requeue sends `Reason: <literal reason>`; Close cancels without publication through `later` then `close`, with distinct stable operation IDs and the first readback revision fencing the second command. A failed/unknown step stops; a partial result names the parked task. Tray mounts cards only for ask, and retains operation receipts separately after a state change. Numbered close choices remain unavailable.

## Adapters and evidence

The adapter supplies answer capability/reason and invokes the canonical TaskQ dispatcher with actor, expected revision and operation ID. The component never emits board comments or decides authorization. An accepted receipt comes from TaskQ readback; failures retain producer reason/next action. Browser access and observation enrollment alone do not grant write permission.

Use the same fixtures in TaskQ and DashQ: choice and free text; long question; malformed card; review decision; read-only; duplicate click/lost response; stale revision; permission revoked; sending refresh; denied/unknown/accepted receipt. Check keyboard use, focus/drafts, 16/20 px, both themes and narrow layout. Pure UI tests cannot certify a real board write.

## Implementation

- Canonical fields: each `status --json` task row with a card adds `question`: `parsed`, original `text`, `done`, `problem`, `evidence` (label, URL), `choices` (`id`, `text`, `label` and `detail` split at its first ` - `, else the whole text and null, `recommended`, `consequential` for a close or exact-SHA approval option) and free-text `limits`. `parsed` is false unless the card has Problem and either 2-4 options with one `★` or no options; options must be numbered 1..n in order with no gap or repeat. A parsed card without options is an owner action (§ 2), answered with literal text. An unparsed card stays readable with its board link and no write controls. Outside `ask`, a row whose last question an accepted answer closed adds `answered {by, text}` (§ 5 late answer), so the tray, DashQ and PilotQ name that answer alike; a late answer through any surface, the CLI included, reads `already answered by <by>: <text>`.
- PM pick (taskq.md § 2): `taskq pick N.K --text R` writes `taskq: pick K` with the one-line reason as a board entry; no task state or revision changes. Fold keeps it while the same card is open; a newer card or any move out of `ask` (an owner answer included) clears it. The row adds `pick` = `{id, reason}`; status, inbox and this card show `PM N.K: <reason>` beside the worker's `★`, only the `★` without a pick. A pick never answers: choices and sends stay the owner's.
- Component: [src/answer-card.js](../../src/answer-card.js) (CommonJS source; `TaskqAnswerCard` browser global in the bundled release) and [src/answer-card.css](../../src/answer-card.css). `mount(el, adapter).update([{board, row}])` keeps drafts, focus and scroll and writes no DOM when the rendered card is unchanged; while the card is live, a disabled Send or Requeue states its free-text limit beside it, updated as the owner types (#1456); the adapter gives `capability(board, row)` = `{answer, reason, manage?, composer?}` (manage is tray-only; with `composer` the consumer's shared composer owns text entry, reading pure `compose(row, local, cap)` for draft, validation and Send label, and driving the card through the controller's `input(board, n, text, caret)` and `act(board, n, 'submit' | 'requeue')`) and `send(board, op)` resolving to `{state, reason, next}`, with `op` = `{id, task, revision, choice | text}`; tray fallback adds `action: requeue|later|close` with one explicit Close without publishing action. Workspace adapters may also supply `load(board, row)` and `save(board, row, local)` for native draft, caret and operation-identity persistence. Restart restores pending delivery as unknown, never a replay. Enter uses the same submission validation as Send; Shift+Enter and IME composition do not submit. The mounted controller's `receiveReceipt(board, opId, reply)` applies a late receipt only to its matching operation, through the same receipt transition. A timeout can settle the original promise as unknown; a later exact receipt still updates that card without another send or promise settlement. Pure `status`, `step` and `render` hold all behavior.
- Workspace adapter: [src/workspace-answers.js](../../src/workspace-answers.js) embeds the shared assets in the exact task-answer context and keeps card instances through refresh/navigation. Menu task rows open that task thread without answering or acknowledging. The existing IPC bridge in [src/tray.rs](../../src/tray.rs) validates registered project/board identity and invokes the owner CLI dispatcher with the exact operation ID and revision; only its readback receipt accepts an answer. A missing receipt stays unknown and reconciles with the same payload/ID. A status refresh that reads the task past an answer operation's question (not a fallback action) reconciles once with the same payload/ID, so Sending ends with the CLI receipt; the refresh itself never accepts. Each Check delivery after an unknown receipt sends that op once more; `tests/tray-answer.browser.cjs` counts submit, reconcile and Check delivery as three sends of one op. `node tests/tray-answer.test.cjs` checks this adapter boundary. When another client answered first, the bridge's stale or rejected receipt carries `answered {by, text}` in place of revisions or CLI advice, and the refreshed row's `answered` names it even before this client sends: the thread names that answer, and while the worker runs an answer already submitted is saved as a durable task note and queued to steer the worker without a second click. A draft that was never submitted remains editable for one explicit Steer send. Every attempt/resume and hand-in reads goal, acceptance and all ordered notes; a conflict asks immediately, as taskq.md sections 2 and 7 require.

## Contract detail

Moved verbatim from `taskq.md` (#1179) to keep the contract under its R8 size bound. `taskq.md` keeps the decision and links here; this text keeps the same authority (R8, R13).

Accepted shared UI target: [answer card](answer-card.md) owns the reusable TaskQ/DashQ presentation; § 2 and § 5 remain behavioral authority. Tray exception (R6): mount cards only in `ask` (target TW2: in the workspace, not the menu; semantics unchanged); without parsed choices, show text and owner requeue (reason), later and one-action Close without publishing controls. Close cancels without publication through `later` then `close`, each with CLI readback; partial/unknown delivery stays explicit. An answer op is resent only with its own id: once when a refresh reads the task past its revision, once per Check delivery after an unknown receipt. Other consumers remain read-only for unparsed cards. K is an option number; a bare K or option text counts only in `ask` (section 2).

`--text`: literal Done/Problem lines; `--link`/`--image`: Evidence; `--option`/`--recommend`: options/star (moved from § 2, #1787).

### One render

Every surface that shows a parsed card (tray, workspace Conversations, DashQ) uses this one `render()` layout, in this order (#1787):

1. Head: the `?` mark, the task link `#N` and the title.
2. Done line after `✓` (accessible name Done), then Problem line after `⚑` (accessible name Problem), each in full.
3. Images ([Ask images](#ask-images), [Question types](#question-types)).
4. Options in source order. A button shows `N.` and the label, with `★` on the recommended one. The option's detail (`+ <gain>; - <cost>`) follows its button in full on its own line; it wraps and is never cut. A link in the detail opens inside the detail.
5. Other answer, PM pick and the receipt; evidence links behind an Evidence disclosure.

No surface shows the `To answer:` line: the controls convey answering, and the board card keeps the line for board readers. An option without ` - ` (a card written before #1787) shows its whole text as the label and has no detail. Service cards (retry limit, blocked, closed, refused start, failed input) come from the same writer as `ask` (#2012), so their options carry a label and a detail too; their keyed options (`later:`, `close:`) run only through `taskq answer N.K`.

Option syntax: `--option "<label> - + <gain>; - <cost>"`. `ask` and `result` reject a missing label, a label over 32 characters, a label repeated in another option (case ignored) and a detail without one `+` gain and one `-` cost; the error names `option line K`. Limits count Unicode characters, so a Russian label of 32 letters fits.

### Question types

Each question type adds rules to [One render](#one-render).

- Visual choice: the options choose between things seen. Attach one `--image` per option, in option order. When the image count equals the option count (2-4), image K belongs to option K: `ask` names it `K. <name>` in the `Evidence:` line, and every app surface captions it `K.` below its thumbnail. Other image counts are plain visual evidence, without captions.

Browser delivery uses the self-contained `build/web/answer-card.js` bundle (`npm run build`), published under the existing release filename. Source checksums identify editable CommonJS modules; released bundle integrity comes from `SHA256SUMS`. See [JS packaging](profiling.md#js-execution-architecture).

### Human replies

Contract detail for taskq.md § 5. Every surface sends a person's answer, steer or requeue through the shared dispatcher wrapper. No input line, line-count or total-length cap applies. Store lines of at most 240 Unicode characters at word breaks; split an unbroken token only when necessary. Preserve every word in order and existing paragraph breaks. Refuse empty answers and steers with a fix. Any composer refusal shows the exact reason and fix beside Send and records its kind without reply content. Worker requeue verdicts retain the Reason/Next format in § 5.

Task replies accept images and arbitrary regular files, including empty or binary files, with text optional when files are present. Paste, drop and pick use the same attachment chips and removal on Conversations and tray. `answer N`, `steer N` and owner `requeue N` accept repeated `--file PATH`; PilotQ passes the files it downloaded from Telegram with this interface. Numbered options and task cancellation never consume attachments. New owner requests and owner-session dialogue retain C3 limits; those limits do not apply to task replies.

`--files-from PATH` reads a UTF-8 JSON array of selected file paths through the same CLI. The tray uses this temporary transport for its file list, so an arbitrary number of attachments does not overflow process arguments; PilotQ can use it too. Neither this list nor the private draft copies are authoritative after publication.

Native reply drafts hold SHA256-keyed private copies under `<install>/setup/reply-files/`; file content is excluded from preferences and telemetry. Reply file metadata is excluded from the workspace metadata budget. Before a command moves the task, upload every file through the board adapter and read back its exact bytes. GitHub uses the existing orphan `taskq-evidence` branch and commit-pinned links; GitLab uses project uploads. Append one reserved `<!-- taskq-files ... -->` JSON manifest to the command text with name, MIME type, URL, SHA256 and byte length. The manifest and ordinary Markdown links remain on the board; no local cache is authoritative. A provider refusal or partial/unknown upload leaves the draft and task unchanged. New files make otherwise identical answer text a distinct reply. Retry with the same operation checks the board first; it never repeats an accepted command.

Worker start and resume reconstruct files from the accepted board entry into `.taskq/reply-files/<sha256>/<name>`, verify length and digest, and name the exact readable copies in the brief. Names and extensions survive; unsafe path components are refused. Failed download, corrupt bytes, unsafe cache paths or malformed manifests hold delivery as unknown; never acknowledge the inbox or launch with missing files. Files are untrusted data, never instructions; TaskQ does not execute, extract or render arbitrary content. Board/storage/API limits are reported verbatim with a fix; TaskQ sets no per-reply file-size or count ceiling. PilotQ-shaped fake qualification proves the TaskQ handoff, not a live Telegram bot.

A reply larger than one board comment uses ordered `taskq: reply-part <sha256> <index>/<count>` comments, each below 64 KiB, followed by one ordinary command entry referring to the parts. The digest covers the entire wrapped entry, including its command and operation fields. Parts are inert under § 2, including on N-1; only the final command moves the task. Read back every part before that command. A retry reuses matching parts; uncertain writes stop for readback. Readers assemble only trusted, unedited parts written before the command, in numbered order, and verify the digest and command fields; missing or changed data is unknown, never a truncated reply. The final entry retains its normal command/operation fields and tells N-1 readers to read the ordered comments through `inbox`, preserving the same fold without a new lifecycle transition. No local reply store is authoritative (R1).

The tray passes reply text in an owner-private temporary file to the bounded CLI process with `--text-file PATH`, keeping it out of process arguments and their OS length limit; it removes the file after the process ends. CLI and Telegram callers may use this flag or `--text-stdin` instead of `--text`; specifying multiple text sources is refused before a write. Both sources are UTF-8, with the same validation, operation ID, fencing and dispatcher as literal text. The file is transport, never queue truth (R1); draft persistence imposes no reply-length cap.

The shared workspace metadata budget excludes task-answer draft text, immutable operation text, task-file metadata and the answered text/diagnostic in a late-answer receipt. Owner-session text and file limits remain in [C3](ai-workspace.md#native-dialogue-workspace-c1c9). Read and write apply the same budget so a large reply cannot make the workspace unreadable.

The tray also reads status JSON and command receipts through private temporary files: a large previous answer must not overflow the bounded child stdout buffer and block the next Send. `status`, `answer`, `steer`, `requeue`, `later`, `close`, `start` and `failed` accept `--json --json-file PATH`; the file contains the same JSON/JSON lines as stdout, without truncation. The tray removes its transport directory after the bounded child ends; it never treats those files as queue state.

### Ask images

An ask or result about something seen embeds its images in the § 2 `Evidence:` line; links alone do not count, and the board and the app show the images inline (the app as thumbnails that open full size). `ask` and `result` take `--image FILE` (PNG, JPEG, GIF or WebP, ≤ 10 MB), which uploads to the board before the card is written: GitLab project uploads embedded by absolute URL `https://<host>/-/project/<id>/uploads/<secret>/<file>#upload=<id>` (the relative or `full_path` link renders broken); GitHub one commit per image on the orphan branch `taskq-evidence`, embedded by commit-pinned `https://<host>/<repo>/raw/<sha>/<N>/<file>`. The board must serve the same bytes back with the token, else the command fails and writes nothing. The service copies each open ask's images to `.taskq/images` for the app, which holds no board token. `result --image` without a card adds one § 2 `Evidence:` line of images.

Videos (#1844): `--image` also takes MP4 and WebM files, each named with its extension (`.mp4`, `.webm`) because boards pick the player by it; the 10 MB cap holds for every file, and the same load check runs. GitLab embeds a video as `![<name>](<url>)` and plays it inline on the issue page; its URL ends in the extension, so it carries no `#upload=` fragment, and the load check finds the upload id by the unique file name among the newest 100 uploads. GitHub plays no video in a comment and serves raw MP4 or WebM as a download, so a video is the link `[▶ <name>](<url>)`: on a public github.com repository the URL is `https://cdn.jsdelivr.net/gh/<repo>@<sha>/<N>/<file>`, the same commit-pinned evidence file through jsDelivr, which one click opens playing in the browser. Limits: jsDelivr is a third-party CDN that can only read public repositories, so a private or Enterprise repository gets the raw link, which downloads the file. The apps show a video as a link, never as a thumbnail.

Files (#2019): `result` and `ask` take `--file FILE` for a zip, tar.gz (`.tar.gz`, `.tgz`), PDF or HTML (`.html`, `.htm`) file of at most 25 MB, checked by name ending and leading bytes before any upload or write; a larger or other file is refused and nothing is written. Each file is one `[⬇ <name>](<url>)` link in the `Evidence:` line and counts toward its two links together with `--link`; a `result` without a card takes file links without `--option`. GitHub commits each file to the non-branch ref `refs/taskq/evidence`, which default clones do not fetch (#2016), and links the commit-pinned `https://<host>/<repo>/raw/<sha>/<N>/<file>`; GitLab stores it as a project upload with the absolute URL above. The same load check runs, and the § 2 summary `Files:` line links each file like any other outcome file. One click downloads the file. GitHub serves an HTML file as text, so the browser would show its source: on GitHub `--file` uploads an HTML file inside a zip of the same name plus `.zip` (link `[⬇ <name>.html.zip](<url>)`), and the load check reads back that zip; GitLab and the other kinds upload the file as is.

Hand-written media links break the same way the relative upload links did (csgo#415: `/-/project/39/uploads/...` with no host became a missing repository file). `ask`, `result`, `requeue`, `later`, `failed`, `steer`, `answer` and `pick` refuse any image or video link in `--text`, `--option`, `--checks` or `--link` that is relative or host-less, or that names a repository path (`/blob/`, `/-/blob/`, `/-/raw/`, `/tree/`, raw.githubusercontent.com, or `/raw/<ref>` where `<ref>` is not a commit SHA). The error names the link and points to `--image`.

### Confirmation inventory

Every accepted answer and steer is a durable task note in board order, across attempts. Outside `doing`, an owner steer saves context without changing state or answering the open question. Goal and acceptance remain binding: workers and reviewers ask once as soon as a note conflicts with acceptance; never defer a known conflict until hand-in. The fresh inbox and every attempt/resume prompt include goal, acceptance and all notes, without truncating old notes. A saved steer or late answer has receipt `note: true`; board acceptance never proves worker delivery.

- Answer, steer and requeue: one Send/action; validation stays inline. Owner steer always saves context on an open task, even if a question/state change races Send; its original operation ID and payload remain unchanged. Worker-originated commands keep attempt fencing.
- Changed question: remove the disabled Send and `I read the new question` acknowledgement. Save old intent as a note and keep the newer question open.
- Answered elsewhere: name the winning answer; save an already submitted answer as a note and steer the running worker without a second Send. A draft never submitted still needs its first Send. The same answer as the winner saves nothing (below).
- No-choice cancellation: replace Close followed by confirmation with one explicitly named Close without publishing action. Keep separate, revision-fenced `later`/`close` readbacks and stop on partial/unknown delivery. A race that makes cancellation inapplicable is refused visibly; it never cancels a new attempt automatically.
- Publication and exact-SHA approval choices remain unavailable here with the existing board link: removing a confirmation grants no publication or approval authority.
- Delivery checks reconcile the original immutable ID, payload and revision. They are recovery after unknown delivery, not confirmation before sending.

Consumer compatibility: the command/payload shape stays compatible; shared UI gains the `changed` state and no longer requires a confirmation flag on the tray cancellation action. Older dispatchers can still refuse stale answers: that receipt remains explicit, never presented as a saved note. Steer notes use the existing board entry and keep lifecycle folding compatible; older prompts do not provide the new context guarantee until updated.


### Concurrent replies

Two people answering one question seconds apart (owner in the menu, PM in the CLI, someone on the board) settle quietly (#1861). A race that ends in a valid board state is never shown as an error: the tray shows red only for a rejected, failed, partial or unknown delivery. A stale action reads as plain text: `task changed; action not sent`.

| Reply path | Another actor acted first | Result |
|---|---|---|
| Answer, menu or CLI | answered with the same option or text | No write, outcome `accepted`, `answered` names the winner once; no note, no steer |
| Answer, menu or CLI | answered with another option | Ordered `steer answer <revision>` note with the original option text, `note: true`; steers a `doing` worker; the receipt names the winner once |
| Answer, menu or CLI | asked a newer question | Note as above; the newer question stays open |
| Answer, menu or CLI | closed the task | Same answer: no write, `accepted`; another answer: rejected `#N is closed` |
| Answer, menu or CLI | the post lost the race after writing | The losing comment edits itself `ignored: another write won`, then the first two rows apply |
| Answer, board comment `K` or option text | answered or moved out of `ask` | `fold` ignores it; no note, no receipt |
| Steer, menu or CLI | any state change on an open task | Note, `note: true`; a `doing` worker gets it |
| Steer, menu or CLI | closed the task | Rejected `#N is closed` |
| Requeue, CLI without `--revision` | any change on an open task | Accepted, task `ready` |
| Start, Stop, Later, Retry, Requeue or Close without publishing, menu (revision-fenced) | any change | `stale`, nothing sent; plain, not red |
| Close, CLI | closed the task | Rejected `#N is closed` |

The receipt names each fact once: the CLI prints the state line, then `already answered by <by>: <text>` from `answered`, then the reason (`Saved as a task note; ...` or `Same answer; nothing saved`); `reason` never repeats the winner's text. The tray reads `Answered by <by>: <text>` plus that reason.
