# AI requests

Design under [R3/R9](../../taskq.md). [Menu M7](menu.md#m7-ai-entry) · [Use cases](../use-cases/README.md).

Owner decision (#1427): a tray AI request opens a new visible session, like setup ([#1426](standalone-onboarding.md#contract-detail)). There is no operator turn, no conversation storage, no proposal or `rev` confirmation and no request log. The session does the work itself and may act as PM; the owner reads and answers it in its runtime.

Approved target (#1462, not shipped): the composer moves to the workspace and a request opens a session in any available runtime, Claude or Codex, named in the request UI ([TW4](tray-workspace.md#contract-detail)). Messages, archive and permanent delete act on TaskQ message records only ([TW5–TW7](tray-workspace.md#contract-detail)); no TaskQ conversation storage returns.

New owner requests offer explicit Claude Code or Codex selection under TW4. Native platform qualification remains separate from source support (R12). #1580 implements the draft/file workspace below; no conversation store or proposal protocol returns.

Owner-approved #1467 scope ([answer 6328516821](https://github.com/taskqorg/taskq/issues/1467#issuecomment-6328516821)) accepts M's seven-image layout and message-only outcome. Combined #1465/#1466 acceptance and native workspace qualification remain separately gated.

## Native dialogue workspace (C1–C9)

The [#1580 owner answer](https://github.com/taskqorg/taskq/issues/1580#issuecomment-6343852087) selected native-only dialogue; the owner reversed that part on 2026-10-23: replies continue in the workspace per [D1–D8](#workspace-dialogue-d1d8). A1/A7 keep workspace drafts, files, request history and Open session. R3 and TW5–TW7 retain authority. The archived design's operator, transcript, proposal protocol and active-only archive guards do not return.

- C1/C2 one thread screen (#1699, replaces the #1691 Inbox section and the request/session split of C1): Conversations lists threads: TaskQ-known owner drafts/requests and one task thread per board task with an open question or a question event, plus every task opened from the menu. Menu-opened event-free task identities remain in Recent for revisit; they are navigation metadata, never task state. A request event belongs to its own conversation thread; no thread is created for an event without a source. Rows are compact: task or project, title, an Unread or Needs reply marker and one open action. Work sessions stay a distinct R6 list behind the toolbar. History contains the last 20 submitted texts and fills only. There is no scan of unrelated native chats.
- C2/C7/CW1–CW8: Native Close and safe Reload preserve the last recoverable draft/files/caret/focus, selected exact source and valid reading anchor. A failed save names its reason and retains the prior durable state; recovery never treats it as an empty history or replays a pending action. New clears search, result filters and scoped paging, then shows and focuses its own draft in Recent. The first draft line is a temporary title until the request is sent; a sent or native thread keeps the first line of its sent request while the owner types the next message; an explicit name wins. Each draft retains project, text, caret and record scroll. Owner, task and event threads share one selection model. Recent and Archive retain their own selected thread identities; switching lists restores a visible selection from that list or shows an empty detail. A hidden or unavailable selection never leaves another list’s detail visible. Clear search keeps selection. Archive any item, stay in the list, choose another and offer Undo; Restore/Undo opens the item. An archived task thread opened from the menu selects Archive, remains read-only and offers Restore; only explicit Restore returns it to Recent. Archiving a task thread archives only its TaskQ event record; the board task, native session and other event records stay. Each thread keeps draft, files, caret, selection and scroll across switches, Settings and close/reopen. Close hides, never sends, cancels or archives. Pin, enlarge/restore and resize use the native window. Explicit Detach/Return transfers one editable owner; reopen raises that owner. Restart restores metadata when opened and returns ownership to main without reopening detached windows.
- C3 composer: one shared composer owns context, editable text, attachment chips/removal, validation and Send on every surface that takes owner text: a new request, a D2 reply and a task answer. Task answers, steers and owner requeues accept files under [Human replies](answer-card.md#human-replies), keeping source option numbers and exact-revision semantics; a question that changes while typing keeps the draft and Send, which saves the original intent and files as a durable task note without re-confirmation. One short destination line or tooltip identifies the project and recorded runtime. Details explains unsupported owner-session inputs and number-as-text semantics; actionable validation stays beside the input.
- C5 events (#1699): there is no Inbox section. The menu Conversations entry opens Conversations with the list visible and the first unread thread selected, an actionable question first; with no events it restores the last thread. Opening, selecting or reading a thread acknowledges nothing; Mark read is explicit and its receipt shows in that thread only, never in the shared status line or on other routes. Every menu task offers one Conversations entry, including Later, Doing, Review and Ask. Opening a task with no event retains its own task thread in Recent; nothing is duplicated, acknowledged, sent or launched. A task thread has one identity heading; row metadata stays compact and technical IDs stay in Details.
- C5 rows: threads show plain delivery errors; request, operation and correlation IDs appear only in details. A failed or unknown delivery offers Check delivery with the same operation, never a resend. A retained pending-correlation conflict is named in user terms (an earlier answer with this operation is still pending with different content) and investigated before retry; never suppress the guard.
- C3 owner sessions: Selection/drop reads explicit files, never source paths. UTF-8 text/Markdown and PNG/JPEG/WebP: at most 4 files, 5 MiB each, 20 MiB per draft and 100 MiB of owned copies per installation. Empty files, binary text, directories and executables are refused. Image selection rejects unreadable data and dimensions above 8000 pixels per side. PDF is unsupported (0 pages): no qualified page-count validator. Owner-session draft text is at most 64 KiB; local metadata stops at 8 MiB, excluding [task reply payloads](answer-card.md#human-replies) under taskq.md § 5. No truncation or automatic history eviction. Show these limits before selection and preserve other files/draft on refusal. Image preview uses local bytes only.
- C3/C7: Native storage owns copies in `<install>/setup/<request-id>/attachments/`, keyed by SHA256. Send freezes ID/hash/length and verifies bytes before handing paths to the native session's Read tool. File contents never enter command history or telemetry. Remove affects only the draft reference. Permanent deletion removes owned copies and metadata, never source files/native chats; deletion fences prevent resurrection.
- C4: One immutable launch request per item. Native preference revision fences stale saves; Send persists its immutable input before dispatch. Unknown/partial delivery retains draft/files; Check delivery reads that same ID without replay. New/selection/reload/detach/close never dispatch. A next draft is editable while launch waits; an explicit New from draft creates a separate owner request. Continue replies in the workspace (D2) or through Open session. Cancel acknowledges only a pending launch under the setup lock; launching/launched/unknown requests require the native runtime. No enabled runtime Stop without an adapter.
- C5/C6: Board questions keep source numbers, order, recommendation and exact-revision receipts in their task thread; old message and answer routes open that thread; sessions and operation pages return to Conversations; operation review remains in existing reviews. Work-session targets use #1565/R6; missing/remote capabilities stay explicit. Local workspace adds no gateway, grants or task store; its only scheduler is the D6 watch. Remote PM launch uses the separate opt-in [PM exchange](pm-requests.md), never observation/resource authority.
- C7/C9: Extend `<install>/tray-requests.json` for local draft/view metadata, preserving existing request/answer/history fields. Corrupt or unavailable storage refuses writes and leaves existing bytes. Durable setup records remain launch truth. Never infer runtime completion from `launched`. Archive and permanent deletion follow TW6/TW7, including the prelaunch deletion refusal and no trash/undo for Delete.
- C7/TW7: New from draft moves text/context/files to a separate draft ID with same-ID reconciliation, never a launch. Deleting a sent message first preserves independent unsent text and newly selected files as a separate draft, then removes the sent record/copies. Unchanged sent text/files are not recovery sources; independently edited next text survives even when identical. Send freezes its input revision. Copy/storage failure refuses deletion and keeps the original. Deletion readback removes sent content from open views; an unsaved local edit stays visible for copying, never resends.

## Workspace dialogue (D1–D8)

**Live task worker panel (#1831).**

A Doing task's Conversations thread shows its worker's live native transcript on the viewing host. The native read adapter resolves the session from the service's fresh, complete task/attempt snapshot and the attempt log; client session IDs never select a transcript. Each read is fenced to that attempt and registered project. A worker on another host of the board is read through the [host link](host-link.md) with the same request, answered by that host's own adapter; a host that does not answer within 5 s reads unknown with the reason. Missing transcripts and stale or unreadable observations stay explicitly unavailable.

The open panel reads once a second and appends worker messages, owner turns delivered through the board, and one tool-name line per call. Tool arguments and command output are omitted. Closing or leaving the thread cancels polling; an ended or replaced attempt stops reads and discards late replies. Owner input continues through the next-turn steer path, never a native resume from this panel (D3).

D1 keeps the native file as the only dialogue record: no transcript is saved by TaskQ. D4 keeps bounded whole-record cursor reads and at most 600 transient live items, in native order, with the newest at the bottom; the panel is a live tail. Scrolling up pauses following and keeps the message anchor; Jump to latest resumes it. Missing data remains unknown. This panel adds no writer, scheduler or acknowledgement.

The Conversations window uses the adopted v7 look ([visual style](visual-style.md#geometry-and-type)); list rows show project and a plain status (Working, Ready, Status unknown, Draft, Delivery unknown), never `unknown`. A launch brief stays in the transcript as a collapsed Setup brief, not an owner message.

Owner decision 2026-10-23 (target, not shipped): the owner talks to an owner session in the workspace without opening Claude or Codex. Any number of conversations; any one may do PM work; none is special. Phase 1 is the local workspace; DashQ follows.

- D1 Source: the native transcript is the only record. Claude: `~/.claude/projects/*/<id>.jsonl`; Codex: `~/.codex/sessions/**/rollout-*-<id>.jsonl`. TaskQ keeps no copy, index or summary; transient in-memory record offsets and page heights for rendering are not an index, and a saved reading anchor holds only record identity and offset. A missing or unreadable transcript shows unknown, never empty.
- D2 Send: the composer of a launched conversation sends the next message as one native turn, text on stdin, files per C3: Claude `claude -p --output-format stream-json --permission-mode <mode> --resume <id>`, App-owned Codex uses the existing AgentQ App queue in that same native thread, never a competing `codex exec resume` writer ([adapter](../runtime-qualification.md#runtime-adapters)). Never `claude --bg --resume` into a live session: it starts a copy. Send persists the immutable input before dispatch; unknown delivery keeps the draft (C4).
- D3 One writer: at most one turn per session. While a TaskQ turn runs, Send queues nothing and says `working`. Before a turn TaskQ checks for a native holder: Claude `agents --json` lists the session ID in an interactive, busy or other job, or Codex native history still has an active turn; then Send says `open in <runtime>; close it there first` and keeps the draft. The idle background job TaskQ launched is no holder: Claude resumes only a stopped session, so the turn runs `claude stop <job>` first and starts only when the readback lists no holder. Probe 2026-10-23: two concurrent Claude resumes fork the transcript and lose one branch; Codex refuses the second resume.
- D4 rich content: The shared safe prose renderer formats headings, lists, emphasis and fenced code in PM/worker messages and result prose. Bundled language grammars provide syntax tokens; unknown languages, code above 8,192 UTF-16 units or highlighting failure retain selectable plain code. Raw source remains inspectable and unchanged. The image-aware parser versions its source generation: a pre-image saved ordinal explicitly requires Latest rather than opening a different block. Drafts and delivery receipts remain independent of that read fence. No raw HTML or script executes. Native history image blocks use only bytes embedded in the selected transcript, never arbitrary file paths or automatic remote fetches. PNG/JPEG/WebP/GIF previews are bounded to 2 MiB encoded bytes per page, four images per page and mounted reader, and 4 million pixels per image. Decode is lazy; native cursor pages and the existing resident-byte ceiling bound transient retention, with no disk image cache. Each image retains record identity and the provider role, without inferring owner/board authorship from a provider user-image wrapper, plus aspect ratio, useful source name/alt, inspect control and a recorded HTTP(S) artifact link when present. Missing, oversized, unsupported or undecodable images remain explicit; later pages can be read without resending input. A real source-backed native image episode is required for image qualification; invented previews are instruments only.

- D4 View: Worker text, recorded questions, answers and result share one readable document with consistent author, source time and spacing. The current question/action stays primary; earlier questions, events, tools and advanced actions remain inspectable without redundant nested reader disclosures. user and assistant text in order, tool calls as one line each, newest at the bottom. Read backwards from the file end in bounded pages of whole records (256 KiB, at most 200 items; one record over 16 MiB is refused as unknown). Each item carries its record identity: the byte offset where its record starts and its block ordinal. The view mounts one contiguous window of at most 600 items and reads the previous or next page by byte cursor while the window edge is within one viewport (infinite scroll; Load earlier stays); pages of only skipped records continue the read, at most 8 such pages in a row before Load earlier or Load later asks for a user action. Whole records beyond two viewports leave the window, except records that hold a selection, and are read again from the native transcript when needed. A reply for a replaced window or an outdated cursor is ignored. The first visible record and its offset are the reading anchor: prepend, append, font, width and content-size changes keep it within 2 CSS px. The anchor is view metadata in the saved navigation (24 most recent threads, at most 1.5 KiB); returning to the thread reads the page that starts at it, and an anchor whose record is gone is said and Latest opens. The view follows new records only while the reader is at the end of a window that holds the file end; otherwise Jump to latest, labelled New messages when records arrived, is the visible way back, and only that explicit action resumes following. Transcript reading never acknowledges events. While the view is open and holds the file end, poll the file size every 2 s and append new records. A page load is announced as one short status, not read in full. Unknown record types are skipped. The thread detail owns one content scroll for status, transcript or question, and composer; Status and composer have no separate content scroll. Launch diagnostics, handoff and Status collapse into details above the transcript. Expanded Status, long watch prompts and long questions preserve the reading position and keep the composer reachable at 18–20 px. Archived launched owner threads keep the D4 transcript read-only and require Restore before reply. TaskQ archive does not archive the native conversation; session IDs stay in Details.
- D2/D5 App receipts: Persist the exact operation/input and native completion baseline and complete-record byte boundary before one App submission. Queue success is not acceptance; only exact input plus matching native turn completion settles it. Restart or a lost queue reply observes that same input after its saved byte boundary without submitting again; an older identical aborted input cannot acknowledge the new operation. The composer retains the original text/files until native exact-input acceptance is read back explicitly. Revalidate the existing project App grant before submission; no CLI fallback, migration, lock removal or authentication copying. A legacy CLI active-writer refusal keeps its immutable input; only an explicit owner retry after verified CLI exit and idle native state re-admits that same operation to the App queue.
- D4 transport evidence: Show the recorded original owner request in the main document. Exact attributable handshake/OK, owned brief pointers and provider citation metadata stay inspectable as secondary evidence, with source offsets intact. A queued initial brief is not PM Ready while native tools still run; absent or uncertain native completion remains unknown.
- D5 State: `working` (TaskQ turn alive), `idle`, `open in <runtime>` (D3 holder), `unknown`. An App-owned turn ends only on its matching native terminal record; process exit does not settle it. For CLI-owned turns, Claude's `result` and Codex's `turn.completed`/`turn.failed` give the outcome. Exit alone never says success. The last turn's input, state and outcome live in `<install>/setup/<id>/turn.json`; a restart while it starts is unknown, never a resend.
- D6 Watch: a conversation may hold one watch: `prompt`, `every` (minutes, at least 5) and `events` (subset of `close|failed|ask|blocked|gone` from the project's `.taskq/events`). The service sends `prompt` as a D2 turn when due and the session is idle; matching new event lines since the last watch turn are appended to the prompt and make it due at once. Stored in `<install>/setup/<id>/watch.json` with `last_turn`, `last_outcome`, `next_due`. The emergency hold and Stop pause watch turns; owner Send still works. A watch never creates tasks or grants by itself; the session acts through TaskQ commands.
- D7 Status: the conversation's collapsed Details shows the watch (prompt, every, events), last and next turn, last outcome and the last assistant prose line, from `watch.json` and the transcript. A complete provider-citation suffix is secondary metadata, not that preview; the exact transcript stays unchanged. Composer and reading behavior: input grows with text and wrapping, including restored drafts, paste and font/window changes. No manual field grip or inner text scroll. Short input stays at the bottom; a long draft uses the same reading viewport, with Send remaining reachable. Preserve independent draft/caret and a visible message anchor across updates, prepends, disclosure, resizing and switches. Scrolling up pauses following; new content shows a compact latest-message action without moving the view. Only that explicit action resumes following. Reduced motion skips animated jumps. ## Contract detail

- Request: the workspace Ask AI composer names one registered project (default: the first). Send writes `<install>/setup/<id>.json` with `root` = that project and `brief` = the owner's text inside the fixed request template in `src/setup.rs`, then pokes the host. Empty text or an unregistered project writes nothing. The workspace offers Claude Code and, on supported native platforms, Codex, with separate fresh readiness for each. The draft retains the explicit choice across saves, switches and recovery; existing drafts default to Claude Code. Send freezes that runtime with the exact project and text; replies retain the launched runtime. No fallback or host default change occurs. Project owner launches use the exact project working directory and the selected visible adapter’s existing worker grant: Claude Code or Codex app. Standalone setup retains its owned folder. Codex app Workspace remains refused until its native boundary is qualified; choosing Codex never upgrades a CLI grant. Native qualification remains separate (R12). A stable request ID binds the project, runtime and literal request. Check delivery reads that same setup record, including after restart; it never creates a new-ID retry. A lost or partial receipt preserves the draft and shows unknown until readback.
- Launch: the host service launches each request once through the setup path (`setup::step`), with the project root as working directory; brief and launch log stay in `<install>/setup/<id>/`. States, no-start reasons (`runtime missing:`, `sign-in needed:`, `access refused:`), `interrupted` on an unknown outcome and recovery are the [setup contract](standalone-onboarding.md#contract-detail).
- Capacity (owner): an AI request is opened for the human. It takes no § 3 grant; runtime limits, `admission.max`, the emergency hold, Stop, restart, the load gate and launch spacing count only queue workers and reviewers.
- Workspace: under the composer the newest AI request shows its kind, reason and next step; `Open session` opens its native session; replies follow D1–D8. Draft and the last 20 distinct sent texts live in `<install>/tray-requests.json`; picking one fills the input only.
- Retro: `taskq retro` writes the same request for the current project with the retro template: read the use-case Proposals and the board's `ask`/`answer`/`requeue` history, give numbered recommendations, and file the ones the owner accepts with `taskq add`.
- Add project (M10): `Set up with AI…` for a new or plain folder writes a setup request (`service setup`) with that folder as its only target.
- C7 (target, TW6/TW7): archive any message entry; delete one or all archived ones permanently. Delete removes only TaskQ message records and owned attachment copies, refuses a request not yet launched, and never stops a session, changes a task or touches source files or native chats.
- Owner comments on `ask` tasks are plain comments; `fold` ignores them (§ 2).
- Leftover `<root>/.taskq/requests/`, `requests.log` and `retro.json` from older versions stay on disk, unread.

## PM-to-result (#1929)

R1/R13: `add --conversation ID --op-id ID` binds a new held brief to its originating owner chat. The first accepted `hold` carries `conversation: <opaque owner-request ID>`; edited, ignored and later holds grant no association. The create claim binds this reference too. The PM brief names this flag and requires an inspectable held brief and the owner’s Assign action before starting chat-origin work. Existing tasks without a reference keep their task threads; never infer origin from prose, title or equal text.

The originating chat renders the associated board brief, state, current question, append-only answers and result. Assign uses the existing revision-bound Start control once; it never starts from a timer or PM prose. Reply to a task uses the existing answer composer and returns to the PM destination after acceptance; PM and task drafts/files remain independent. Task activity is optional. Completed tasks are read through the existing bounded board history, with explicit paging and exact-task recovery after an open row disappears. An empty association says no linked tasks are loaded, never an inverted range; available older-board discovery stays in a compact disclosure until linked tasks exist. Omit exhausted empty paging controls. A failed read is unknown with retry, not completion.

Working worker threads offer board steer before their first question. Reviewer, ended and unknown attempts explain the write boundary and keep unsent text/files. A receipt proves board delivery, never native consumption. Unknown steer delivery reconciles the same operation and immutable payload.

Q-A3–Q-A5 use one paragraph/record anchor owner with coordinated post-layout restore; native scrolling stays passive. The shared reader retains the native generation plus record/cursor and pixel offset. Board questions, answers, briefs and results use stable task/revision record keys in the same bounded navigation; reflow and thread switching keep their reading offset. A source replacement is explicit and never mixes generations. Wheel-up, upward keyboard/touch movement and reading older output pause follow; only Latest resumes it. Send preserves a paused reading position. Transcript blocks never flex-shrink under a long composer. The same viewport owns a long draft; its tool row keeps Send reachable.

Reply delivery uses an optional immutable `reply` intent in the existing owner draft and `op_id` on the existing native turn. Persist intent before dispatch; Check delivery reads that turn without dispatching. Acknowledgement clears intent only after a matching ID/input readback. Every refusal before turn storage clears the intent and keeps editable input/files, including a failed native-holder probe. Unknown storage/dispatch keeps the intent, text and files. A due watch waits under the existing setup lock until reply acknowledgement, so it cannot overwrite the operation receipt. Older readers refuse a pending new field as unknown and retain bytes; an acknowledged draft omits it, so rollback cannot silently replay an uncertain send. This is owner-request recovery metadata, not task state or another native writer.

Transcript generations use native file identity and the first record prefix. They detect file replacement, changed prefixes and the existing shrink refusal; they cannot prove arbitrary in-place rewriting beyond that prefix. Such provider mutation remains unqualified. Empty/partial-prefix reads contain no accepted record; a changed prefix requires explicit Latest. The native page remains 256 KiB / 200 items, with the existing 16 MiB oversized-record refusal. Recorded-question paging retains the source prefix revision/count separately from the accepted-receipt overlay. A confirmed question/answer tail remains readable during polling lag; reading the older prefix never reopens or re-answers that question. The 600-record resident window also has a 32 MiB text ceiling; a selected range may pin records and must disclose any overflow. Large text uses at most 32,768 UTF-16 units per visible text page with exact Unicode seams and bounded saved offsets. Historical questions read at most 64 whole records / 256 KiB per page (one larger record retains the 16 MiB source ceiling), fenced by project/task/revision and cursor. No large record creates an inner scroll. C2/C7 and D3–D5 retain source, drafts, receipts and authority.

## Conversation time (D-A19)

All Conversations messages, tool summaries/details, briefs, question/answer history, events, sidebar activity and turn/watch facts use one relative-time renderer (UX30-17–19). Labels use `<1m`, `3m`, `2h`, `4d` (ASCII lower-case units); future values say `in <1m` / `in 3m`, never silently clamped. Hover and keyboard focus expose local date, seconds and the IANA zone/UTC offset; accessible names retain the timed event.

Native transcript `updated` is ISO time; `at`/`i` are byte-cursor identities only. Board comment times are seconds; request creation and turn/watch times are milliseconds. Label request creation and turn submission explicitly: neither proves delivery, completion or a changed request state. No issue-creation, earlier-record, read-time or window-open fallback. Missing, malformed, zone-less and unavailable values show Time unknown with a reason. Historical brief/question/result timestamps unavailable in the adapter remain unknown.

On each wall-clock minute boundary, update only label text. Keep record nodes, deterministic native order, keyboard focus and reading anchors. Fixed label geometry prevents boundary changes from rewrapping rows. Existing native transcript/board adapters remain authoritative; no separate event store. Native host and screen-reader acceptance remains separate under R12 and §7.8.
