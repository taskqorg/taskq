# AI requests

Design under [R3/R9](../../taskq.md). [Menu M7](menu.md#m7-ai-entry) · [Use cases](../use-cases/README.md).

Owner decision (#1427): a tray AI request opens a new visible session, like setup ([#1426](standalone-onboarding.md#contract-detail)). There is no operator turn, no conversation storage, no proposal or `rev` confirmation and no request log. The session does the work itself and may act as PM; the owner reads and answers it in its runtime.

Approved target (#1462, not shipped): the composer moves to the workspace and a request opens a session in any available runtime, Claude or Codex, named in the request UI ([TW4](tray-workspace.md#contract-detail)). Messages, archive and permanent delete act on TaskQ message records only ([TW5–TW7](tray-workspace.md#contract-detail)); no TaskQ conversation storage returns.

Owner-approved #1464 scope ([answer 6319522673](https://github.com/taskqorg/taskq/issues/1464#issuecomment-6319522673)) accepts the seven-image layout and the Claude-only handoff; native workspace/Codex qualification remains release work. #1580 implements the separately approved draft/file workspace below; no conversation store or proposal protocol returns.

Owner-approved #1467 scope ([answer 6328516821](https://github.com/taskqorg/taskq/issues/1467#issuecomment-6328516821)) accepts M's seven-image layout and message-only outcome. Combined #1465/#1466 acceptance and native workspace qualification remain separately gated.

## Native dialogue workspace (C1–C9)

The [#1580 owner answer](https://github.com/taskqorg/taskq/issues/1580#issuecomment-6343852087) selected native-only dialogue; the owner reversed that part on 2026-10-23: replies continue in the workspace per [D1–D8](#workspace-dialogue-d1d8). A1/A7 keep workspace drafts, files, request history and Open session. R3 and TW5–TW7 retain authority. The archived design's operator, transcript, proposal protocol and active-only archive guards do not return.

- C1/C2 one thread screen (#1699, replaces the #1691 Inbox section and the request/session split of C1): Conversations lists threads: TaskQ-known owner drafts/requests and one task thread per board task with an open question or a question event, plus every task opened from the menu. Menu-opened event-free task identities remain in Recent for revisit; they are navigation metadata, never task state. A request event belongs to its own conversation thread; no thread is created for an event without a source. Rows are compact: task or project, title, an Unread or Needs reply marker and one open action. Work sessions stay a distinct R6 list behind the toolbar. History contains the last 20 submitted texts and fills only. There is no scan of unrelated native chats.
- C2/C7/CW1–CW8: New clears search and focuses its own draft. The first draft line is a temporary title; an explicit name wins. Each draft retains project, text, caret and record scroll. Owner, task and event threads share one selection model. Recent and Archive retain their own selected thread identities; switching lists restores a visible selection from that list or shows an empty detail. A hidden or unavailable selection never leaves another list’s detail visible. Clear search keeps selection. Archive any item, stay in the list, choose another and offer Undo; Restore/Undo opens the item. Archiving a task thread archives only its TaskQ event record; the board task, native session and other event records stay. Each thread keeps draft, files, caret, selection and scroll across switches, Settings and close/reopen. Close hides, never sends, cancels or archives. Pin, enlarge/restore and resize use the native window. Explicit Detach/Return transfers one editable owner; reopen raises that owner. Restart restores metadata when opened and returns ownership to main without reopening detached windows.
- C3 composer: one shared composer owns context, editable text, Attach, attachment chips/removal, validation and Send on every surface that takes owner text: a new request, a D2 reply and a task answer. A task answer keeps source option numbers and exact-revision semantics ([answer card](answer-card.md)) inside its task thread; a question that changes while typing fences Send, keeps the draft and says so; sharing the composer adds no file-answer transport. A dialogue composer names the recorded session runtime of the request handoff and says the reply goes to that session from this window. Unsupported inputs (PDF, file answers) stay explicit.
- C5 events (#1699): there is no Inbox section. The menu Conversations entry opens Conversations with the list visible and the first unread thread selected, an actionable question first; with no events it restores the last thread. Opening, selecting or reading a thread acknowledges nothing; Mark read is explicit and its receipt shows in that thread only, never in the shared status line or on other routes. Every menu task offers one Conversations entry, including Later, Doing, Review and Ask. Opening a task with no event retains its own task thread in Recent; nothing is duplicated, acknowledged, sent or launched. A task thread has one identity heading; row metadata stays compact and technical IDs stay in Details.
- C5 rows: threads show plain delivery errors; request, operation and correlation IDs appear only in details. A failed or unknown delivery offers Check delivery with the same operation, never a resend. A retained pending-correlation conflict is named in user terms (an earlier answer with this operation is still pending with different content) and investigated before retry; never suppress the guard.
- C3: Selection/drop reads explicit files, never source paths. UTF-8 text/Markdown and PNG/JPEG/WebP: at most 4 files, 5 MiB each, 20 MiB per draft and 100 MiB of owned copies per installation. Empty files, binary text, directories and executables are refused. Image selection rejects unreadable data and dimensions above 8000 pixels per side. PDF is unsupported (0 pages): no qualified page-count validator. Draft text is at most 64 KiB; local metadata stops at 8 MiB. No truncation or automatic history eviction. Show these limits before selection and preserve other files/draft on refusal. Image preview uses local bytes only.
- C3/C7: Native storage owns copies in `<install>/setup/<request-id>/attachments/`, keyed by SHA256. Send freezes ID/hash/length and verifies bytes before handing paths to the native session's Read tool. File contents never enter command history or telemetry. Remove affects only the draft reference. Permanent deletion removes owned copies and metadata, never source files/native chats; deletion fences prevent resurrection.
- C4: One immutable launch request per item. Native preference revision fences stale saves; Send persists its immutable input before dispatch. Unknown/partial delivery retains draft/files; Check delivery reads that same ID without replay. New/selection/reload/detach/close never dispatch. A next draft is editable while launch waits; an explicit New from draft creates a separate owner request. Continue replies in the workspace (D2) or through Open session. Cancel acknowledges only a pending launch under the setup lock; launching/launched/unknown requests require the native runtime. No enabled runtime Stop without an adapter.
- C5/C6: Board questions keep source numbers, order, recommendation and exact-revision receipts in their task thread; old message and answer routes open that thread; sessions and operation pages return to Conversations; operation review remains in existing reviews. Work-session targets use #1565/R6; missing/remote capabilities stay explicit. Local workspace adds no gateway, grants or task store; its only scheduler is the D6 watch. Remote PM launch uses the separate opt-in [PM exchange](pm-requests.md), never observation/resource authority.
- C7/C9: Extend `<install>/tray-requests.json` for local draft/view metadata, preserving existing request/answer/history fields. Corrupt or unavailable storage refuses writes and leaves existing bytes. Durable setup records remain launch truth. Never infer runtime completion from `launched`. Archive and permanent deletion follow TW6/TW7, including the prelaunch deletion refusal and no trash/undo for Delete.
- C7/TW7: New from draft moves text/context/files to a separate draft ID with same-ID reconciliation, never a launch. Deleting a sent message first preserves independent unsent text and newly selected files as a separate draft, then removes the sent record/copies. Unchanged sent text/files are not recovery sources; independently edited next text survives even when identical. Send freezes its input revision. Copy/storage failure refuses deletion and keeps the original. Deletion readback removes sent content from open views; an unsaved local edit stays visible for copying, never resends.

## Workspace dialogue (D1–D8)

Owner decision 2026-10-23 (target, not shipped): the owner talks to an owner session in the workspace without opening Claude or Codex. Any number of conversations; any one may do PM work; none is special. Phase 1 is the local workspace; DashQ follows.

- D1 Source: the native transcript is the only record. Claude: `~/.claude/projects/*/<id>.jsonl`; Codex: `~/.codex/sessions/**/rollout-*-<id>.jsonl`. TaskQ keeps no copy, index or summary; transient in-memory record offsets and page heights for rendering are not an index, and a saved reading anchor holds only record identity and offset. A missing or unreadable transcript shows unknown, never empty.
- D2 Send: the composer of a launched conversation sends the next message as one native turn, text on stdin, files per C3: Claude `claude -p --output-format stream-json --permission-mode <mode> --resume <id>`, Codex `codex exec --json resume <id> -` ([adapter](../runtime-qualification.md#runtime-adapters)). Never `claude --bg --resume` into a live session: it starts a copy. Send persists the immutable input before dispatch; unknown delivery keeps the draft (C4).
- D3 One writer: at most one turn per session. While a TaskQ turn runs, Send queues nothing and says `working`. Before a turn TaskQ checks for a native holder: Claude `agents --json` lists the session ID, or Codex answers `already has an active writer`; then Send says `open in <runtime>; close it there first` and keeps the draft. Probe 2026-10-23: two concurrent Claude resumes fork the transcript and lose one branch; Codex refuses the second resume.
- D4 View: user and assistant text in order, tool calls as one line each, newest at the bottom. Read backwards from the file end in bounded pages of whole records (256 KiB, at most 200 items; one record over 16 MiB is refused as unknown). Each item carries its record identity: the byte offset where its record starts and its block ordinal. The view mounts one contiguous window of at most 600 items and reads the previous or next page by byte cursor while the window edge is within one viewport (infinite scroll; Load earlier stays); pages of only skipped records continue the read, at most 8 such pages in a row before Load earlier or Load later asks for a user action. Whole records beyond two viewports leave the window, except records that hold a selection, and are read again from the native transcript when needed. A reply for a replaced window or an outdated cursor is ignored. The first visible record and its offset are the reading anchor: prepend, append, font, width and content-size changes keep it within 2 CSS px. The anchor is view metadata in the saved navigation (24 most recent threads, at most 1.5 KiB); returning to the thread reads the page that starts at it, and an anchor whose record is gone is said and Latest opens. The view follows new records only while the reader is at the end of a window that holds the file end; otherwise Jump to latest, labelled New messages when records arrived, is the visible way back, and it or Send resumes following. Transcript reading never acknowledges events. While the view is open and holds the file end, poll the file size every 2 s and append new records. A page load is announced as one short status, not read in full. Unknown record types are skipped. The thread detail owns one content scroll for status, transcript or question, and composer; Status and composer have no separate content scroll. Launch diagnostics, handoff and Status collapse into details above the transcript. Expanded Status, long watch prompts and long questions preserve the reading position and keep the composer reachable at 18–20 px. Archived launched owner threads keep the D4 transcript read-only and require Restore before reply. TaskQ archive does not archive the native conversation; session IDs stay in Details.
- D5 State: `working` (TaskQ turn alive), `idle`, `open in <runtime>` (D3 holder), `unknown`. A turn ends on process exit; Claude's `result` and Codex's `turn.completed`/`turn.failed` give the outcome. Exit alone never says success. The last turn's input, state and outcome live in `<install>/setup/<id>/turn.json`; a restart while it starts is unknown, never a resend.
- D6 Watch: a conversation may hold one watch: `prompt`, `every` (minutes, at least 5) and `events` (subset of `close|failed|ask|blocked|gone` from the project's `.taskq/events`). The service sends `prompt` as a D2 turn when due and the session is idle; matching new event lines since the last watch turn are appended to the prompt and make it due at once. Stored in `<install>/setup/<id>/watch.json` with `last_turn`, `last_outcome`, `next_due`. The emergency hold and Stop pause watch turns; owner Send still works. A watch never creates tasks or grants by itself; the session acts through TaskQ commands.
- D7 Status: a Status control per conversation shows the watch (prompt, every, events), last and next turn, last outcome and the last assistant line, from `watch.json` and the transcript. Set, edit and remove the watch there; no watch reads `no watch`.
- D8 Rules: what to check and how to report live in the session's own files (project rules, memory); the watch prompt points to them. TaskQ stores no PM rule set.

Composer and reading behavior: input grows with text and wrapping, including restored drafts, paste and font/window changes. No manual field grip or inner text scroll. Short input stays at the bottom; a long draft uses the same reading viewport, with Send remaining reachable. Preserve independent draft/caret and a visible message anchor across updates, prepends, disclosure, resizing and switches. Scrolling up pauses following; new content shows a compact latest-message action without moving the view. Only that explicit action resumes following. Reduced motion skips animated jumps. One contextual information control holds technical details; question reason/evidence and primary actions do not require nested disclosures. Board links use the recorded GitHub/GitLab mark and exact accessible destination; unknown providers stay explicit.

## Contract detail

- Request: the workspace Ask AI composer names one registered project (default: the first). Send writes `<install>/setup/<id>.json` with `root` = that project and `brief` = the owner's text inside the fixed request template in `src/setup.rs`, then pokes the host. Empty text or an unregistered project writes nothing. The workspace names the qualified Claude Code runtime; the any-runtime target remains unqualified. A stable request ID binds the project, runtime and literal request. Check delivery reads that same setup record, including after restart; it never creates a new-ID retry. A lost or partial receipt preserves the draft and shows unknown until readback.
- Launch: the host service launches each request once through the setup path (`setup::step`), with the project root as working directory; brief and launch log stay in `<install>/setup/<id>/`. States, no-start reasons (`runtime missing:`, `sign-in needed:`, `access refused:`), `interrupted` on an unknown outcome and recovery are the [setup contract](standalone-onboarding.md#contract-detail).
- Capacity (owner): an AI request is opened for the human. It takes no § 3 grant; runtime limits, `admission.max`, the emergency hold, Stop, restart, the load gate and launch spacing count only queue workers and reviewers.
- Workspace: under the composer the newest AI request shows its kind, reason and next step; `Open session` opens its native session; replies follow D1–D8. Draft and the last 20 distinct sent texts live in `<install>/tray-requests.json`; picking one fills the input only.
- Retro: `taskq retro` writes the same request for the current project with the retro template: read the use-case Proposals and the board's `ask`/`answer`/`requeue` history, give numbered recommendations, and file the ones the owner accepts with `taskq add`.
- Add project (M10): `Set up with AI…` for a new or plain folder writes a setup request (`service setup`) with that folder as its only target.
- C7 (target, TW6/TW7): archive any message entry; delete one or all archived ones permanently. Delete removes only TaskQ message records and owned attachment copies, refuses a request not yet launched, and never stops a session, changes a task or touches source files or native chats.
- Owner comments on `ask` tasks are plain comments; `fold` ignores them (§ 2).
- Leftover `<root>/.taskq/requests/`, `requests.log` and `retro.json` from older versions stay on disk, unread.
