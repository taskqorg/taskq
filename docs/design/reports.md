# Results

## Conversations design checkpoint (#1977)

Conversations is the destination for questions, reports and finished tasks (taskq.md Product). RC1-RC7 define the merged behavior; implementation and native qualification are recorded separately in the review package (R8/R12/R13). Package: [design review](reports-conversations.md), [editable mockup](exploration/reports-conversations.html), [task report](../research/1977.md).

- RC1 Placement: remove the separate Results disclosure/reader. A result opens directly in the selected Conversations thread's reading pane. Preserve the conversation sidebar, per-thread reading positions, drafts, Back/List and Previous/Next; notifications deep-link to that same result. Legacy Results destinations redirect to Conversations with the exact board/task/result identity. The CLI `results` and `reports` alias remain compatible.
- RC2 Membership: use [CS1–CS6](tray-workspace.md#conversations-sidebar-1808) Pinned, project and Other groups. A board task has one sidebar identity through question, work and completion; its report/result is appended to its history, not a second conversation. An originating PM conversation keeps its linked task outcome. Only independently opened tasks have their own task row. Neither a report nor a completed task enters queue/admission counts.
- RC3 Filters: All is the default. Needs reply selects actionable questions; Needs decision selects reports with no terminal decision, including read/Later reports; Finished selects all collected closed tasks, including accepted, dropped and made reports. Search intersects the selected filter across collapsed groups. Pinned takes precedence in every filter; search/filter reveal matching groups temporarily without replacing saved collapse. Counts describe loaded matching rows; incomplete collection says unknown, never an authoritative total. More uses the existing close-time/number cursor and preserves selection and scroll. Closed history stays pageable; no new board read on selection.
- RC4 Attention: read and decided are independent. Opening content queues the existing asynchronous SHA-bound read marker after display; opening the window/filter acknowledges nothing. A read but undecided report keeps Needs decision. Accept records acknowledgement of the exact result, never approval/publication/start. Drop and Make tasks are terminal report decisions; Later keeps a read report undecided. Decided results remain in Finished. Local Archive hides a row only on this host, preserving its board decision; it neither decides nor deletes report content. Results cannot use Delete to delete board tasks or reports.
- RC5 Reactions: [shared decision-card extension](answer-card.md#result-decision-candidate-1977). The main question offers 1 Accept, 2 Later, 3 Drop, in that order, with exactly one contextual recommendation. Other actions reveals the correction question, 1 Reopen and 2 Follow up. Both collect one reason and submit through the shared composer. Reopen creates a linked held correction successor; Follow up creates linked held additional work. Originals stay closed, preserving dependencies. No action starts work.
- RC6 Proposed work: reports keep Question, Recommendation and readable Proposed tasks before Full report. Beside the proposed tasks, a shared question offers 1 Make tasks and 2 Keep report. The displayed titles, goal/acceptance disclosures and held-only effect are the review; no additional confirmation dialog. Empty/invalid proposals disable creation with a reason. Keep report performs no board write. Existing immutable create claims, first-winner reservation, partial receipts and separate Start remain required.
- RC7 Delivery: accepted, failed, partial, stale and unknown receipts stay beside their source card. A successful action offers numbered Next actions; creating work recommends Read held draft, otherwise Next unresolved item, with Stay here available. Never auto-navigate or auto-start. Pending/unknown delivery disables conflicting decisions and reconciles the same immutable request. A late receipt cannot move focus or decide a newer SHA. Stale result actions refuse until the exact current result is reviewed; unlike free-text task answers, result actions cannot be converted into task notes.

Build impact: reuse `reports.rs` collection/claims and the shared answer-card renderer/controller with a typed result adapter. Add durable SHA-bound report acceptance; preserve ordinary result markers. Expose decided history from the collected projection so Finished can retain it; an active-only page cannot prove absence. Reconcile Accept with an in-flight Make tasks reservation before writing; it cannot hide or undo partial drafts. Extend receipt/idempotency handling to retain the operation and source identity through refresh/restart. Mockups alone do not prove these requirements. No §2 queue transition changes.

## Operator flow

Reports are one kind of completed result. A finished trusted task appears once, with a SHA-bound seen state, in the tray Notifications panel and Conversations; already seen results add no new attention. Background-collected summary, checks, open items, PR and evidence support local list, open and next/previous navigation. Both kinds use the RC5 shared decision and correction cards; reports additionally retain the RC6 proposed-work question.

The shared use case is: work finishes; the service collects the result; the operator notices it where they already work, reads the cached decision card and chooses the appropriate reaction. Accept acknowledges a delivered result; Follow-up proposes new work; Reopen requests more work on the original outcome. A read or acknowledgement is not permission to start work. Missing or stale data remains unknown.

Reopen creates a held successor linked to the original task and carrying the operator's reason. The operator reads it back and starts it separately. The original stays closed, preserving every dependency that already read it done; no §2 transition changes. Follow-up also creates a linked held draft, for additional work rather than correction. Both use immutable create claims: repeating the same displayed SHA, action and reason reconciles the original receipt. Changed reasons are separate requests. Accept acknowledges the exact result; it neither approves an unmerged candidate nor changes task state.

An ordinary card shows Changed, Checks and Open verbatim from the accepted hand-in and close verdict, with their PR and evidence links. Missing hand-in data reads unknown. Reading sends an asynchronous seen marker after local display; it does not accept the result. Accept sends a separate marker. Follow-up and Reopen expose a reason field and one submit action, then show the held draft link for readback. Next and Previous use the same collected rows; neither navigation nor opening history performs a board read.

Trusted, unedited `taskq: result-read <sha>` and `taskq: result-accept <sha>` comments record ordinary result attention. These are metadata, ignored by the lifecycle fold. Reports use their SHA-bound markers below; ordinary Later and Drop use corresponding result-later and result-drop metadata. A source result SHA is the identity; tasks without a recorded result use `close-<comment id>` (or their trusted issue number when no close entry exists) and explicitly label their missing hand-in unknown. Unknown collection never means zero results.

The service reconstructs the projection from closed board tasks, including summary and immutable report content. It refreshes updated closed tasks incrementally and invalidates on close events. The existing local sleep tick publishes completed collection without forcing another board pass. Restart hydrates only the disposable projection, then verifies it against the board; stale data stays visible with its reason. Every view uses this projection, including the legacy Completed list. This removes a separate history read before the operator can assess a result.

## Contract detail

Taskq.md §7 owns this lifecycle (R13). Finished research and proposals deliver a report by PR and pass review before closing. An owner decision is required before close only when another task waits on that decision. Reports are closed tasks, never queue states: admission, focus, capacity and Held/Blocked/Ask counts ignore them (R1, R6).

The report at `docs/research/<N>.md` contains Question, Findings with source links, Options with pros and cons, Recommendation and Proposed tasks. Follow-ups use one fenced `taskq-tasks` JSON array under Proposed tasks. Each object has `title`, `goal`, `acceptance` and optional `scope`, `type`, `runtime`, `priority`; §1 input limits apply. An empty array explicitly proposes no tasks. No executable instructions or grants come from report content.

The service initially collects closed task pages in the background, independently of execution supervision, then refreshes issues updated since the last successful board observation, with a one-second overlap. Changed open or untrusted objects leave the projection. Each ordinary pass schedules a due collection; observed close events invalidate it immediately. The collector reuses unchanged issue projections only after reading beyond their board update second, and immutable content by result SHA. Its rebuildable projection lives in `<root>/.taskq/reports.json`; it is never decision truth (R1). `status.json`, and so `service status --json`, carries only `complete`, `reason`, `observed` and the `count`, `unread` and `history` counts, so that output stays under 256 KB for 7 boards with 500+ reports each (#1975); rows come from `taskq results`. A status written before the split still carries rows inline: `results` reads them until `reports.json` exists, and `service status --json` cuts them to counts. Collection errors retain previous rows with an unknown reason and do not advance the cursor. Missing, incomplete or older-than-`ttl` data reads unknown; an unavailable report has its own reason. Collection, list and open timings use built-in telemetry (R12).

Menu, Conversations and CLI read this collected projection without board calls or a UI polling timer. A validated report adds `Report: docs/research/<N>.md` to the accepted result comment, also for docs proposals; unrelated docs remain ordinary task results. Discovery requires no later label write. Legacy research whose decision was already answered stays out of active Results and attention but remains in Completed history. Rows remain newest closed first; duplicate project registrations cannot duplicate reports. More uses the last close-time/issue-number cursor, so decisions removing earlier rows cannot skip unseen reports. Opening or reading never changes order. Content always belongs to its exact result SHA, never a moving branch or local checkout.

The operator flow has four steps, each with one purpose:

1. Notice: unread reports appear in the tray Notifications panel and the Conversations thread list; the bell counts result notifications, while the Conversations header badge counts only messages/questions. This brings the decision to the operator's existing workplace. Queue and admission counts still exclude reports.
2. Understand: one click opens the collected card with Question, Recommendation and Proposed tasks first, as readable text and task titles. This exposes the decision without requiring a long document read. Full report expands in one action.
3. Decide: use the RC5/RC6 source-numbered questions without an intermediate confirmation or PM relay. Accept acknowledges; Make tasks creates only displayed held drafts; Later keeps the report undecided; Drop dismisses its decision. Read acknowledgement is asynchronous after successful local display, so a board write never delays reading. Its failure remains visible and unread stays unconfirmed.
4. Continue: the RC7 Next row offers the next matching unresolved item or Stay here; held creation recommends readback first. The source and its draft remain in Conversations. Readback updates the view and wakes collection; failures retain receipts for reconciliation.

In-flight receipts overlay only their own SHA's markers, preserving source content and close order. The collected `comments_through` revision retires an overlay once collection reaches its readback; an older acknowledgement cannot replace a newer report or reservation.

Only trusted, unedited issue comments count. `taskq: report-read <sha>` marks that report read. `taskq: report-accept <sha>` acknowledges it and retains it in Finished. `taskq: report-later <sha>` keeps it visible and read. `taskq: report-drop <sha>` dismisses it. `taskq: report-making <sha>` reserves Make tasks before any creation; `taskq: report-made <sha>` records created issue numbers and completes it. The first Accept, Drop or make-intent wins across hosts: a make-intent keeps the report visible until its receipts reconcile, and a concurrent Accept or Drop cannot hide newly created drafts. These are report metadata, not queue transitions. Markers bind to the report SHA; an old marker cannot decide a newer report. Read/Later cannot undo a terminal decision. No local read or decision store exists.

The report card uses RC5/RC6 inside the Conversations reading pane. List and Back to conversation preserve the filtered sidebar and original draft. Make tasks explicitly authorizes the displayed follow-ups as held drafts, with `Depends on #<report>` linking their source. It never starts them. It validates proposals and the board's `create_claim_issue` before reserving Make tasks: without the key it first settles the claim issue as `taskq claim-issue` does (reuse, find or create; key written and read back), on GitHub and GitLab alike, and a refused or unknown claim issue reserves nothing. It then reuses §1 immutable create claims; stable report/SHA/item operation IDs reconcile retries read-only. Partial or unknown creation retains the report and names the receipts; it never claims a completed decision. Later keeps the report read. Drop removes it from Needs decision while retaining Finished content, without creating tasks or reopening research. Empty proposals disable Make tasks.

`taskq results [N] [--action open|read|accept|followup|reopen|later|drop|make] [--sha SHA] [--text REASON] [--page N|--before TIME:N] --json` serves both interfaces and PilotQ callers. `reports` remains an alias. The existing JSON `reports`/`report` fields now carry both kinds, distinguished by `kind: task|report`; older report rows without `kind` render as reports. No task number lists one collected page; `open` returns exact cached content without acknowledging read. The UI separately sends `read` after successful display. Writes require the displayed identity and owner CLI context; worker/reviewer attempts cannot decide results. Follow-up and Reopen require a one-line reason of at most 180 characters. Every write is read back and wakes collection; actions validate current board state even when the displayed cache is stale. Closed tasks remain closed; these comments do not amend the §2 queue model and older versions safely ignore them.
