# Results

## Operator flow

Reports are one kind of completed result. A finished trusted task appears once, with a SHA-bound seen state, in the tray Notifications panel and Conversations; already seen results add no new attention. Background-collected summary, checks, open items, PR and evidence support local list, open and next/previous navigation. Ordinary task reactions are Accept, Follow-up and Reopen; report reactions retain Make tasks, Later and Drop.

The shared use case is: work finishes; the service collects the result; the operator notices it where they already work, reads the cached decision card and chooses the appropriate reaction. Accept acknowledges a delivered result; Follow-up proposes new work; Reopen requests more work on the original outcome. A read or acknowledgement is not permission to start work. Missing or stale data remains unknown.

Reopen creates a held successor linked to the original task and carrying the operator's reason. The operator reads it back and starts it separately. The original stays closed, preserving every dependency that already read it done; no §2 transition changes. Follow-up also creates a linked held draft, for additional work rather than correction. Both use immutable create claims: repeating the same displayed SHA, action and reason reconciles the original receipt. Changed reasons are separate requests. Accept acknowledges the exact result; it neither approves an unmerged candidate nor changes task state.

An ordinary card shows Changed, Checks and Open verbatim from the accepted hand-in and close verdict, with their PR and evidence links. Missing hand-in data reads unknown. Reading sends an asynchronous seen marker after local display; it does not accept the result. Accept sends a separate marker. Follow-up and Reopen expose a reason field and one submit action, then show the held draft link for readback. Next and Previous use the same collected rows; neither navigation nor opening history performs a board read.

Trusted, unedited `taskq: result-read <sha>` and `taskq: result-accept <sha>` comments record ordinary result attention. These are metadata, ignored by the lifecycle fold. Reports retain their existing markers and decision rules. A source result SHA is the identity; tasks without a recorded result use `close-<comment id>` (or their trusted issue number when no close entry exists) and explicitly label their missing hand-in unknown. Unknown collection never means zero results.

The service reconstructs the projection from closed board tasks, including summary and immutable report content. It refreshes updated closed tasks incrementally and invalidates on close events. The existing local sleep tick publishes completed collection without forcing another board pass. Restart hydrates only the disposable projection, then verifies it against the board; stale data stays visible with its reason. Every view uses this projection, including the legacy Completed list. This removes a separate history read before the operator can assess a result.

## Contract detail

Taskq.md §7 owns this lifecycle (R13). Finished [experiments](#experiments) deliver a report by PR and pass review before closing. An owner decision is required before close only when another task waits on that decision. Reports are closed tasks, never queue states: admission, focus, capacity and Held/Blocked/Ask counts ignore them (R1); R6 lists the undecided ones in [Decide](#decide).

The report at `docs/research/<N>.md` contains Question, Findings with source links, Options with pros and cons, Verdict, Recommendation and Proposed tasks. Follow-ups use one fenced `taskq-tasks` JSON array under Proposed tasks. Each object has `title`, `goal`, `acceptance` and optional `scope`, `type`, `runtime`, `priority`; §1 input limits apply. An empty array explicitly proposes no tasks. No executable instructions or grants come from report content.

The service initially collects closed task pages in the background, independently of execution supervision, then refreshes issues updated since the last successful board observation, with a one-second overlap. Changed open or untrusted objects leave the projection. Each ordinary pass schedules a due collection; observed close events invalidate it immediately. The collector reuses unchanged issue projections only after reading beyond their board update second, and immutable content by result SHA. Its rebuildable projection lives in `<root>/.taskq/reports.json`; it is never decision truth (R1). `status.json`, and so `service status --json`, carries only `complete`, `reason`, `observed` and the `count`, `unread` and `history` counts, so that output stays under 256 KB for 7 boards with 500+ reports each (#1975); rows come from `taskq results`. A status written before the split still carries rows inline: `results` reads them until `reports.json` exists, and `service status --json` cuts them to counts. Collection errors retain previous rows with an unknown reason and do not advance the cursor. Missing, incomplete or older-than-`ttl` data reads unknown; an unavailable report has its own reason. Collection, list and open timings use built-in telemetry (R12).

Menu, Conversations and CLI read this collected projection without board calls or a UI polling timer. A validated report adds `Report: docs/research/<N>.md` to the accepted result comment, also for docs proposals; unrelated docs remain ordinary task results. Discovery requires no later label write. Legacy research whose decision was already answered stays out of active Results and attention but remains in Completed history. Rows remain newest closed first; duplicate project registrations cannot duplicate reports. More uses the last close-time/issue-number cursor, so decisions removing earlier rows cannot skip unseen reports. Opening or reading never changes order. Content always belongs to its exact result SHA, never a moving branch or local checkout.

The operator flow has four steps, each with one purpose:

1. Notice: unread reports appear in the tray Notifications panel and the Conversations thread list; the bell counts result notifications, while the Conversations header badge counts only messages/questions. This brings the decision to the operator's existing workplace. Queue and admission counts still exclude reports.
2. Understand: one click opens the collected card with Question, Recommendation and Proposed tasks first, as readable text and task titles. This exposes the decision without requiring a long document read. Full report expands in one action.
3. Decide: Make tasks, Later and Drop are direct buttons, without an intermediate confirmation or PM relay. Make tasks creates only the displayed held drafts; Later takes a revisit date, records read and keeps the report; Drop dismisses it. Read acknowledgement is asynchronous after successful local display, so a board write never delays reading. Its failure remains visible and unread stays unconfirmed.
4. Return: Back restores Conversations and its draft. Successful decisions update the current view from their readback and wake background collection; failures retain the card and receipts for reconciliation.

In-flight receipts overlay only their own SHA's markers, preserving source content and close order. The collected `comments_through` revision retires an overlay once collection reaches its readback; an older acknowledgement cannot replace a newer report or reservation.

Only trusted, unedited issue comments count. `taskq: report-read <sha>` marks that report read. `taskq: report-later <sha>` with a second line `until <UTC>` keeps it visible and read and out of Decide until that time; the newest Later counts, and a Later without a date (older versions) is not a decision. `taskq: report-drop <sha>` dismisses it. `taskq: report-making <sha>` reserves Make tasks before any creation; `taskq: report-made <sha>` records created issue numbers and completes it. The first Drop or make-intent wins across hosts: a make-intent keeps the report visible until its receipts reconcile, and a concurrent Drop cannot hide newly created drafts. These are report metadata, not queue transitions. Markers bind to the report SHA; an old marker cannot decide a newer report. Read/Later cannot undo a terminal decision. No local read or decision store exists.

The report card shows the report, its issue link and Make tasks, Later and Drop. In Conversations, an open report gets one scrollable reading area; returning to the list or collapsing Reports restores the conversation and preserves its draft. Make tasks explicitly authorizes the displayed follow-ups as held drafts, with `Depends on #<report>` linking their source. It never starts them. It validates proposals and the board's `create_claim_issue` before reserving Make tasks: without the key it first settles the claim issue as `taskq claim-issue` does (reuse, find or create; key written and read back), on GitHub and GitLab alike, and a refused or unknown claim issue reserves nothing. It then reuses §1 immutable create claims; stable report/SHA/item operation IDs reconcile retries read-only. Partial or unknown creation retains the report and names the receipts; it never claims a completed decision. Later asks for a revisit date (default one week) and keeps the report read. Drop removes it without creating tasks or reopening research. Empty proposals disable Make tasks.

`taskq results [N] [--action open|read|accept|followup|reopen|later|drop|make] [--sha SHA] [--text REASON] [--until UTC] [--page N|--before TIME:N] --json` serves both interfaces and PilotQ callers. `reports` remains an alias. The existing JSON `reports`/`report` fields now carry both kinds, distinguished by `kind: task|report`; older report rows without `kind` render as reports. No task number lists one collected page; `open` returns exact cached content without acknowledging read. The UI separately sends `read` after successful display. Writes require the displayed identity and owner CLI context; worker/reviewer attempts cannot decide results. Follow-up and Reopen require a one-line reason of at most 180 characters. Later on a report requires `--until`, a future `YYYY-MM-DDTHH:MM:SSZ` time. Every write is read back and wakes collection; actions validate current board state even when the displayed cache is stale. Closed tasks remain closed; these comments do not amend the §2 queue model and older versions safely ignore them.

## Experiments

An experiment task tests an idea and ends in a decision, whatever its type label ([specq experiment tasks](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#experiment-tasks)). Taskq treats a task as an experiment when it carries `research` or its body has a `Hypothesis:` line; research, design and proposal tasks are experiments. Code, docs and asset experiments deliver the same report at `docs/research/<N>.md` and register it with `Report: docs/research/<N>.md` in their result.

The report has a Verdict section, and the reviewer's `close --text` carries one `Verdict: confirmed|refuted|inconclusive <evidence>` line after Changed. `inconclusive` names the missing evidence and how to get it. Close refuses an experiment without a valid Verdict line and leaves it in review. Before publication, close writes the label `verdict-<v>` (removing any other `verdict-*` label) and reads it back; an unconfirmed label refuses the close. The collector reads the verdict from that label, else from the accepted close's `Verdict:` line, else `unknown` (legacy reports).

## Decide

An undecided report is a visible report whose outcome nobody decided: no Make tasks (made or in progress), no Drop, and no Later whose revisit date is still ahead. Legacy answered research stays out. At its revisit date a Later report returns.

`taskq status` prints `Decide:` after Questions, from the collected projection without a board call: `| Report | Verdict | Age | Recommendation |`, one row per undecided report, oldest close first. Report links the issue; Age is the time since close; Recommendation is the first line of the report's Recommendation section (≤ 120 characters). Missing, incomplete or stale collection prints `Decide: unknown (<reason>)` instead of rows. `status --json` adds `decide` `{complete, reason, rows}`, each row `{n, title, url, sha, verdict, closed, age_s, recommendation, later_until}`.

The PM reads Decide each tick and keeps its rows in `Next:` until decided: it decides technical outcomes itself through `taskq results` and asks the owner only product, scope or visual outcomes as decision questions. No task starts on an undecided outcome.

In the app, the Reports list shows the Decide rows first, oldest first, with verdict and age. A row opens the existing report card (Make tasks, Later with a date, Drop); a decision removes the row after its readback. #1977 later moves the card into Conversations.
