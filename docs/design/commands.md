# Commands

`taskq balance [claude=N codex=N antigravity=N | --clear]` reads or replaces this local host's runtime weights. Only an owner-authenticated CLI can write; all values are integers 1..1000000, duplicate/unknown runtimes refuse before writing. An omitted runtime loses its previous weight. `--clear` accepts no assignments. This is a host policy save with readback, not evidence of service application; existing attempts remain unchanged. [Balancing](../../taskq.md#balancing).

Command syntax, task bodies, outputs, op ids and receipts.

## Contract detail

Linked from `taskq.md` [§ 1](../../taskq.md#1-tasks) and [§ 5](../../taskq.md#5-commands); this text binds like the contract (R8, R13).

### Task body written by `add`

`add` writes these sections in that order, then dependencies: Goal 1-2 lines; Acceptance 1-8 items, one line each, unlabelled (a typed `A<n>.` is refused);

Scope optional, 1-4 bullet lines; `--rules "<ID>, <ID>|all"` adds a line `Rules: <IDs>` that scopes the [rule gate](rule-ids.md#contract-detail) and is refused unless each ID is a `taskq.md` rule ID; with `--op-id`, a last line `op-id: <id>` marks the create for read-only recovery. Title ≤ 80 characters; body lines ≤ 240. Short imperative sentences: Goal names the user outcome; each Acceptance a visible check; Scope a boundary. Headings on their own lines; one blank line between sections. More than eight checks: split before filing (R2).
Task text lint (§1 Task text): `add`, and `start` on the issue's Goal and Acceptance, refuse each `R<n>`, `§<n>` or `§2.<k>` that `taskq.md` does not define and each `` `taskq <command>` `` span whose command is in neither `taskq help` nor `taskq.md`, naming every term; `new R14` names a rule the task adds. Scope and links are not read.

### Held dependency amendment

`taskq deps N --board URL --deps LIST --op-id ID --revision R [--json]` is an owner/PM operation on the configured board. URL is the exact board URL from status (without an issue number). LIST is comma-separated `#N` or `owner/repo#N`; empty clears dependencies. Read `taskq inbox N` for R. A worker, reviewer or service environment refuses before writes. The target must be trusted, open, held, lack `taskq`, and have no accepted start in its history.

Log entries `deps R`, `deps-write ID`, `deps-release ID` and `deps-done ID` keep held state. The accepted intent stores the original and replacement body plus the exact request on the board. It fences all other task mutations until completion. Only one native writer may edit; an interrupted writer retains its claim until a verified later boot proves its request tree exited. The service reconciles pending intents. Unknown body or write readback retains the fence; retry the identical command for discovery. A changed body refuses overwrite. Readback requires exact replacement body, held state and absence of admission labels before completion. No labels, title, placement or unrelated body bytes are changed. Dependencies use normal §1 open/unknown blocking after start.

A repeated ID with the same board, task, revision and dependency list returns its durable first completion revision without another edit, including after start. Different payload refuses. Stale revision, started/closed/untrusted target and unauthorized caller refuse without writes. Concurrent intents have one board-order winner. Update all board hosts before use: older readers ignore the new fence entries.

### Outputs, op ids and receipts

- Task writes: `#N <state>`; close adds one publication link/SHA line.
- Other acknowledgements: action, project/version; one line ≤ 160 characters. Capacity writes add `Receipt: <id>`. Batch: one outcome per item.
- [Human replies](answer-card.md#human-replies): `answer`, `steer`, owner `requeue`: text/images/files, no size/count cap.
- `service focus/list/status`: named project, focus, counts, freshness and unknown reason; one field/item per line, ≤ 160 characters.
- `update`, `cleanup`, setup and `selftest`: one outcome per version/path/check ([Core Write](https://github.com/taskqorg/specq/blob/main/caveman/rules/core.md#write)).
- Help keeps full syntax; `inbox`, raw service logs/status JSON and original issue/log text have no display caps ([verbatim diagnostics](https://github.com/taskqorg/specq/blob/main/caveman/rules/changes.md#keep-the-source-and-sink-separate)).
- Refuse unused positionals before actions: `unused positional arguments: <arguments>`; repeat value flags per item.
- `--op-id ID`, `--revision R` (answer, requeue, later, failed, steer, result, ask, close, start, approve; `add`: op id, §1): a seen id returns its first receipt; stale revisions refuse, except owner answers/steers save a §2 note with that id, nothing for a repeat of the winning answer. A raced entry edits itself first. Unknown delivery reconciles the same payload/id.
- Receipt: `--json` prints `{task, op_id, outcome, state, revision, reason, next}`; outcome `accepted` (readback state), `rejected`, `stale` or `unknown` (written, no readback: `Next:` reads `inbox N`, retries the op id); else the lines above. Late answers add `answered {by, text}`, like R6 rows outside `ask`; every surface reads `already answered by <by>: <text>` once. [Task controls](task-controls.md) `taskq.task-controls/1`: start/stop/later/retry, no close.

`add --runtime antigravity` creates a strict `run-antigravity` pin for both worker and reviewer. `service capacity --host H --antigravity N` edits only owner capacity; `--default-runtime antigravity` sets the unpinned preference. These commands never create grants or sign-ins. Quota holds are observed availability, never capacity edits.

### Runtime reroute

`taskq reroute --from <runtime> --to <runtime> [--json]` is owner/PM-only. Both runtimes must be different subscription CLIs (`claude`, `codex`, `antigravity`). It selects this board's open TaskQ tasks with the exact strict source pin, refuses non-ready tasks or unreleased executions and validates labels. Existing attempts keep their original session/runtime/account. Host policy and soft preferences are unchanged.

The first trusted `taskq: reroute <from> <to>` with a final `routing-fence: 1` line on a ready task without unresolved execution reserves its routing fence. It changes no task state; concurrent reroutes and spawns are ignored until matching `taskq: rerouted <id>`. A claim after any fence must carry `routing-revision: <latest accepted fence id>` in its text; stale claims are ignored, even after completion. Historical unfenced audit comments keep their old meaning. The service reads current labels after the routing revision before claiming. Before reading pins for mutation, each finisher acquires `taskq: routing-write <intent id>` by board order, with a `writer:` JSON line naming its machine and native PID/start identity. Only the first unreleased writer is accepted. It re-reads the intent, replaces the source pin and reads back labels, state and execution while retaining that claim. After its last label operation it posts `taskq: routing-release <writer id>`; completion is ignored while a writer remains. A delayed or losing finisher cannot write labels. On a crash, only a matching machine with a verified later boot may release the writer. Caller absence or changed PID identity cannot prove an HTTP child exited. Live, remote, unreadable, malformed or incompletely terminated writers wait with an explicit reason; a normal returning finisher releases after its last synchronous label call. Age alone never releases it. This protects the final API write, including multiple services reconciling the same intent. Every receipt reports that fresh state; partial or unconfirmed writes are unknown, never Ready by assumption. The service automatically reconciles pending intents; retrying the same command reuses the fence. Unknown reads retain it. Upgrade all board hosts before using reroute: older services cannot enforce the fence.

### Host unpin

`taskq unpin N --host H --revision R --op-id ID [--json]` uses the current configured board credential and owner/PM authority; a worker/reviewer (`TASKQ_ATTEMPT` present) is refused. No new grant is created. N is one exact open trusted TaskQ issue; H is the exact existing host name without `host-`. R must match its §2 revision before any board write. Missing, stale, unauthorized or ambiguous input refuses without mutation.

The command writes a durable `taskq: host-unpin` audit intent with the exact board task, host, revision and operation ID, removes only `host-H`, then reads back the issue and log before writing its durable completion receipt. These audit kinds do not change the fold, revision, attempt or execution receipts, including on N-1. Body, runtime and other labels remain unchanged. Active host/process/session/leases stay owned by their original attempt; only future admission sees unpinned placement. This operation never calls restart, cancellation or execution release. Before a later claim, services that observe its audit re-read placement labels and discard stale selections.

A repeated ID with identical input returns its recorded outcome without another label write; changed input refuses. An incomplete intent or uncertain write reads unknown and never replays a removal: inspect the task before issuing a new operation. Concurrent same-ID callers use the first board-ordered intent; only its writer may remove the label. Board comment read-after-write ordering has the same qualification as §3 claims. External manual placement edits remain outside this CLI serialization.

`add` retains §9 labelled-host defaults. Its text and JSON outcomes identify host placement as requested, host default or unpinned; omitted runtime is an admission default, never a requested runtime pin. This output describes creation policy, not a running executor.
