# Advisory readiness

## Contract detail

R8/R12/R13: source-ready and binary-ready are separate, read-only evidence projections. Legacy `Depends on`, admission, explicit dev-build demand, coalescing and the dependency close-time trigger remain unchanged (§1/§4/§8). A source proof, close time, installed release, selection or UI bundle never requests a build, release, restart or admission. No timer or per-merge release is added.

Publication retains an optional `advisory` JSON line in the existing accepted `enqueued` or `close` entry. It binds the board task URL, trusted accepted result entry ID, owning worker attempt and result SHA to the publication repository and PR number. Readers use the accepted transition projection, never the latest raw result text. Edited, replaced, rejected or mismatched results/attempts do not qualify; a rebased result without separately proved coverage stays unknown. Old folds ignore the extra text; no new state or log kind is introduced.

Before queue admission, retain the PR's exact base and head. A private fallback retains them before its merge request. Successful publication retains the integration SHA, merged SHA, historical merge parent and exact-source CI kind/SHA and observed `ci_run_id`/`ci_run_attempt` from the publication readback. Missing run metadata stays null; readers never invent a rerun identity. Source-ready requires the frozen head to equal the accepted result, the historical parent to equal the frozen base, and green merge-group CI on the integration/merged SHA, or private fallback exact-SHA CI on the frozen head. Missing frozen inputs, moved heads, mismatched CI and unproved rebase coverage remain unknown. An already merged PR without a retained pre-integration freeze stays unknown; current main never reconstructs a historical base. A queue that advanced its base is conservatively unknown until evidence of that exact frozen integration exists.

`taskq inbox N --json` and completed task JSON expose `source_readiness` from those retained entries without reading PRs or CI. Its schema 1 keeps the proven accepted-result identity independently of publication readiness: `accepted_result_state`, `task`, `url`, `result_entry`, `attempt`, `result_sha`, and the separately folded `current_result_sha`. Unknown publication or historical base never erases that identity. A rebase can expose the accepted original result while source coverage remains unknown. `evidence.frozen` and `evidence.landed` are nullable typed publication observations, not reconstructed history. Collection reuses publication/readback and runs only during publication, never for each status or admission pass. Missing proof includes a reason; advisory failure does not change publication authority or the canonical gates.

The separate heartbeat `binary-evidence` line and local diagnostics report the embedded source revision and SHA-256 of the publishing executable, its native PID/creation identity, host generation and original native observation time. Hash once per release process: Windows executing-file locking or Linux?s loaded-image handle binds the bytes. macOS pathname replacement during signing has no loaded-vnode proof, so its digest and overall binary readiness stay unknown while the embedded revision and native identity remain visible. Debug builds do not qualify artifact/source identity; do not hash a selected/installed path as running evidence. Local collection requires the existing native service record to match this process and generation. Heartbeat readers bind the installation service identity and require both board and producer freshness; stale/failed/future observations stay unknown. The binary's reported revision is an identity, not proof of source CI or workload health. Missing evidence from older binaries stays unknown even when `current` and healthy markers name a newer release. UI bundle adoption qualifies only that bundle.

## Rollout and rollback

Ship with normal reviewed publication and full integration gate; canonical `python3 scripts/check.py` remains required. Adopt through the existing release procedure, with no activation action granted here. Read back fresh source evidence for a newly published task, and binary evidence from a fresh heartbeat/local status with the exact native owner generation after ordinary activation. Verify the running revision/digest independently against the accepted artifact before any runtime-dependent trigger or batch pilot is enabled by a later contract change. Portable/fake-board tests prove evidence rejection and wiring only, not a deployed artifact or native rollout on another host.

Rollback through the existing qualified release/handover procedure, preserving active executions and ownership. Older folds ignore advisory text and older diagnostics readers ignore the separate heartbeat line; older producers expose unknown. Do not use advisory data to select a rollback, stop a service or change build demand. Historical tasks are not backfilled from moving refs. A missing freeze or CI readback must remain unknown, even if the legacy publication was valid.

Source request and acceptance: [#2391](https://github.com/taskqorg/taskq/issues/2391).

## Producer export

The authoritative producer is `src/readiness.rs::source`, called by `taskq inbox N --json` and completed task JSON. An isolated consumer exports that `source_readiness` object rather than parsing lifecycle entries itself. From an exact producer checkout, `cargo run --locked -- inbox N --json` reads the configured board; it requests no PR/CI history and writes no publication event. Retain the producer commit and executable digest with the exported observations. Historical publication/base gaps remain null/unknown; a replay consumer owns its separate frozen integration base and CI observations and must never substitute them for historical evidence.
