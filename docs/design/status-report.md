# Status report

The human report and the status file that every surface reads.

## Contract detail

Linked from `taskq.md` [R6](../../taskq.md#r6-human-report), [§ 2](../../taskq.md#2-log-and-states) and [§ 4](../../taskq.md#4-service); this text binds like the contract (R8, R13).

### Report parts

Tray/browser project summaries and task rows (M3) reuse [shared project blocks](project-blocks.md), with separate Doing/Review, [counters/filters](task-counters.md) with Held and no Closed counter:

1. `<project> · [board](<url>)`, preceded while a local `status.json` within `ttl` reports a board rate-limit pause (§ 4) by `Rate limit: board requests paused until <time> (<host>)`, else by the § 4 low-budget line, also when this read fails.
2. `In work N · Waiting for answer N · Ready N`. In work: `doing` + `review`. Waiting: `ask`. Ready: `ready`.
3. `| Task | State | Runtime | Session |`, a row per open task except `held`, `ask`, `later`, `failed`, by priority, number; task cells link; sessions link Claude's Remote Control URL, Codex `codex://threads/<id>` on its own host only, elsewhere the DashQ progress page, else plain host; `waiting` rows say `blocked ([#M](url) open)`: each § 1 dependency linked, `open` or `unknown: <reason>`; `--json` rows add `blocked` (`ref`, `url`, `reason`), ready/waiting rows and reviews awaiting a reviewer `admission` ([codes](enrollment.md#contract-detail)); a `capacity` code reads `Waiting for a free slot · <runtime> slots full`; `host-<name>` without a heartbeat, `No host <name>`. Staged tasks (§ 2) show `stage k/n` in State, `Later:`, tray.
4. `Questions (answer N.M):` and `| Question | Brief reason | Options |` with `N.1 <option> · N.2 <option> ★` (★ recommended), a row per `ask` and `review` with options; an owner action (§ 2) reads `waiting for owner: <action>`. Then [`Decide:`](reports.md#decide) rows.
5. `Stale heartbeats:` lists only Doing/Review health warnings from the same `tasks[].heartbeat` projection as JSON and the native UI, after Questions/Decide and before final Next. Each item links task/project and names runtime, host, current attempt/execution (or explicit unknown), heartbeat and progress sources, exact UTC observations and ages, the shared diagnostic and one safe inspection step. Distinguish stale host ownership, missing/error/unknown progress, overdue tools with a fresh lease and input awaiting execution/acceptance; quiet healthy work is omitted. Omit an empty block. Do not repeat these tasks in `Stuck:`. Existing questions, undecided results and queue cadence remain discoverable. The manager chooses action through existing controls; the block never answers, requeues, restarts, replays, releases execution or changes grants/capacity. Existing structured heartbeat fields are sufficient; add no second detector or thresholds.
6. `Held: [#N title](url), ...`, then `Later:` (timed: `until <local time>: <reason>`), one line each; then a `Failed:` reason table; then `Stuck: [#N title](url) (<state>, <age>), ...`: last log entry ≥ 2 h old in `held`, `ask`, `later`, unleased `doing`/`review` (§ 3), or at once `waiting` with every blocker closed. A current `doing`/`review` attempt with pending input and an unaccepted Exit is stuck immediately, even with a fresh ownership lease; `--json` rows add `stuck` true and `age_s`. Observe only.
7. Tray running agents follow [M3](menu.md#running-agents) (target: Home panels, TW3). `Hosts: <host> v<version> <age>[ stale][ focus off|unknown][ <rt> limit until|probe <time>][ tray <code>], ...` from heartbeats (§ 4).
8. `Next: 1 <action> ★ · 2 <action>` from the PM ([shared Next contract](https://github.com/taskqorg/specq/blob/main/design/workflow.md#ai-assisted-controls)).

### Status file and events

- Each pass writes `<root>/.taskq/status.json` for `service status`, tray and DashQ: coreq.md common keys, service state, § 5 snapshot (`tasks` with § 2 `revision`; failed passes keep rows with `complete` false), `capacity` (limits, gate, admission, reservations), `requests`, `incident`, `agents` (§ 5, probed ≤ every 5 min), § 8 `access` and `reports` counts (rows: `reports.json`): `service status --json` ≤ 256 KB for 7 boards. `diagnostics`: selected `current` (CoreQ), health `healthy` (§8), lifecycle (consumer), CoreQ (Cargo.lock); [detail](service-version-producer.md#contract-detail). Capacity publishes on each sample; missing or older than `ttl` reads unknown ([specq](https://github.com/taskqorg/specq/blob/main/engineering/verification.md)). Failed publication is logged, blocks release-health marking and preserves supervision.
- Events: a pass appends to `<root>/.taskq/events` one line `<board time> #<N> close|failed|ask|blocked|gone <id>` per observed move (`blocked`: to `waiting`) and new `gone` entry; 30-day bound; offline moves are missing. An R6 stuck task (`review` too) logs `#N event stuck <state> <age>` once until it moves; [churn](profiling.md#contract-detail): >100 notes or >5 unaccepted spawns in 1 h. Detail: [menu](menu.md#contract-detail).

### Task summary comment

Contract detail for [§ 2 Summary](../../taskq.md#2-log-and-states). The summary comment's lines: `**<State>**`, `result <sha7>` while open, the PR/MR link, the close's merge receipt or `<role> running`, joined by ` · `; then in `ask` the open card, in `review` the result's `Changed:`/`Open:` (a pending publication's once written), when closed the close verdict's, in `later`/`failed` `Reason:` with its first line;
then `Files: ` with ≤ 3 file links of the issue body and outcome entries (newest outcome first, body last; uploads or a file extension), then `and [N more](<comment>)`.

With `deploy`, a delivered task's summary shows `Merged, waiting for deploy` until its first `deployed` entry, which removes it with the label. Then one line per configured environment, in its order, from its first entry: `<project> <version> · <env> · <UTC time>`, then ` · <host>` if named. A no-change close shows none. `taskq status` adds `Waiting for deploy: N tasks, oldest <age>`, each task linked.

### Snapshot contract

Consumers (DashQ, the tray, PilotQ) read results, states and vocabularies from typed `status --json` fields and never re-parse board text (#2014, [research](../research/1981.md)).

- Ownership and execution health are separate. Preserve the pending `#N attempt` heartbeat lease and all input/execution fences. For current pending input behind an unaccepted Exit, include that exact execution in `tasks[].executions` with `release: "exit"`, `state: "unknown"` and the missing-agent/acceptance cause and safe recovery action in `reason` and `execution_wait`. The row's wait text names the exited agent and required input recovery. No fresh host or running heartbeat overrides the board's Exit or establishes input acceptance. Every snapshot source applies this immediately, so PM observers see `stuck: true` without an age threshold or a new task comment. The existing stuck log emits once per blocked period. Quiet running tasks and ordinary admission/input waits keep their existing behavior. These projections neither release assignment nor authorize resubmission.

- `verdict`: each task row carries the § 7 fields of the accepted `result` entry behind its current result: `changed` (text or null), `checks` (one string per `Checks:` line, in order) and `open` (text or null); continuation lines stay in their field, other fields and the card after a blank line are left out. A row without a current result carries null.
- `vocabulary`: `states`, one `{id, name, label}` per state in counter order (`label` is the canonical board label, `waiting` reads `q-blocked`), and `telemetry` with the request `errors`, `stage_errors` and `runtimes` codes. `status.json` carries the same object.
- Schema 1 grows only by new keys. `tests/fixtures/status-snapshot.schema.json` describes it; `tests/fixtures/status-snapshot.json` is the golden output (`status_json_matches_the_golden_fixture`, `TASKQ_BLESS=1` rewrites it) and must meet the schema (`status_json_meets_the_released_snapshot_schema`).
- Each release publishes both as `taskq-<version>-status-snapshot-schema.json` and `taskq-<version>-status-snapshot-fixtures.json`, covered by `SHA256SUMS` and provenance like the [answer card](answer-card.md) assets.

Conversations read-only source identity: each task may carry `worker: {attempt, session, role}` from its last accepted worker projection, independent of the current `attempt`, `session` and `role`. Ask and ended attempts retain this source for bounded history reads; it never supplies task controls, execution health or admission authority. The tray resolves its native target through the same owning-host attempt log.

### Task execution health

R6/R12/R13: `tasks[].heartbeat` is an advisory projection, independent of task state and execution/admission authority. Every task detail (Home, project, saved View and Conversations) shows host/attempt, source, last observation, age, freshness and diagnostic reason. Doing/review rows reserve one fixed warning slot with an accessible name and a textual diagnostic; healthy rows keep the same geometry. Missing, duplicate, invalid, stale or failed observations are explicit unknowns, never healthy. Tasks without a live attempt say not applicable.

- Logical Doing/Review is not native work. `heartbeat.executor` names a confirmed active executor, input awaiting execution/acceptance, or unknown observation from the exact current execution. A folded answer/steer with no new executing/accepted receipt says `awaiting execution`; it never implies a native turn or authorizes resubmission.
- Host observation comes from the unique trusted owning host issue, using board `updated_at`, board response time and project `ttl`. Fresh host ownership never proves progress. An absent matching attempt lease is unknown even on a fresh host.
- Execution progress comes from the owning runtime's exact current source, published in its existing `execution` heartbeat row. Sampling observation times do not force a board write; the existing heartbeat cadence and meaningful state changes still govern publication. Read only bounded incremental native records; do not export tool arguments, paths or output. Complete native events update `last_event`; reads, lease renewal, partial records and metadata touches do not. Source errors, replacement, truncation, unsupported events or unbound input stay unknown with a fixed diagnostic.
- Match tool starts and completions by native id, preserving concurrent tools. Native timestamps establish event time where available; otherwise an append's file modification time is a lower bound, explicitly labelled. A tool with an explicit positive timeout uses that deadline plus two project polls for observation. Without a deadline, 15 minutes without a completed native event warns `overdue`: this diagnoses an unbounded tool, not a failed or ended execution. Quiet reasoning without a pending tool is `quiet`, never overdue merely for lack of board comments.
- A current overdue tool makes doing/review `stuck` even with a fresh lease. A matching completion or a newer current execution clears it automatically. Missing/stale/error heartbeat or progress gives a local warning, without cancellation, replay, restart, release, receipt mutation or admission changes. Existing pending-input Exit recovery stays authoritative.
- Record `service.progress.overdue` once per overdue period and `service.progress.recovered` once when observed progress clears it, with task/attempt/execution counters only; existing stuck notices deduplicate the same period. Observation failure is not recovery. `profile watch` reports these task signals before board inactivity and retains separate queue cadence. Healthy quiet doing/review work is not flagged for board inactivity alone.


### Runtime balancing status

Weighted host snapshot rows expose the validated heartbeat `balancing` projection. Unweighted and unknown/incompatible rows retain the existing snapshot shape. Schema 2 carries configured `weights`, per-runtime `load` (`running` occupied/retained slots, `free`, nullable quota `headroom`) and the last-spawn tie hint. The host row's `updated` controls freshness; stale occupancy is not current running work. `taskq status` shows occupancy versus weights and explicit unknown headroom beside each weighted host. Admission reasons retain the selected runtime, occupied slots, owner weight, effective weight and any host-spread decision. [Policy](../../taskq.md#balancing).
