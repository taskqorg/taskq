# GitHub publication waits

Implemented detail of the GitHub `pr` route (#1820, pilotq #106). The decisions are in [taskq.md § 7](../../taskq.md#7-worker-reviewer-publication): conflict is `main-moved`, unknown is pending, failed CI or conflict requeues, and a pending publication stays in review. This page records how the service applies them so that no publication waits silently. Chain check: `github_queue_qualifies_the_merge_result_and_preserves_unknowns` in `src/board/mod.rs` and `publication_stall_shows_its_reason_and_age_then_requeues_on_conflict` in `src/service.rs`.

Each service pass either moves a published task (merged, enqueued, requeued, asked) or names why it waits. A task never stays in review past one pass without a merge-queue entry or a stated reason.

- PR head is not the result SHA (for example, a rebase pushed in review): the PR is not at the result SHA and never merges, so `main-moved` names the PR and both short SHAs. The worker reviews the head and delivers it as a new result.
- PR conflicts with `main` (`mergeable` is `CONFLICTING`, before enqueue or after a `merge_conflict` dequeue): `main-moved` names the conflict files. They are the files changed both on the PR since its merge base and on `main` since that base, read from the board's compare API (Git-free; five at most, then `+N more`; unreadable: `conflict files unknown`).
- Dequeued as `merge_conflict` but the PR is now `MERGEABLE` (the conflicting entry ahead of it left): no conflict remains, so the service enqueues the same head again. The merge queue builds on current `main`; no rebase is needed. Mergeability not computed yet: pending with that reason.
- Enqueue refused for another reason (for example, a required check still running): a failed check at the result SHA is failed CI (`publication-failed`, naming it); otherwise pending with the refusal and the check state.
- No open PR at the result, but a task-branch PR merged at another head (a rebase in review moved the SHA; pilotq #106, PR #114): the service closes the task as published when that head carries the result's patch. Both diffs start at the merge commit's first parent, so merge, squash and rebase merges compare alike. Each side's `git patch-id --stable` is computed from the board's compare reply. That reply gives no file mode, so an added or removed file counts as a regular file (100644). When the patch-ids differ or one is unknown, the head still carries the result when its changes match (#2061, dashq#241): per file the same name, prior name and status, the same removed lines and the same added lines, each in order and without whitespace, with hunk context and positions ignored, because a rebase onto a moved `main` changes context lines and can list a removed line after the added ones. A file whose patch GitHub omits (binary or very large) matches by its blob SHA. The receipt notes which matched: `the result's patch-id` or `the result's changes`. Any other difference or unknown (300 files or more) keeps the owner's `publication-blocked` ask with its `close` option. For a task PR in another repository (#2047) every read is in that PR's repository, never the board repository. Chain check: `a_pr_merged_at_a_rebased_head_with_the_result_patch_closes` and `a_task_pr_named_by_reference_publishes_in_its_repository_and_closes_its_rebased_merge` in `src/board/mod.rs` and `patch_id_is_gits_stable_patch_id` in `src/board/github.rs`.
- On a `publication-blocked` ask, `taskq answer N --text` that starts with an option key (`close:`, `later:` or `retry:`, any case) applies that card option, as `taskq answer N.K` does. A key the card lacks is refused, and the error names each option in the `N.K` form. Other text stays a free-text answer, which resumes the publication. Chain check: `blocked_publication_answer_text_with_an_option_key_applies_it_or_refuses` in `src/service.rs`.
- Each pending pass sets the task's status row `publication` (`reason`; `since`, the `publish` entry time; `age_s`) and its `wait` text `Publication waiting <age> · <reason>`, which the menu and dashboard show. Telemetry records one `checks` stage, outcome `retried`, per distinct reason, never one per pass.
