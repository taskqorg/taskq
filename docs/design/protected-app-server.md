# Protected app-server

## Contract detail

R8/R9: TaskQ supplies a narrow host adapter for external AgentQ/AssetQ Codex app-server consumers. Asset operations remain AssetQ jobs. This is an external consumer launch under §3, never a development-board attempt or resident authority service. Existing worker, reviewer and owner paths retain their APIs.

`taskq service app-server --action prepare|launch|observe|cancel|reconcile --request JSON` accepts `taskq.app-server/1`. The request contains `schema`, an existing `slot` request (the `taskq.slots/1` binding and release key), `policy_revision`, `account`, and an independently obtained `preparation` digest. `prepare` accepts only `schema` and `slot`, derives current revision/account and returns the private host preparation. Unknown fields refuse. No executable, profile, permission, environment, model or grant text is accepted. The operation is the slot's immutable caller/op-id pair; one slot permits exactly one native launch, including after failure, interruption or host restart. The caller retains its original job identity and never replays uncertain work.

Launch is macOS Codex only, with a canonical registered project and explicit existing project Workspace grant. Host defaults, legacy and Full grants, Windows and other unknown enforcement refuse before native input. The adapter uses the existing policy resolver and runtime executable wrapper. It preserves host model/effort and the selected account home; it never changes login, native configuration or optimizer integration. Authority comes from the operator store, not task, environment, receipt or request text.

The host account's home comes from its native OS identity. Ambient `HOME`, `TASKQ_INSTALL` and `CODEX_HOME` must match the existing host locations. Native executable lookup uses the existing resolver against `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin`, `/bin` and the account's existing `.local/bin`, independent of consumer `PATH`. Custom installations and other account-home layouts remain unsupported by this adapter; existing consumers keep their paths. Receipts bind the resolved native image and digest, which consumers match to their qualified artifact. The generated profile additionally protects the adapter/native executable directories and standard host executable directories, including a staged candidate's directory.

This reuses the existing write boundary: its runtime homes, caches and temp exceptions remain; reads and network retain the existing profile's scope. It does not promise confinement of all reads, new network restrictions or isolation from an unrestricted same-user operator. No extra configuration or approval store is introduced.

As with existing Workspace launches, Codex's inner sandbox is disabled inside the required TaskQ Seatbelt; failed outer enforcement never retries native execution without that boundary. Launch and observe use the same environment for the resolver's protected-path set; a changed profile refuses. Occupied or unknown launch receipts retain their adapter release through normal update cleanup until the existing whole-turn slot release.

Supported host Codex arguments are `-s|--sandbox workspace-write|danger-full-access`, `-m|--model <model>`, and `-c|--config` with `model_reasoning_effort=<effort>` or exactly `sandbox_workspace_write.network_access=true`. The existing `-s workspace-write -c sandbox_workspace_write.network_access=true` request retains that config under the required outer Workspace boundary; it grants no authority. Model, effort and account remain unchanged. Network narrowing (`false`), other sandbox modes, unknown config and unknown arguments refuse rather than silently changing their meaning.

The host operation store retains launch intent on the existing slot before spawn. Its protected readback binds canonical project, generated profile digest, native executable path/digest, account/home, policy revision and approver, host generation, operation, supervisor and native PID/creation identities. Requested, saved and verified-effective facts are separate. Effective evidence names native image and effective sandbox queries; it does not claim exhaustive profile equivalence or native workload qualification.

Launch stdout is exclusively native app-server stdout. Native stderr remains stderr. Consumers read authority through a separate `observe` invocation of the trusted adapter. Neither a copied receipt nor a local receipt file authorizes input. Before forwarding native input, the supervisor verifies fresh matching slot authority, unchanged policy/account/executable/profile and exact native identity/enforcement, then commits and reads back its receipt. Every subsequent input delivery repeats authority validation. Refusal closes the input gate; no fallback or fresh identity retry occurs. Unknown process or store observations remain unknown.

Every failed native sandbox query reports its fixed operation and semantic path category (`workspace-probe`, `policy-store`, `taskq-launcher`, `native-executable`, `account-config`, `outside-workspace`, `scope-control`), expected permission, observed permission or unknown result, raw return code and numeric OS error for a query error. Diagnostics never include path values or configuration contents. A query error or permission mismatch still refuses input; diagnostics do not qualify containment or authorize skipping a query.

Kernel path queries use existing trusted filesystem objects, never absent marker paths: the workspace directory for positive write-data, and the policy file, installed launcher, native executable, selected account's config file and host home directory for negative write-data/create/unlink. Their canonical paths, object types and native filesystem identities bind the launch authority and are checked before and after every query. File stamps also bind metadata; directory content changes alone do not change directory identity. Missing, unreadable, replaced or retargeted objects refuse as unknown, including a missing required config or launcher. No canary is created and no query is skipped. Kernel query evidence remains separate from real disposable operation probes.

Cancellation signals only the verified native incarnation. It never releases the slot or proves descendants/turn effects ended. EOF, caller loss, supervisor interruption, child exit and service restart do not attest tool completion. The external consumer retains slot ownership and must reconcile its entire native turn before submitting the existing irreversible slot release. Unknown work stays occupied under §3.

Cancellation is saved even before a native identity exists. A race with process creation may briefly start a child; the gate refuses its input and requests exact termination. A host-generation change, cancelled or unknown receipt, mismatched authority/native/supervisor identity, or changed native enforcement closes the gate. Exact cancellation requires live supervisor/child ownership; an orphan remains unknown rather than targeting a guessed PID.

## Prepared authority and descendant completion

R8/R9/R12/R13: `prepare` authenticates the original reserved slot and actual consumer PID/creation/boot without launching or changing configuration. It saves canonical project, current policy revision/approver, account/home, adapter/native image identities and hashes, effective profile hash and immutable slot binding in the existing host operation store. Repeating preparation returns the original value only while fresh authority still matches. The launch request independently supplies its digest and revision/account; missing or changed preparation refuses before dispatch/input. Launch/observe receipts are never the consumer's source of expected authority.

Each prepared launch consumes one transient `gui/<uid>` launchd generation before registration, with no automatic start/restart and `LaunchOnlyOnce=true`. Its trusted adapter supervisor establishes the existing resolved Workspace boundary for the native client; native spawning/session/group APIs remain available. This changes no ordinary worker launch or operator grant. Private stdio sockets and job metadata live under the existing protected installation and are protected from the native profile. The supervisor and frontend authenticate exact native peer incarnations and adapter image before exchanging the private request. A crash before binding never authorizes another registration, dispatch or operation identity.

The supervisor's same-boot resource coalition is bound durably before native spawn and must differ from the frontend's coalition. Launchd dispatch acknowledgment precedes native input. Cancellation/input loss seals future native input; root exit seals it too. The trusted supervisor then creates no further work. A successful kernel accounting read with only that exact live supervisor remaining proves inherited descendants ended; missing/reaped coalition, unsupported layout, query error, identity mismatch or regressed counters remains unknown. It is never inferred from root absence, process-group polling, EOF or a model event. Completion does not attest delegated remote/XPC/tool effects: AssetQ must finish those separately.

The supervisor saves and reads back its sealed completion certificate before waiting for exact-generation cleanup. `reconcile` reads only the original operation and performs bounded native readback/cleanup; it never launches or replays input. Cleanup consumes its own intent before one exact-job bootout and requires successful acknowledgment and verified supervisor exit. Interrupted/unknown cleanup retains occupancy and original receipts. An already verified completion remains immutable across duplicate/reordered observations and host restarts. A same-key slot release is refused until protected native completion/cleanup is verified; it still attests the consumer's entire turn and requires the existing service acknowledgment. Existing unresolved/legacy launches cannot manufacture completion. Verified later boot retains the existing §3 recovery rule.

These native paths require staged PM qualification after merge-result CI. Portable model/transport checks are separate. Reuse the accepted AssetQ composed proof; no model/paid turn, crate/boundary replay, new grant, Full fallback, ordinary install, account/model/capacity change, attempt stripping or slot-refusal bypass is included.

## Consumer recipe

1. Reserve and observe an existing §3 slot for runtime `codex`, canonical project and the real consumer process identity. Keep its private release key and immutable job operation.
2. Call `prepare` with the original slot. Persist its private preparation digest and independently returned authority, revision and account before launch. No new grant, account or native input is created.
3. Spawn the adapter's `launch` command with piped stdio. Do not append `app-server` or native flags. AgentQ #186 owns its reusable transport integration; existing `AppServer::start` consumers retain their compatible path.
4. Invoke `observe` separately with the same request. Require verified-effective readback bound to the expected project, account, executable and operation before sending an app-server handshake or turn. Never publish private roots, homes, release keys or credentials.
5. Use native thread/turn observation and interruption; `cancel` seals input and requests exact native stop. Call `reconcile` on the same operation until protected completion/cleanup verifies. After all consumer/external tool effects also end, release the original slot and read back its acknowledgment. Unknown work stays occupied; never relaunch.
